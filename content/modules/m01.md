@@lesson monolith

A **monolith** is an application built, tested and deployed as a single unit. All of its features — users, orders, payments, notifications — live in one codebase, compile into one artifact and run in one process (or several identical copies of it). Most successful systems you have heard of started this way, and many still run this way.

## What is it?

Picture the Order Management System as a monolith. One Go binary contains every package:

~~~text title="shop/ (one repository, one go.mod, one binary)"
shop/
├── cmd/shop/main.go          ← one entry point
├── internal/users/           ← registration, login, profiles
├── internal/orders/          ← create, cancel, list orders
├── internal/payments/        ← charge cards, refunds
├── internal/notify/          ← emails
└── migrations/               ← ONE schema shared by every package
~~~

When a request arrives, the router calls a handler, which calls functions in other packages directly. Those calls are ordinary function calls: they take nanoseconds, cannot time out, and cannot be "half delivered". Every package reads and writes the same PostgreSQL database, usually through shared tables.

::diagram{id="monolith"}

## Why do teams build monoliths?

Because for most products they are the cheapest correct architecture.

- **One thing to run.** One deployment pipeline, one set of logs, one process to debug with a breakpoint.
- **ACID transactions for free.** Creating an order, charging a card and decrementing stock can commit together or not at all. In a distributed system you will spend weeks recreating this guarantee with sagas and outboxes.
- **Refactoring is cheap.** Your IDE renames a function across every caller; the compiler tells you what broke. Moving a responsibility between modules is a pull request, not a cross-team migration.
- **Performance.** No serialisation, no network hops. A request that touches five modules still finishes in one process.

:::rec Start with a monolith (usually)
For a new product with an uncertain domain and a team that fits in one room, a well-structured monolith is almost always the better first choice. You do not yet know where the stable boundaries are, and wrong service boundaries are far more expensive to fix than wrong package boundaries.
:::

## How does a request flow internally?

In Go, a monolith's request path is a chain of function calls on one goroutine:

```go title="internal/orders/service.go (monolith)"
func (s *Service) PlaceOrder(ctx context.Context, userID int64, items []Item) (*Order, error) {
	tx, err := s.db.Begin(ctx)
	if err != nil {
		return nil, err
	}
	defer tx.Rollback(ctx)

	user, err := s.users.Get(ctx, tx, userID) // in-process call, same transaction
	if err != nil {
		return nil, err
	}
	order, err := s.repo.Insert(ctx, tx, user.ID, items)
	if err != nil {
		return nil, err
	}
	if err := s.payments.Charge(ctx, tx, order); err != nil { // same transaction
		return nil, err // rollback undoes the order too
	}
	return order, tx.Commit(ctx)
}
```

Notice what you get without trying: a single transaction spans users, orders and payments, and an error anywhere rolls everything back.

## What goes wrong as it grows?

Monoliths rarely fail technically; they fail **organisationally**.

| Symptom | Root cause |
|---|---|
| Deploys take an hour and happen weekly | Every change, however small, ships the whole application and needs the whole test suite |
| "Who owns this table?" | Every module reads every table, so a schema change can break code anywhere |
| One team's bug takes down everyone | A memory leak or panic in `notify` kills the process that also serves checkout |
| Scaling is all-or-nothing | Search needs 20 CPUs and payments needs 2, but you can only scale the whole binary |
| Merge conflicts and release trains | 60 engineers committing to one deployable unit must coordinate |

The classic decay pattern is the **big ball of mud**: module boundaries erode because nothing enforces them. `orders` imports `payments/internal/helpers`, `notify` writes directly to `orders` tables, and soon every change is risky.

:::warn A monolith is not the same as a mess
Most of the pain above comes from a *poorly modular* monolith, not from being a monolith. A modular monolith — with enforced module boundaries and module-owned tables — keeps most benefits and removes most of the pain. You will compare all three styles interactively in [Monolith vs modular monolith vs microservices](#/lesson/m01/comparison).
:::

## Production best practices

- Enforce module boundaries with Go's `internal/` packages and import-linting (for example `depguard` in golangci-lint).
- Give each module its own tables and forbid cross-module joins in code review — it makes a later split possible.
- Scale horizontally behind a load balancer: run several identical, stateless instances.
- Measure deploy frequency and lead time. When they degrade because of coordination, not code, you have an organisational reason to split.

:::quiz concept="monolith"
Your monolith's checkout, catalogue and email features share one PostgreSQL database. Which property is **hardest** to keep if you split them into separate services?
- [ ] Horizontal scaling behind a load balancer
- [x] A single ACID transaction spanning checkout and catalogue changes
- [ ] Structured logging
- [ ] Running automated tests in CI
> In one process with one database, a transaction can span every module. Once data is split across services and databases, you lose cross-service atomicity and need patterns such as sagas and the transactional outbox.
:::

@@lesson microservices

**Microservices** structure an application as a set of small services, each owning one business capability and its data, deployed independently and communicating over the network.

## What is it?

Three properties define a microservice. If any one is missing, you have something else.

1. **Independently deployable.** The Order team can ship `order-service` at 3 p.m. without the User team doing anything. If two services must always deploy together, they are one service split into two processes — a *distributed monolith*.
2. **Owns its data.** Only `order-service` reads and writes `orders-db`. Others ask through its API or learn through its events.
3. **Organised around a business capability**, not a technical layer. "Orders" is a service; "the database layer" is not.

::diagram{id="microservices"}

In our Order Management System:

| Service | Capability | Owns | Exposes |
|---|---|---|---|
| User Service | Identity and profiles | `users-db` | `/v1/users`, `/v1/auth/login`, `/internal/users/:id` |
| Order Service | Order lifecycle | `orders-db` | `/v1/orders`, events `order.created`, `order.cancelled` |
| Notification Service | Customer communication | — | consumes order events |
| API Gateway | Edge policies | — | the public API |

## What microservices are *not*

- **Not "small" for its own sake.** A service sized by lines of code instead of capability ends up as a *nanoservice* that cannot do anything useful without calling five others.
- **Not a technology choice.** Kubernetes, gRPC and Kafka are tools you might use; they do not make a system microservices.
- **Not a free scalability upgrade.** A monolith with ten replicas scales fine for most workloads.

## Why do we need them? What problem do they solve?

The problems microservices solve are about **change at scale**:

- **Team autonomy.** Each team owns a service end to end — code, data, deploys, on-call — and can move without coordinating releases.
- **Independent scaling.** Order Service can run 12 replicas during a sale while User Service runs 3.
- **Fault isolation.** A crash in Notification Service delays emails; it does not take checkout down.
- **Technology fit.** A service with unusual needs (a search index, an ML model) can use a different stack without forcing it on everyone.

## How does it work internally?

The function call from the monolith lesson becomes a network call:

```go title="order-service/internal/service/order_service.go (excerpt)"
// We need User Service's answer to decide, so this call is synchronous.
cust, err := s.users.GetUser(ctx, in.UserID)
switch {
case errors.Is(err, model.ErrCustomerNotFound):
	return nil, false, model.ErrCustomerInactive
case err != nil:
	return nil, false, fmt.Errorf("%w: user-service: %v", model.ErrDependencyUnavailable, err)
case cust.Status != "active":
	return nil, false, model.ErrCustomerInactive
}
```

`GetUser` now involves DNS, TCP, HTTP, JSON, a remote process and its database. It can be slow, fail, time out, or succeed after you stopped waiting. Every line of resilience code in the [user client](#/playground?file=order-service/internal/client/user_client.go) exists because of that.

## What can go wrong?

:::danger The distributed monolith
Services that share a database, must deploy in lockstep, or call each other synchronously in long chains give you all the costs of distribution and none of the benefits. Watch for: shared tables, a "common" library every service must upgrade together, and release notes that say "deploy A before B".
:::

- **Latency adds up.** Five sequential calls at 20 ms each is 100 ms before any real work.
- **Availability multiplies down.** Four services at 99.9% in series give about 99.6%.
- **Debugging is harder.** One user action produces logs in five places; without correlation IDs and tracing you are guessing.
- **Data consistency becomes eventual.** You cannot `JOIN` across services or wrap them in one transaction.

## Production best practices

- Define services around business capabilities and bounded contexts (next lessons), not entities or layers.
- Give each service its own repository *or* clear ownership in a monorepo, its own pipeline and its own database.
- Prefer asynchronous events for side effects; keep synchronous calls for decisions you truly cannot make without.
- Invest in the platform first: CI/CD, observability, service templates. Microservices without automation are an operational burden.

:::quiz concept="microservices"
Two services can only be released together because they share several tables and one changes the schema the other reads. What is this?
- [ ] A modular monolith
- [x] A distributed monolith
- [ ] A bounded context
- [ ] Event sourcing
> Shared databases and lockstep deployments mean the services are not independently deployable — the defining property of microservices. You pay for distribution without getting autonomy.
:::

:::quiz concept="microservices"
Which property is **essential** for a service to be a microservice in the sense used in this course?
- [ ] It is written in a different language from other services
- [ ] It has fewer than 1,000 lines of code
- [x] It can be deployed without coordinating with other services
- [ ] It runs on Kubernetes
> Independent deployability (plus owning its data and representing a business capability) is the defining property. Size, language and platform are incidental.
:::

@@lesson comparison

There are three common ways to structure the same system. The difference between them is where boundaries are enforced: not at all, by the compiler, or by the network.

## The three architectures

| | Monolith | Modular monolith | Microservices |
|---|---|---|---|
| Deployable units | 1 | 1 | Many |
| Boundaries enforced by | Discipline (often not at all) | Compiler, linters, module APIs | Network and separate repos/databases |
| Data | One shared schema | One database, tables owned per module | Database per service |
| Cross-module call | Function call | Function call through a module API | HTTP / gRPC / messages |
| Transactions | ACID across everything | ACID across everything | Local only; sagas across services |
| Failure isolation | None | None (same process) | Per service |
| Operational cost | Low | Low | High |
| Team autonomy | Low | Medium | High |

## What to notice

- In the **monolith**, failing the notifications module crashes the shared process, so checkout fails too.
- In the **modular monolith**, boundaries are clean and refactoring stays cheap — but it is still one process, so a crash is still total.
- In **microservices**, a failed Notification Service only delays emails because the order path does not depend on it at request time. But the network adds latency to every request, and failing User Service *does* break order creation, because Order Service calls it synchronously.

## The modular monolith in Go

A modular monolith keeps one binary but makes each module a mini-service with a public API and private internals:

~~~text
shop/
├── cmd/shop/main.go
├── orders/
│   ├── api.go            ← the ONLY package other modules may import
│   └── internal/...      ← invisible outside orders/ (Go enforces this)
└── users/
    ├── api.go
    └── internal/...
~~~

```go title="orders/api.go"
// Package orders exposes the module's public surface.
package orders

// UserLookup is what orders needs from the users module. Declared here, by
// the consumer, so orders never imports users' internals.
type UserLookup interface {
	IsActive(ctx context.Context, userID int64) (bool, error)
}

type Module struct{ svc *internal.Service }

func New(db *pgxpool.Pool, users UserLookup) *Module { /* ... */ }

func (m *Module) PlaceOrder(ctx context.Context, in PlaceOrderInput) (*Order, error) {
	return m.svc.PlaceOrder(ctx, in)
}
```

Go's `internal/` directory rule means `users` physically cannot import `orders/internal`. Add a linter rule forbidding cross-module table access and you have most of the design discipline of microservices without the network.

:::rec Choosing between them
- Unclear domain, small team, new product → **modular monolith**.
- Several teams blocked by each other's releases, or parts with very different scaling and reliability needs → extract **microservices** along the module boundaries you have already proven.
- A plain, unstructured monolith is rarely a deliberate choice; it is what a modular monolith decays into without enforcement.
:::

:::quiz concept="modular-monolith"
What does a modular monolith give you that an unstructured monolith does not?
- [ ] Independent deployment of each module
- [ ] Fault isolation between modules
- [x] Enforced module boundaries that make a later extraction into services feasible
- [ ] A separate database per module
> It is still one deployable and one process, so it has neither independent deployment nor fault isolation. What it adds is enforced boundaries (APIs, `internal/` packages, module-owned tables) — the prerequisite for splitting safely later.
:::

@@lesson adoption

Organisations rarely adopt microservices for technical reasons alone. They adopt them because the way the system is built has started to limit how fast the company can change.

## Why organisations adopt microservices

**1. Team scaling and Conway's law.** "Organisations design systems that mirror their communication structure." Ten teams sharing one deployable unit spend their time coordinating. Giving each team a service aligned to a business capability lets them ship independently. Many companies now apply the *inverse Conway manoeuvre*: design the team structure you want, then let the architecture follow.

**2. Deployment frequency.** Small, independent deployables are faster to test and less risky to release. Teams go from weekly release trains to many deploys per day per service.

**3. Independent scaling.** Scale the hot path (orders during a sale) without scaling everything.

**4. Fault isolation.** A failing recommendation engine should not stop customers paying.

**5. Technology heterogeneity.** Use a column store for analytics or Python for an ML model without imposing it everywhere.

## What it costs

Every one of these benefits is bought with operational and cognitive cost.

| Cost | What it means in practice |
|---|---|
| Network unreliability | Every call needs timeouts, retries, circuit breakers and fallbacks |
| Data consistency | No cross-service transactions: sagas, outboxes, idempotency, eventual consistency |
| Observability | Logs, metrics and traces must be correlated across services |
| Operational overhead | Dozens of pipelines, dashboards, alerts, on-call rotations |
| Testing | Contract tests and environments with many moving parts |
| Latency | Network hops and serialisation on every interaction |
| Organisational | Clear ownership, API governance, platform teams |

:::warn The microservices premium
Martin Fowler calls this the *microservices premium*: a fixed cost you pay before getting any benefit. For small systems the premium outweighs the gains. The curve only crosses over when the complexity of coordinating people in one codebase exceeds the complexity of operating a distributed system.
:::

## When NOT to adopt them

- One or two teams, one product: use a modular monolith.
- You cannot yet deploy one application reliably and automatically.
- You have no centralised logging, metrics or tracing.
- The domain is still being discovered; boundaries would move every month.
- The motivation is "Netflix does it" or "it will scale better" without a measured scaling problem.

## A sensible migration path: the strangler fig

When the pain is real, migrate incrementally:

1. Put an API gateway (or routing layer) in front of the monolith.
2. Pick one capability with a clear boundary and real pain — often notifications or search.
3. Build it as a service; route its traffic through the gateway to the new service.
4. Move its data: the service owns new tables; synchronise or migrate history.
5. Delete the old code path. Repeat.

The monolith shrinks while the business keeps running — the way a strangler fig gradually replaces its host tree.

:::rule Measure before and after
Decide which outcomes you expect (deploy frequency, lead time for changes, change failure rate, time to restore — the DORA metrics) and measure them before migrating. Without a baseline you cannot tell whether the premium is paying off.
:::

:::quiz concept="adoption-tradeoffs"
A startup with six engineers wants to "use microservices so the product scales". Their single Go service handles 50 requests per second. What is the best advice?
- [ ] Split into one service per database table to maximise scalability
- [x] Keep a modular monolith, enforce module boundaries, and extract services later if team coordination becomes the bottleneck
- [ ] Move to Kubernetes first; the architecture will follow
- [ ] Rewrite in a faster language
> At this size the microservices premium outweighs the benefits, and 50 req/s is trivial for one process. A modular monolith keeps future extraction cheap.
:::

@@lesson boundaries

The hardest decision in a microservices architecture is not technical. It is **where to draw the lines**. Good boundaries make services independent; bad ones produce chatty, tightly coupled services that must change together.

## What is a service boundary?

A boundary decides which data and behaviour belong together. Inside a boundary, things change together and can be consistent with a local transaction. Across a boundary, communication goes through explicit contracts and consistency is eventual.

The goal is **high cohesion inside, loose coupling across**: most changes should touch one service.

## Domain-Driven Design in one page

Domain-Driven Design (DDD) gives us vocabulary and tools for finding boundaries.

- **Domain** — the business problem space: selling things online.
- **Subdomains** — parts of the business:
  - **Core** — what differentiates you (pricing, recommendations). Build in-house with your best people.
  - **Supporting** — necessary and specific to you, but not differentiating (order management).
  - **Generic** — solved problems (authentication, email delivery). Buy or use open source.
- **Ubiquitous language** — the precise terms domain experts and engineers share. If the business says "fulfilment", the code says `Fulfilment`, not `ShippingHelper2`.
- **Aggregate** — a cluster of objects treated as one unit for changes, with one root that enforces invariants. An `Order` with its `OrderItems` is an aggregate: you never modify an item without going through the order, which keeps the total correct.
- **Bounded context** — the boundary within which a model and its language are consistent (next lesson).

## Heuristics for drawing boundaries

| Heuristic | Ask |
|---|---|
| Business capability | Is this something the business does (take orders, bill customers), and would one team own it? |
| Data ownership | Which data does this capability create and change? It should own that data. |
| Change frequency | Which code changes together in your git history? Keep it together. |
| Transactional consistency | Which invariants must hold *immediately*? Those belong in one aggregate, in one service. |
| Communication | Would the split create a call on every request? A chatty boundary is in the wrong place. |
| Team structure | Can one team own it end to end without depending on another team's release? |

:::tip Event storming
A practical workshop technique: put domain experts and engineers in a room, write every business event on an orange sticky note (`OrderPlaced`, `PaymentCaptured`, `ParcelShipped`), arrange them on a timeline, then look for clusters and the places where language changes. Those seams are candidate boundaries.
:::

## Anti-patterns

- **Entity services.** `CustomerService`, `ProductService`, `OrderService` as thin CRUD wrappers over tables. Every business operation then needs all three, so they must be called synchronously together — a distributed monolith.
- **Layer services.** A "data service" or "validation service" splits by technical layer, so every feature change touches several services.
- **Nanoservices.** One function per service. The network overhead exceeds the work.

## How it looks in Go

The aggregate enforces its invariants; nothing outside it can put it into an invalid state.

```go title="order-service/internal/model/order.go (excerpt)"
// transitions is the state machine. Anything not listed is illegal, which
// makes the allowed lifecycle explicit and testable.
var transitions = map[Status][]Status{
	StatusPending:   {StatusConfirmed, StatusCancelled},
	StatusConfirmed: {StatusShipped, StatusCancelled},
	StatusShipped:   {StatusDelivered},
}

func (s Status) CanTransitionTo(next Status) bool {
	for _, allowed := range transitions[s] {
		if allowed == next {
			return true
		}
	}
	return false
}
```

The `Order` aggregate and its rules live entirely in Order Service. User Service never decides whether an order may be cancelled.

- [x] A `ProductService`, `PriceService` and `StockService` that every checkout request must call synchronously, one after another
- [ ] A Notification service that consumes order events
- [ ] A Search service fed by product change events
> Splitting by entity forces every business operation to call all of them synchronously. Boundaries should follow capabilities so that most operations stay inside one service.
:::

:::quiz concept="ddd"

- [ ] A service that combines data from several other services
- [x] A cluster of objects changed as one unit through a root that enforces invariants

@@lesson bounded-contexts

The same word means different things in different parts of a business. A **bounded context** is the boundary inside which one model, and one meaning for each term, applies.

## What is it?

Consider "customer":

- In **Sales**, a customer has a cart, a loyalty tier and marketing preferences.
- In **Shipping**, the relevant concept is a *recipient*: a name, an address, a phone number for the courier.
- In **Billing**, it is a *payer*: billing address, VAT number, payment methods.

Forcing all of these into one `Customer` model creates a 60-field table that every team edits and nobody understands. Bounded contexts let each part of the business keep a model that fits its job.

::diagram{id="bounded-contexts"}

## Why do we need it?

- **Clarity.** Inside a context, terms are unambiguous; code reads like the business.
- **Independence.** Shipping can add `delivery_instructions` without a meeting with Sales.
- **Natural service boundaries.** A bounded context is often the right size for one service (sometimes a few).

## How contexts relate: context mapping

Contexts still need to collaborate. DDD names the common relationships:

| Pattern | Meaning | Example |
|---|---|---|
| Customer–Supplier | Upstream team plans for downstream needs | User Service (upstream) adds the `status` field Order Service needs |
| Conformist | Downstream adopts the upstream model as-is | Using a payment provider's API shapes directly |
| Anti-corruption layer (ACL) | Downstream translates the upstream model into its own | Shipping converts Sales' `Customer` into its `Recipient` |
| Published language | A shared, documented exchange format | Versioned JSON event schemas |
| Open host service | Upstream offers a well-defined protocol for many consumers | A public, versioned REST API |

## An anti-corruption layer in Go

Order Service does not import User Service's model. It defines its own minimal view and translates at the edge:

```go title="order-service/internal/model/order.go (excerpt)"
// Customer is what Order Service needs to know about a user. It is a local,
// minimal view of another service's data — not a shared model.
type Customer struct {
	ID     int64  `json:"id"`
	Email  string `json:"email"`
	Status string `json:"status"`
}
```

If User Service renames fields or splits `name` into `given_name` and `family_name`, only the translation in the client changes; the rest of Order Service is untouched. Compare with sharing a `common/models` package between services — every model change would force every service to upgrade together.

:::warn Shared model libraries
A shared "domain models" module is one of the most common ways teams accidentally rebuild a distributed monolith. Share *contracts* (API schemas, event schemas) — not internal domain types.
:::

## What can go wrong?

- Contexts drawn around org charts that will change next quarter.
- Translations scattered everywhere instead of concentrated in one ACL package.
- "Integration by database": two contexts reading the same table, which silently merges their models.

:::quiz concept="bounded-contexts"
Shipping needs a customer's address from Sales. Which approach best protects Shipping's model?
- [ ] Import Sales' `Customer` struct from a shared Go module
- [ ] Read the Sales `customers` table directly
- [x] Translate Sales data into Shipping's own `Recipient` type in an anti-corruption layer
- [ ] Ask Sales to add shipping fields to its `Customer` model
> An ACL keeps the foreign model at the edge. Shipping depends only on the contract, and its internal model can evolve independently.
:::

@@lesson database-per-service

**Database per service** means each service's persistent data is private to that service and accessible only through its API or events.

## What is it?

`order-service` owns `orders-db`; `user-service` owns `users-db`. They might be separate PostgreSQL instances, separate databases on a shared cluster, or separate schemas with separate credentials. The essential property is not the physical layout; it is that **no other service can read or write the data directly**.

::diagram{id="db-per-service"}

## Why do we need it?

Shared databases are the strongest form of coupling between services:

- **Schema coupling.** If Order Service reads `users.full_name`, User Service cannot rename that column without breaking another team's service.
- **Runtime coupling.** A slow analytical query from one service locks rows or exhausts connections for another.
- **Deployment coupling.** Migrations must be coordinated across every service that touches a table.
- **Hidden contracts.** Nobody knows who depends on which column until something breaks in production.

Owning data lets a service change its storage — add an index, denormalise, move to another engine — without asking anyone.

## How do services then share data?

| Need | Technique | Trade-off |
|---|---|---|
| Ask a question at request time | Call the owner's API (`GET /internal/users/42`) | Runtime dependency; needs timeouts and fallbacks |
| Combine data for a screen | **API composition**: the gateway or a BFF calls several services and merges | More calls, partial failures |
| Read a lot of another service's data | Keep a **local replica** updated from events (`user.updated`) | Eventually consistent, but no runtime dependency |
| Complex queries across many services | **CQRS read model** fed by events from all of them | Extra infrastructure, eventual consistency |

## How we implement it

In our Compose file every service gets its own database container and credentials:

```yaml title="docker-compose.yml (excerpt)"
user-service:
  environment:
    DATABASE_URL: postgres://users:${USERS_DB_PASSWORD}@users-db:5432/users?sslmode=disable
order-service:
  environment:
    DATABASE_URL: postgres://orders:${ORDERS_DB_PASSWORD}@orders-db:5432/orders?sslmode=disable
```

And the orders schema deliberately has no foreign key to users:

```sql title="order-service/migrations/000001_create_orders.up.sql (excerpt)"
CREATE TABLE orders (
    id           BIGSERIAL    PRIMARY KEY,
    -- user_id is NOT a foreign key: users live in another service's database.
    user_id      BIGINT       NOT NULL,
    ...
);
```

:::rule Credentials enforce ownership
Agreements in a wiki do not prevent shortcuts under deadline pressure. Separate database users (or instances) mean another service *cannot* connect. Treat any request for "read-only access to your tables" as a request for an API or an event.
:::

## What can go wrong?

- **No referential integrity across services.** An order can reference a user that was deleted. Handle it in the domain (soft-delete users, react to `user.deleted` events).
- **Reporting gets harder.** Analysts can no longer join everything in one query; feed a data warehouse from events or change data capture.
- **Consistency is eventual.** A local replica lags behind the source by milliseconds to seconds; design UX accordingly.

:::quiz concept="database-per-service"
Order Service needs the customer's name on every order confirmation page. Which option keeps services decoupled at request time?
- [ ] Join `orders` with `users` across databases using a foreign data wrapper
- [ ] Give Order Service read-only credentials to `users-db`
- [x] Store a small local copy of the customer's name in Order Service, updated from `user.updated` events
- [ ] Merge the two databases
> A local, event-driven replica removes the runtime dependency and respects ownership. It may lag briefly — usually acceptable for a display name.
:::

@@lesson distributed-fundamentals

A distributed system is one in which the failure of a computer you didn't even know existed can render your own computer unusable. That joke (Leslie Lamport's) is the best one-line summary of what changes when a function call becomes a network call.

## Partial failure

In one process, an operation either happens or it doesn't. Across a network there is a third outcome: **you don't know**. A request can be lost on the way, processed and the response lost, or still be running when you give up.

::diagram{id="partial-failure"}

Everything in Module 07 — timeouts, retries, idempotency, sagas, outboxes — exists to make systems correct in the presence of that third outcome.

## The eight fallacies of distributed computing

Engineers new to distributed systems implicitly assume:

| Fallacy | Reality | Consequence in code |
|---|---|---|
| The network is reliable | Packets drop, connections reset | Retries with backoff; idempotent operations |
| Latency is zero | Cross-zone calls take ~1 ms, cross-region ~70 ms | Avoid chatty calls; batch; cache |
| Bandwidth is infinite | Large payloads saturate links | Paginate; compress; avoid fetching what you don't need |
| The network is secure | Traffic can be observed or forged | TLS/mTLS; authenticate service calls |
| Topology doesn't change | Pods come and go every deploy | Service discovery; don't hard-code IPs |
| There is one administrator | Many teams, many configs | Explicit contracts; defensive clients |
| Transport cost is zero | Serialisation and network cost CPU and money | Efficient encodings (protobuf) where it matters |
| The network is homogeneous | Mixed versions, proxies, clients | Backward-compatible APIs; versioning |

## Latency you should know

| Operation | Typical time |
|---|---|
| Go function call | ~1–10 ns |
| Read 1 MB from memory | ~3 µs |
| Redis GET in the same zone | ~0.2–0.5 ms |
| Simple indexed Postgres query | ~0.5–2 ms |
| HTTP call to another service, same zone | ~1–5 ms |
| Cross-region round trip | ~60–150 ms |

A request that makes ten sequential service calls has spent 10–50 ms on the network before doing anything useful.

## CAP and PACELC

**CAP**: when a network **P**artition happens, a distributed data store must choose between **C**onsistency (every read sees the latest write, or errors) and **A**vailability (every request gets a non-error response, possibly stale). Partitions are not optional, so the real choice is C or A *during a partition*.

**PACELC** extends this: if there is a **P**artition, choose **A** or **C**; **E**lse (normal operation), choose between **L**atency and **C**onsistency. Even when the network is fine, stronger consistency costs coordination, and coordination costs latency.

In practice:

- PostgreSQL with synchronous replication leans to C.
- A Redis cache in front of it leans to A and L: fast, sometimes stale.
- Our Order Service local replica of customer names is AP: always available, eventually consistent.

## Delivery guarantees

| Guarantee | Meaning | How it is achieved |
|---|---|---|
| At most once | Never duplicated, may be lost | Fire and forget, no retries |
| At least once | Never lost, may be duplicated | Retries + acknowledgements |
| Exactly once (effectively) | Processed once from the business's view | At-least-once delivery + idempotent processing |

True exactly-once *delivery* is impossible in general. Systems achieve exactly-once *effects* by making the receiving side idempotent — which is why our Notification Service remembers processed event IDs.

## Time and ordering

Clocks on different machines drift, sometimes by seconds. Never decide "which happened first" across services by comparing wall-clock timestamps. Use:

- a single writer per piece of data (the owning service decides),
- version numbers (optimistic concurrency, as in Order Service's `version` column),
- per-key ordering from the broker (Kafka partitions by key).

:::tip The mindset shift
Write every remote call assuming it may fail, be slow, or succeed without you knowing. Then ask: what does the user see, and is the data still correct? The rest of this course is a toolbox of answers.
:::

- [x] Availability
