@@lesson project-structure

Go has very few rules about project layout, which is both a gift and a trap. This lesson shows the structure used by every service in this course and, more importantly, the reasons behind it.

## What is a module, what is a package?

- A **module** is a versioned unit of code with a `go.mod` file: `github.com/microverse/order-management/order-service`. Each of our services is its own module, so each can upgrade dependencies and release independently.
- A **package** is a directory of `.go` files compiled together. Its name is the last path element (`repository`, `service`). Packages are the unit of encapsulation: identifiers starting with a capital letter are exported, everything else is private to the package.

```text title="order-service/go.mod"
module github.com/microverse/order-management/order-service

go 1.26

require (
	github.com/gin-gonic/gin v1.12.0
	github.com/jackc/pgx/v5 v5.12.0
	github.com/rabbitmq/amqp091-go v1.16.0
	github.com/sony/gobreaker/v2 v2.4.0
	...
)
```

## The layout

~~~text title="order-service/"
order-service/
├── cmd/server/main.go        ← composition root: config, wiring, startup, shutdown
├── internal/
│   ├── config/               ← load + validate environment
│   ├── model/                ← domain types, state machine, domain errors (no deps)
│   ├── handler/              ← HTTP: decode, validate, map errors → status codes
│   ├── service/              ← business rules; declares the interfaces it needs
│   ├── repository/           ← SQL via pgx; implements service.Repository
│   ├── client/               ← calls to other services; implements service.UserDirectory
│   ├── events/               ← outbox relay + RabbitMQ publisher
│   ├── middleware/           ← request ID, logging, recovery, identity
│   └── reqctx/               ← request-scoped context helpers
├── migrations/               ← versioned SQL
├── Dockerfile
└── go.mod
~~~

::diagram{id="go-layers"}

## Why this shape?

**`cmd/`** holds entry points. A service may grow a second binary (a migration tool, a worker), each in `cmd/<name>/main.go`. Keeping `main` small and focused on wiring makes everything else testable.

**`internal/`** is enforced by the compiler: packages under `order-service/internal/...` can only be imported by code inside `order-service/`. Nobody can import your repository from another module, so you are free to change it.

**Layering by responsibility:**

| Layer | Knows about | Must not know about |
|---|---|---|
| `handler` | HTTP, JSON, status codes, the service interface | SQL, Redis, RabbitMQ |
| `service` | business rules, domain types, interfaces it declares | HTTP, SQL, concrete clients |
| `repository` | SQL, pgx, transactions | HTTP, other services |
| `model` | nothing (pure types) | everything else |

Dependencies point **inward**: handler → service → model; repository → model. The service never imports the repository; `main` connects them.

:::rec Package by responsibility, then by feature
For a service of this size, layer packages (`handler`, `service`, `repository`) are clear. When a service grows many features, group by feature first (`internal/orders/...`, `internal/refunds/...`) with layers inside. Avoid packages named `utils`, `common` or `helpers` — they become dumping grounds with unclear ownership.
:::

## What can go wrong?

- **Import cycles.** Go forbids them. If `service` imports `handler` and `handler` imports `service`, the build fails — usually a sign that a type is in the wrong layer. Move shared types to `model`.
- **A "shared" module across services.** It looks like reuse, but every change forces every service to upgrade in lockstep. Duplicate small helpers (our `reqctx` exists in both services on purpose).
- **Fat `main.go`.** Business logic in `main` is untestable. `main` should read like a wiring diagram.

## Production best practices

- One `go.mod` per independently deployable service.
- Run `go vet`, `staticcheck` and `golangci-lint` in CI; add `govulncheck` for dependency vulnerabilities.
- Keep `cmd/*/main.go` under ~200 lines; push logic into `internal/`.

:::quiz concept="go-structure"
Another team's service imports `github.com/acme/order-service/internal/repository`. What happens?
- [ ] It compiles but logs a deprecation warning
- [x] It fails to compile: `internal` packages can only be imported from within the module tree that contains them
- [ ] It compiles if both modules use the same Go version
- [ ] It compiles but panics at runtime
> The Go toolchain enforces `internal/` visibility. This protects your freedom to change internals without breaking other teams.
:::

@@lesson structs-interfaces

Go has no classes or inheritance. It has **structs** for data, **methods** for behaviour, **embedding** for composition and **interfaces** for abstraction. Used well, these make services small, explicit and easy to test.

## Structs and methods

```go
type Order struct {
	ID         int64     `json:"id"`
	UserID     int64     `json:"user_id"`
	Status     Status    `json:"status"`
	TotalCents int64     `json:"total_cents"` // money in integer cents, never float64
	Items      []Item    `json:"items"`
	Version    int       `json:"version"`
	CreatedAt  time.Time `json:"created_at"`
}

// Value receiver: does not modify the order.
func (o Order) IsCancellable() bool { return o.Status.CanTransitionTo(StatusCancelled) }

// Pointer receiver: modifies the order.
func (o *Order) Cancel() error {
	if !o.IsCancellable() {
		return ErrInvalidTransition
	}
	o.Status = StatusCancelled
	return nil
}
```

**Pointer or value receiver?** Use a pointer when the method mutates the receiver, when the struct is large, or when it contains a `sync.Mutex` (which must not be copied). Be consistent within a type.

Struct tags (`json:"id"`) are metadata read by packages like `encoding/json` and Gin's validator. `json:"-"` excludes a field — our `User.PasswordHash` uses it so hashes never leak into responses or caches.

## Interfaces are satisfied implicitly

A type implements an interface simply by having the methods. There is no `implements` keyword. This has a powerful consequence: **the consumer can define the interface**.

```go title="order-service/internal/service/order_service.go (excerpt)"
// Repository is the persistence this service needs.
type Repository interface {
	FindByIdempotencyKey(ctx context.Context, userID int64, key string) (*model.Order, string, error)
	CreateWithOutbox(ctx context.Context, p model.CreateOrderParams) (*model.Order, bool, error)
	GetByID(ctx context.Context, id int64) (*model.Order, error)
	ListByUser(ctx context.Context, userID int64, limit int, beforeID int64) ([]model.Order, error)
	UpdateStatus(ctx context.Context, o *model.Order, to model.Status, eventType string) error
}

// UserDirectory answers questions about customers.
type UserDirectory interface {
	GetUser(ctx context.Context, id int64) (*model.Customer, error)
}
```

`*repository.OrderRepository` satisfies `Repository` without importing the `service` package or knowing the interface exists. A fake in a test satisfies it too.

## Idioms that keep interfaces useful

- **Accept interfaces, return structs.** Constructors return concrete types (`*OrderRepository`); functions that consume dependencies accept interfaces.
- **Small interfaces.** `io.Reader` has one method and is used everywhere. An interface with 20 methods is hard to fake and couples consumers to everything.
- **Define interfaces where they are used**, not next to the implementation. The service package declares `Repository`; the repository package does not export an interface "for others to use".
- **Don't create an interface until you have two implementations** — and a test fake counts.

## Embedding for composition

```go
type statusRecorder struct {
	http.ResponseWriter // embedded: all its methods are promoted
	status int
}

func (r *statusRecorder) WriteHeader(code int) {
	r.status = code
	r.ResponseWriter.WriteHeader(code) // call the embedded implementation
}
```

`statusRecorder` *is* an `http.ResponseWriter` (it has all the methods) and overrides one. This is how middleware captures status codes. Embedding is composition, not inheritance: there is no `super`, and the embedded value does not know about the outer one.

## What can go wrong?

:::warn The nil interface trap
An interface holding a typed nil pointer is **not** nil.

```go
func find() error {
	var err *MyError = nil
	return err // returns a non-nil error interface wrapping a nil *MyError!
}
```

Always `return nil` explicitly for "no error".
:::

- Copying a struct that contains a `sync.Mutex` (go vet catches this).
- Using `any` (`interface{}`) to avoid designing types — you lose compile-time checks.

:::quiz concept="interfaces"
Where should the `Repository` interface used by `OrderService` be declared?
- [ ] In the `repository` package, next to the implementation
- [x] In the `service` package, where it is consumed
- [ ] In a shared `interfaces` package used by all services
- [ ] In `main.go`
> Go interfaces are satisfied implicitly, so the consumer can declare exactly what it needs. That keeps the interface small and avoids the implementation package dictating the abstraction.
:::

@@lesson dependency-injection

**Dependency injection** (DI) means a component receives the things it depends on instead of creating or finding them itself. In Go you rarely need a framework: constructors and interfaces are enough.

## What problem does it solve?

Compare:

```go
// Hidden dependencies: impossible to test without a real database and network.
func CreateOrder(in Input) (*Order, error) {
	db := globalDB                                 // package-level global
	resp, err := http.Get("http://user-service/...") // hard-coded client
	...
}
```

```go
// Explicit dependencies: anything satisfying the interfaces can be passed in.
type OrderService struct {
	repo  Repository
	users UserDirectory
	log   *slog.Logger
}

func NewOrderService(repo Repository, users UserDirectory, log *slog.Logger) *OrderService {
	return &OrderService{repo: repo, users: users, log: log}
}
```

The second version tells you everything it needs in its constructor signature, has no global state, and can be tested with fakes.

## Wiring in the composition root

`main()` is the only place that knows every concrete type:

```go title="order-service/cmd/server/main.go (excerpt)"
// Wiring
repo := repository.NewOrderRepository(pool)
users := client.NewUserClient(client.UserClientConfig{
	BaseURL:        cfg.UserServiceURL,
	AttemptTimeout: cfg.UserTimeout,
	MaxAttempts:    cfg.UserMaxAttempts,
	BaseBackoff:    100 * time.Millisecond,
}, log)
svc := service.NewOrderService(repo, users, log)
publisher := events.NewRabbitPublisher(cfg.RabbitURL, cfg.Exchange)
relay := events.NewRelay(repo, publisher, cfg.RelayInterval, cfg.RelayBatch, log)
```

Read top to bottom, this is the dependency graph of the service.

## Testing with fakes

Because `OrderService` depends on interfaces, its tests need no database:

```go title="order-service/internal/service/order_service_test.go (excerpt)"
func TestCreateOrderIsIdempotent(t *testing.T) {
	users := &fakeUsers{}
	svc, _ := newService(users)

	first, replayed, err := svc.CreateOrder(context.Background(), input)
	if err != nil || replayed {
		t.Fatalf("first create: replayed=%v err=%v", replayed, err)
	}

	second, replayed, err := svc.CreateOrder(context.Background(), input)
	if err != nil || !replayed || second.ID != first.ID {
		t.Fatalf("retry: id=%d replayed=%v err=%v", second.ID, replayed, err)
	}
	if users.calls != 1 {
		t.Fatalf("user-service called %d times; a replay should not call dependencies", users.calls)
	}
}
```

These tests run in milliseconds and pin down business rules precisely. Integration tests (against a real Postgres in a container) then cover the repository.

## When to use a DI framework

| Tool | Approach | Use when |
|---|---|---|
| Manual wiring | Constructors in `main` | Almost always — up to dozens of components |
| `google/wire` | Compile-time code generation | Very large graphs where manual wiring becomes noisy |
| `uber-go/fx` | Runtime reflection, lifecycle hooks | You want managed start/stop hooks across many modules |

:::rec Prefer explicit wiring
Manual wiring is boring, and boring is good: it is greppable, debuggable and has no magic. Reach for a framework only when the wiring itself becomes a maintenance problem.
:::

## What can go wrong?

- **Service locators** (`container.Get("db")`) hide dependencies just like globals do.
- **Constructors that do I/O** (connect to a database inside `NewOrderService`) make construction slow and failure-prone. Connect in `main`, inject the connection.
- **Injecting through `context.Context`** — context values are for request-scoped data, not dependencies.

:::quiz concept="dependency-injection"
Why does `OrderService` accept a `UserDirectory` interface rather than constructing a `*client.UserClient` itself?
- [ ] Interfaces are faster than structs in Go
- [x] So tests (and main) can supply any implementation, making dependencies explicit and the service testable without a network
- [ ] Because Go does not allow structs as struct fields
- [ ] To avoid importing the `net/http` package
> Constructor injection makes dependencies visible and swappable. The production wiring passes the real HTTP client; tests pass an in-memory fake.
:::

@@lesson errors

Go treats errors as ordinary values returned from functions. That makes failure handling explicit — every call site decides what to do — and it is the foundation for mapping failures to the right HTTP status in a service.

## What is an error?

```go
type error interface {
	Error() string
}
```

Functions return `(result, error)`. The caller checks `err != nil` immediately.

## Adding context: wrapping

Each layer adds what it knows, using `%w` to keep the original error inspectable:

```go title="order-service/internal/repository/order_repository.go (excerpt)"
if err := tx.QueryRow(ctx, `INSERT INTO orders ... RETURNING id, version, created_at, updated_at`,
	o.UserID, o.Status, o.TotalCents, o.Currency,
).Scan(&o.ID, &o.Version, &o.CreatedAt, &o.UpdatedAt); err != nil {
	return nil, false, fmt.Errorf("insert order: %w", err)
}
```

The final message reads like a stack of reasons: `create order: insert order: write failed: connection reset by peer`.

## Inspecting errors: `errors.Is` and `errors.As`

- **Sentinel errors** are package-level values compared by identity:

```go title="order-service/internal/model/order.go (excerpt)"
var (
	ErrNotFound              = errors.New("order not found")
	ErrInvalidTransition     = errors.New("invalid status transition")
	ErrConcurrentUpdate      = errors.New("order was modified concurrently")
	ErrDependencyUnavailable = errors.New("a required dependency is unavailable")
)
```

`errors.Is(err, model.ErrNotFound)` walks the wrap chain, so it still matches after `fmt.Errorf("get order: %w", err)`.

- **Typed errors** carry data and are extracted with `errors.As`:

```go
var pgErr *pgconn.PgError
if errors.As(err, &pgErr) && pgErr.Code == "23505" { // unique_violation
	return model.ErrEmailTaken
}
```

## Mapping domain errors to HTTP

The handler is the only place that knows about status codes:

```go title="order-service/internal/handler/order_handler.go (excerpt)"
switch {
case errors.Is(err, model.ErrValidation):
	problem(c, http.StatusUnprocessableEntity, "Validation failed", err.Error())
case errors.Is(err, model.ErrNotFound):
	problem(c, http.StatusNotFound, "Order not found", "")
case errors.Is(err, model.ErrInvalidTransition):
	problem(c, http.StatusConflict, "Invalid status transition", err.Error())
case errors.Is(err, gobreaker.ErrOpenState):
	c.Header("Retry-After", "30")
	problem(c, http.StatusServiceUnavailable, "Service temporarily unavailable", "")
default:
	l.ErrorContext(ctx, "request failed", "err", err)
	problem(c, http.StatusInternalServerError, "Internal Server Error", "")
}
```

Every response uses the RFC 9457 *problem details* format (`application/problem+json`), so clients handle errors uniformly across services.

## Status codes are part of the contract

| Situation | Status | Should the client retry? |
|---|---|---|
| Invalid input | 400 / 422 | No — fix the request |
| Not authenticated / not allowed | 401 / 403 | No |
| Not found | 404 | No |
| Conflict (state, concurrency) | 409 | Maybe after re-reading |
| Rate limited | 429 + `Retry-After` | Yes, after the delay |
| Our bug | 500 | Maybe (if idempotent) |
| Dependency down / overloaded | 503 + `Retry-After` | Yes, with backoff |
| Upstream timed out | 504 | Yes, if idempotent |

:::rule Never leak internals
Return generic messages for unexpected errors. SQL fragments, hostnames and stack traces in responses help attackers. Log the full error server-side with the request ID instead.
:::

## What can go wrong?

- **Log and return.** Logging an error and also returning it produces the same failure five times in the logs. Either handle it (log, fall back) *or* return it — once.
- **Losing the chain** with `%v` instead of `%w`, which breaks `errors.Is` upstream.
- **Panics for expected failures.** Reserve `panic` for programmer errors; recover at the top of each request (our Recovery middleware) so one bad request cannot crash the process.
- **Comparing error strings.** `err.Error() == "not found"` breaks the moment someone rewords a message.

:::quiz concept="error-handling"
A repository returns `fmt.Errorf("get order 42: %w", model.ErrNotFound)`. Which check in the handler correctly detects "not found"?
- [ ] `err == model.ErrNotFound`
- [ ] `strings.Contains(err.Error(), "not found")`
- [x] `errors.Is(err, model.ErrNotFound)`
- [ ] `err.(model.ErrNotFound)`
> `errors.Is` unwraps the chain created by `%w`. Direct equality fails because the error was wrapped; string matching is brittle.
:::

@@lesson context

`context.Context` carries **deadlines, cancellation signals and request-scoped values** across API boundaries and goroutines. In a service, it is how "the client went away" or "we've run out of time" reaches the SQL query that is still running.

## What is it?

```go
type Context interface {
	Deadline() (deadline time.Time, ok bool)
	Done() <-chan struct{} // closed when the context is cancelled or times out
	Err() error           // context.Canceled or context.DeadlineExceeded
	Value(key any) any
}
```

Contexts form a tree. Deriving a child (`WithTimeout`, `WithCancel`, `WithValue`) never affects the parent, but cancelling a parent cancels every child.

::diagram{id="context-propagation"}

## Why do we need it?

Without propagation, work continues after nobody wants the result:

1. The gateway times out after 2 seconds and returns 504.
2. Order Service is still waiting on User Service, which is still running a query.
3. Multiply by thousands of requests: CPU, goroutines and database connections are wasted on answers nobody will read — exactly when the system is already struggling.

With propagation, cancellation flows down the whole chain and every layer stops.

## How it flows through our service

1. **net/http** creates a context per request and cancels it when the client disconnects or the handler returns.
2. **Gin** exposes it as `c.Request.Context()`.
3. **Handlers** pass it to the service; the service passes it to repositories and clients.
4. **pgx** watches `ctx.Done()` and sends a cancel request to Postgres.
5. **http.Client** aborts the outbound request when the context ends.

```go title="order-service/internal/client/user_client.go (excerpt)"
func (c *UserClient) getOnce(ctx context.Context, id int64) (*model.Customer, error) {
	ctx, cancel := context.WithTimeout(ctx, c.cfg.AttemptTimeout) // per-attempt deadline
	defer cancel()                                                // always release resources

	req, err := http.NewRequestWithContext(ctx, http.MethodGet,
		c.cfg.BaseURL+"/internal/users/"+strconv.FormatInt(id, 10), nil)
	...
}
```

`WithTimeout` here creates a deadline that is the **earlier** of the parent's deadline and now + 800 ms. If the gateway's 2-second budget is nearly spent, the attempt gets only what is left.

And when waiting between retries:

```go
select {
case <-ctx.Done():
	timer.Stop()
	return nil, ctx.Err() // the caller gave up — stop retrying
case <-timer.C:
}
```

## Rules

:::rule Context conventions
- `ctx context.Context` is the **first parameter** of any function that does I/O or may block.
- **Never store a context in a struct**; pass it per call.
- **Always call `cancel`** returned by `WithTimeout`/`WithCancel` (use `defer`), or you leak timers.
- **Never pass `nil`**; use `context.Background()` at the top level or `context.TODO()` while refactoring.
:::

## Context values: use sparingly

Values are for **request-scoped data that crosses API boundaries**: request IDs, the authenticated identity, a request-scoped logger. They are *not* for optional parameters or dependencies.

```go title="order-service/internal/reqctx/reqctx.go (excerpt)"
type ctxKey int // unexported key type: no collisions with other packages

const requestIDKey ctxKey = 0

func WithRequestID(ctx context.Context, id string) context.Context {
	return context.WithValue(ctx, requestIDKey, id)
}

func RequestID(ctx context.Context) string {
	id, _ := ctx.Value(requestIDKey).(string)
	return id
}
```

## What can go wrong?

- **Background work tied to the request context.** If a handler starts a goroutine with `c.Request.Context()`, the goroutine is cancelled when the response is sent. Use `context.WithoutCancel(ctx)` (Go 1.21+) to keep values but drop cancellation, and give it its own timeout.
- **Ignoring `ctx` in loops.** Long loops should check `ctx.Err()` periodically.
- **Deadline too long at the edge.** If the gateway allows 30 seconds, every layer below can hold resources for 30 seconds.

:::quiz concept="context"
A handler starts `go sendAnalytics(c.Request.Context(), event)` and returns 201. Analytics events are often missing. Why?
- [ ] Goroutines cannot use contexts
- [x] The request context is cancelled once the handler returns, so the analytics call is aborted
- [ ] Gin copies the context, losing its values
- [ ] `go` statements are ignored inside handlers
> The request context ends with the request. Detach it for background work with `context.WithoutCancel(ctx)` plus its own timeout — or better, publish an event and let a worker handle it.
:::

@@lesson concurrency

Goroutines and channels make concurrency cheap to write. Making it **correct and bounded** is the real skill: unbounded goroutines and leaks are a classic cause of production outages in Go services.

## Goroutines

A goroutine is a function running concurrently, scheduled by the Go runtime onto OS threads. It starts with a few kilobytes of stack, so you can run hundreds of thousands. net/http already runs each request in its own goroutine.

## Channels

A channel is a typed conduit for passing values between goroutines.

- **Unbuffered** (`make(chan Job)`): a send blocks until a receiver takes it — a synchronisation point.
- **Buffered** (`make(chan Job, 100)`): sends block only when the buffer is full — a bounded queue.
- **Closing** a channel signals "no more values"; `for v := range ch` ends when it is closed and drained. Only the sender closes.

`select` waits on several channel operations at once and is how you combine work with cancellation:

```go
select {
case job := <-jobs:
	process(job)
case <-ctx.Done():
	return ctx.Err()
}
```

## The worker pool

The most useful pattern: a fixed number of workers consume from a queue. It bounds concurrency (and therefore memory, connections and load on dependencies).

```go
func ProcessAll(ctx context.Context, ids []int64, workers int, fn func(context.Context, int64) error) error {
	jobs := make(chan int64)
	g, ctx := errgroup.WithContext(ctx) // golang.org/x/sync/errgroup

	// Producer
	g.Go(func() error {
		defer close(jobs)
		for _, id := range ids {
			select {
			case jobs <- id:
			case <-ctx.Done():
				return ctx.Err()
			}
		}
		return nil
	})

	// Workers
	for i := 0; i < workers; i++ {
		g.Go(func() error {
			for id := range jobs {
				if err := fn(ctx, id); err != nil {
					return err // cancels ctx for everyone
				}
			}
			return nil
		})
	}
	return g.Wait() // first error, after all goroutines exit
}
```

`errgroup` gives you three things at once: a `WaitGroup`, error propagation, and cancellation of siblings on the first failure.

Experiment with the knobs below: see how worker count and queue size change throughput and memory, and what happens when a job blocks forever.

::widget{name="worker-pool"}

## Mutexes or channels?

"Share memory by communicating" is a guideline, not a law.

| Use a mutex when | Use channels when |
|---|---|
| Protecting a small piece of shared state (a map, a counter) | Passing ownership of data between goroutines |
| The critical section is short | Coordinating pipelines, fan-out/fan-in, worker pools |
| Example: the circuit breaker's counters | Example: the consumer's deliveries channel |

```go title="api-gateway/internal/breaker/breaker.go (excerpt)"
func (b *Breaker) Record(failed bool) {
	b.mu.Lock()
	defer b.mu.Unlock()
	...
}
```

## Goroutine leaks

A goroutine that blocks forever is never garbage collected. Common causes:

```go
// LEAK: if the caller returns early (timeout), nobody reads from ch,
// and the goroutine blocks forever on the send.
func fetch(ctx context.Context) (Result, error) {
	ch := make(chan Result)
	go func() { ch <- slowCall() }()
	select {
	case r := <-ch:
		return r, nil
	case <-ctx.Done():
		return Result{}, ctx.Err()
	}
}
```

Fix: make the channel buffered (`make(chan Result, 1)`) so the send never blocks, and pass `ctx` into `slowCall` so it stops too.

:::rule Every goroutine needs an owner and an exit
Before writing `go`, answer: who waits for it, and what makes it stop? In our services, the outbox relay stops when `workerCtx` is cancelled and `main` waits on a `WaitGroup` before exiting.
:::

## Production best practices

- Bound concurrency for anything that touches a dependency (worker pools, semaphores, `errgroup.SetLimit`).
- Run tests with `-race`; the race detector finds data races that are otherwise intermittent.
- Watch the `go_goroutines` metric — a steady climb means a leak.
- Prefer `sync/atomic` types (`atomic.Bool`, `atomic.Int64`) for simple flags and counters (like our readiness flag).

:::quiz concept="concurrency"
A handler spawns one goroutine per item to call another service, for a request containing 50,000 items. What is the main risk?
- [ ] Goroutines are expensive to create, so the request will be slow
- [x] Unbounded concurrency: 50,000 simultaneous calls exhaust connections and overload the dependency
- [ ] Go limits processes to 10,000 goroutines
- [ ] The goroutines will run sequentially anyway
> Goroutines are cheap; the dependency is not. Bound concurrency with a worker pool or `errgroup.SetLimit` so you apply controlled pressure downstream.
:::

@@lesson middleware

**Middleware** wraps a handler with behaviour that applies to many routes: request IDs, logging, authentication, panic recovery, rate limiting, CORS, compression. Written once, applied everywhere.

## What is it in Gin?

A Gin middleware is just a `gin.HandlerFunc`. It does something, calls `c.Next()` to run the rest of the chain, and can do more afterwards:

```go title="order-service/internal/middleware/middleware.go (simplified)"
func Logger(base *slog.Logger) gin.HandlerFunc {
	return func(c *gin.Context) {
		start := time.Now()
		l := base.With("request_id", reqctx.RequestID(c.Request.Context()))
		c.Request = c.Request.WithContext(reqctx.WithLogger(c.Request.Context(), l))

		c.Next() // ← everything after this runs once the handler has finished

		l.Log(c.Request.Context(), levelFor(c.Writer.Status()), "http request",
			"method", c.Request.Method,
			"route", c.FullPath(),
			"status", c.Writer.Status(),
			"duration_ms", time.Since(start).Milliseconds(),
		)
	}
}
```

`c.Abort()` (or `c.AbortWithStatusJSON`) stops the chain: later middleware and the handler do not run, but the "after" code of earlier middleware still does.

::diagram{id="middleware-chain"}

## Order matters

Middleware forms an onion. Our services install:

```go
r.Use(middleware.RequestID(), middleware.Logger(log), middleware.Recovery(log))
```

- **RequestID first**, so every later middleware and log line has the ID.
- **Logger before Recovery**, so a panic recovered by Recovery still produces an access log line with status 500 and the request ID.
- **Auth before handlers**, and in the gateway, **auth before rate limiting**, because the limiter keys on the authenticated user.

## The net/http form

Gin middleware is a convenience over the standard pattern, which you will see in many libraries:

```go
func RequestID(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		id := r.Header.Get("X-Request-ID")
		if id == "" {
			id = uuid.NewString()
		}
		w.Header().Set("X-Request-ID", id)
		next.ServeHTTP(w, r.WithContext(reqctx.WithRequestID(r.Context(), id)))
	})
}
```

## What belongs in middleware?

| Good fit | Poor fit |
|---|---|
| Request IDs, access logs, metrics, tracing | Business rules for one endpoint |
| Authentication, coarse authorisation (role checks) | Loading domain objects |
| Panic recovery, body size limits, timeouts | Anything that needs the parsed request body |
| CORS, compression, security headers | Transactions |

## What can go wrong?

- **Logging raw paths as labels.** `/v1/orders/8812` creates a unique value per order; use the route template `c.FullPath()` (`/v1/orders/:id`).
- **Reading the body in middleware** consumes it; the handler then sees an empty body.
- **Forgetting `return` after `c.Abort...`** — the rest of the middleware function still executes.
- **Trusting headers set by clients** (`X-User-ID`) in services that are reachable directly.

:::quiz concept="middleware"
An auth middleware calls `c.AbortWithStatusJSON(401, ...)`. Which statement is true?
- [ ] The handler still runs, but its response is discarded
- [x] The handler does not run, but code after `c.Next()` in earlier middleware (such as the logger) still runs
- [ ] No other middleware runs at all, including earlier ones
- [ ] The request is retried without authentication
> Abort prevents the remaining handlers in the chain from running. Middleware that already called `c.Next()` resumes after it — which is how the access log records the 401.
:::

@@lesson config-logging

Two cross-cutting concerns every service needs on day one: loading **configuration** safely and producing **logs** that can be searched and correlated across services.

## Configuration: the twelve-factor way

Store config in the **environment**, not in code or per-environment builds. One image runs in dev, staging and production; only environment variables differ.

```go title="order-service/internal/config/config.go (excerpt)"
func Load() (Config, error) {
	cfg := Config{
		HTTPAddr:       getEnv("HTTP_ADDR", ":8082"),
		DatabaseURL:    os.Getenv("DATABASE_URL"),
		RabbitURL:      os.Getenv("RABBITMQ_URL"),
		UserServiceURL: getEnv("USER_SERVICE_URL", "http://user-service:8081"),
	}
	var problems []error
	var err error
	cfg.UserTimeout, err = getDuration("USER_SERVICE_TIMEOUT", 800*time.Millisecond)
	collect(err)
	...
	if cfg.DatabaseURL == "" {
		problems = append(problems, errors.New("DATABASE_URL is required"))
	}
	return cfg, errors.Join(problems...) // report every problem at once
}
```

**Principles:**

- **Validate at startup and fail fast.** A typo in `USER_SERVICE_TIMEOUT` should crash the pod in its first second, not cause mysterious timeouts at 2 a.m.
- **Typed config.** Parse into `time.Duration`, `int`, `[]byte` once; the rest of the code never touches strings.
- **Sensible defaults** for tuning knobs; **no defaults** for secrets and connection strings.
- **Separate secrets from config.** In Kubernetes, ConfigMaps hold settings and Secrets (ideally sourced from Vault or a cloud secret manager) hold credentials.

:::rule Never log secrets
Do not log the config struct, connection strings, tokens or request bodies that may contain passwords. A log pipeline is a far bigger attack surface than a secret store.
:::

## Structured logging with `log/slog`

Plain-text logs are for humans reading one machine. Services need **structured** logs: JSON with consistent fields that a log system (Loki, Elasticsearch, CloudWatch) can index and query.

```go title="order-service/cmd/server/main.go (excerpt)"
func newLogger(level string) *slog.Logger {
	var lvl slog.Level
	if err := lvl.UnmarshalText([]byte(strings.ToUpper(level))); err != nil {
		lvl = slog.LevelInfo
	}
	return slog.New(slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{Level: lvl}))
}

log := newLogger(cfg.LogLevel).With("service", "order-service")
```

A log line then looks like:

```json
{"time":"2026-10-31T09:41:12.481Z","level":"INFO","msg":"order created","service":"order-service","request_id":"8f2c1e7a-…","order_id":8812,"total_cents":4200}
```

and you can query `service="order-service" AND request_id="8f2c1e7a-…"` across every service the request touched.

## Request-scoped loggers

The Logger middleware attaches a logger that already carries `request_id`; code deeper in the stack retrieves it:

```go
reqctx.Logger(ctx, s.log).InfoContext(ctx, "order created", "order_id", created.ID)
```

## Levels and what to log

| Level | Use for | Example |
|---|---|---|
| DEBUG | Detail useful while developing; off in production | Outbox batch sizes |
| INFO | Significant business or lifecycle events | Order created, service started |
| WARN | Unexpected but handled; might need attention | Cache unavailable, falling back to DB |
| ERROR | A request or job failed and someone may need to act | Unhandled error mapped to 500 |

## What can go wrong?

- **Logging in hot loops** costs CPU and money; log at boundaries.
- **High-cardinality message strings** (`"order 8812 created"`) are hard to aggregate — put variables in fields (`"order created", "order_id", 8812`).
- **Logging the same error at every layer.** Log once, where it is handled.
- **Writing to files inside containers.** Write to stdout; the platform collects it.

:::quiz concept="config-logging"
Which log line is easiest to search and aggregate in a log platform?
- [ ] `fmt.Printf("order %d for user %d created at %s\n", id, uid, t)`
- [x] `log.Info("order created", "order_id", id, "user_id", uid)` with a JSON handler
- [ ] `log.Printf("ORDER_CREATED|%d|%d", id, uid)`
- [ ] `log.Info(fmt.Sprintf("order %d created", id))`
> Structured fields with a constant message let you filter (`order_id=8812`) and count (`msg="order created"`) without regex parsing.
:::

@@lesson graceful-shutdown

Every deploy, autoscaling event and node drain stops pods. If a service simply exits on `SIGTERM`, in-flight requests fail and clients see errors during every release. **Graceful shutdown** makes stopping invisible to users.

## What happens when Kubernetes stops a pod?

1. The pod is marked *Terminating*. Two things start **in parallel**:
   - the endpoint controller removes the pod from Service endpoints (load balancers stop routing to it — this takes a few seconds to propagate);
   - the kubelet sends `SIGTERM` to the container.
2. The process has `terminationGracePeriodSeconds` (default 30) to exit.
3. After that, `SIGKILL` — no cleanup possible.

Because step 1 is parallel, a pod can receive *new* requests for a few seconds after `SIGTERM`. Exiting immediately drops them.

::diagram{id="graceful-shutdown"}

## The sequence in Go

```go title="user-service/cmd/server/main.go (excerpt)"
ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGINT, syscall.SIGTERM)
defer stop()
...
select {
case err := <-serveErr:
	return fmt.Errorf("http server: %w", err)
case <-ctx.Done(): // SIGTERM received
}

// 1. Fail readiness so the load balancer stops sending new requests.
ready.Store(false)
// 2. Keep serving while endpoint removal propagates.
time.Sleep(cfg.DrainDelay)

// 3. Stop accepting connections; wait for in-flight requests (bounded).
shutdownCtx, cancel := context.WithTimeout(context.Background(), cfg.ShutdownTimeout)
defer cancel()
if err := srv.Shutdown(shutdownCtx); err != nil {
	return fmt.Errorf("graceful shutdown: %w", err)
}
// 4. Deferred calls close Redis and the DB pool after the server stops.
```

`http.Server.Shutdown` closes listeners, closes idle connections, and waits for active requests to complete — or for the context to expire.

## Background workers

Order Service also runs the outbox relay. It must stop **after** HTTP has drained, so events written by the last requests still get published:

```go title="order-service/cmd/server/main.go (excerpt)"
workerCtx, stopWorkers := context.WithCancel(context.Background())
var workers sync.WaitGroup
workers.Add(1)
go func() {
	defer workers.Done()
	relay.Run(workerCtx)
}()
...
srv.Shutdown(shutdownCtx) // drain HTTP first
stopWorkers()             // then stop the relay
workers.Wait()            // and wait until it has exited
```

For message consumers, stop consuming new messages, let in-flight messages finish (and be acked), then close the connection. Unacked messages are redelivered to another replica — which is why consumers must be idempotent.

## Budget the timeouts

```text
terminationGracePeriodSeconds (30s)
  > DRAIN_DELAY (5s) + SHUTDOWN_TIMEOUT (20s) + time to close resources
```

If the sum exceeds the grace period, `SIGKILL` arrives mid-drain.

:::tip The probe endpoints
- `/healthz` (liveness): "is the process alive?" — always 200 unless it is wedged.
- `/readyz` (readiness): "should I get traffic?" — 503 while starting, while a critical dependency is down, and during shutdown.
:::

## What can go wrong?

- **PID 1 signal handling.** If the container runs a shell script that starts your binary, the shell may not forward `SIGTERM`. Use `ENTRYPOINT ["/app"]` (exec form), as our Dockerfiles do.
- **Long-lived connections** (WebSockets, streaming) are not waited for by `Shutdown`; close them explicitly.
- **Leaking goroutines** that keep the process alive or lose work. Every worker needs a stop signal.

:::quiz concept="graceful-shutdown"
Why does the service sleep for a few seconds after failing readiness and before calling `srv.Shutdown`?
- [ ] To let Go's garbage collector free memory
- [x] Because endpoint removal propagates asynchronously, so new requests may still arrive for a short time after SIGTERM
- [ ] To give the database time to restart
- [ ] Kubernetes requires a minimum sleep before exiting
> Removing the pod from load-balancer endpoints happens in parallel with SIGTERM. Serving for a few more seconds avoids rejecting requests that were already routed to the pod.
:::
