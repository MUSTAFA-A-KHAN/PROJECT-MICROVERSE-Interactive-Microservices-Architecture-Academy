@@lesson oms-overview

Every concept in this course is grounded in one system: an **Order Management System (OMS)** with two core services — User Service and Order Service — plus a gateway, a cache, a message broker and a notification consumer. Its full source is in the [Code Playground](#/playground) and it runs with `docker compose up`.

## The components

::diagram{id="oms"}

| Component | Technology | Responsibility | State |
|---|---|---|---|
| API Gateway | Go, Gin, `httputil.ReverseProxy` | TLS, request IDs, JWT verification, rate limiting, routing, timeouts, circuit breaking | Stateless |
| User Service | Go, Gin, pgx, bcrypt, JWT | Registration, login (issues JWTs), profiles | `users-db` |
| Order Service | Go, Gin, pgx, amqp091 | Order lifecycle, idempotent creation, outbox | `orders-db` |
| Notification Service | Go, amqp091 | Consumes order events, sends emails | Dedupe keys in Redis |
| PostgreSQL ×2 | Postgres 16 | Source of truth per service | Durable |
| Redis | Redis 7 | Rate-limit buckets, profile cache, dedupe keys | Rebuildable |
| RabbitMQ | RabbitMQ 3.13 | Durable delivery of order events | Durable queues |

## Why these pieces?

- **Two core services** keep the design realistic without overwhelming you: identity and orders are different capabilities, owned by different teams, changing at different rates.
- **The gateway** gives clients one stable entry point and centralises edge policy.
- **Redis** shows what a cache is for — and that losing it must not lose data.
- **RabbitMQ** decouples side effects (emails) from the request path.
- **Notification Service** demonstrates an event consumer with no public API.

## A request end to end

Press play on the diagram above, then compare it with the real code path in the playground's *Trace a request → POST /api/v1/orders*. In short:

1. The gateway authenticates the JWT locally and checks the rate limit in Redis.
2. Order Service validates the customer synchronously with User Service.
3. It writes the order, its items, an idempotency record and an outbox event in **one** Postgres transaction.
4. It responds `201 Created`.
5. Asynchronously, the outbox relay publishes `order.created`; Notification Service sends the email.

:::tip Try it in the lab
The [Architecture Lab](#/lab) runs this exact topology as a simulation. Fail User Service and watch Order Service's circuit breaker; fail RabbitMQ and watch the outbox hold events until it returns.
:::

## Design decisions (and their alternatives)

| Decision | Alternative | Why we chose this |
|---|---|---|
| JWT verified at the gateway | Call User Service on every request | No per-request dependency on User Service; tokens are short-lived |
| Synchronous user validation | Local replica of user status via events | Simple and strongly consistent; the lab shows its availability cost |
| Outbox + relay | Publish directly after commit | Avoids losing events on crashes or broker outages |
| RabbitMQ | Kafka | Per-message acks and DLQs fit task-like notifications; Kafka fits event streams with replay |
| Database per service | Shared database | Independent schema evolution and deployment |

:::quiz concept="service-design"
In the OMS, why does the confirmation email **not** happen inside the `POST /orders` request?
- [ ] Go cannot send emails synchronously
- [x] It is a side effect that does not affect whether the order is valid, so it is decoupled via an event — keeping the request fast and independent of email availability
- [ ] RabbitMQ requires all messages to be processed asynchronously
- [ ] Notification Service has no HTTP API
> Only work needed to *decide* belongs on the request path. Side effects become events, so a slow or failing email provider never slows down or breaks ordering.
:::

@@lesson user-service

User Service owns **identity**: who a user is, how they prove it, and their profile. It is the only component that ever sees a password.

## Responsibilities

- Register users with validated email and a strong password.
- Store password hashes (never passwords) with bcrypt.
- Authenticate credentials and issue short-lived JWT access tokens.
- Serve the current user's profile (with a Redis cache).
- Answer other services' questions through a minimal internal API.

**Not** its responsibility: orders, permissions on orders, emails. Keeping the scope tight keeps the service small and its data private.

## API contract

| Method | Path | Auth | Purpose | Success |
|---|---|---|---|---|
| POST | `/v1/users` | public | Register | 201 + user |
| POST | `/v1/auth/login` | public | Exchange credentials for a JWT | 200 + token |
| GET | `/v1/users/me` | JWT (via gateway) | Current profile | 200 |
| PATCH | `/v1/users/me` | JWT (via gateway) | Update display name | 200 |
| GET | `/internal/users/:id` | network-restricted | Service-to-service lookup | 200 `{id,email,status}` |

```http
POST /api/v1/auth/login HTTP/1.1
Content-Type: application/json

{"email": "ada@example.com", "password": "correct-horse-battery"}

HTTP/1.1 200 OK
Cache-Control: no-store
Content-Type: application/json

{"access_token": "eyJhbGciOiJIUzI1NiIs…", "token_type": "Bearer", "expires_in": 900}
```

## Data

```sql title="user-service/migrations/000001_create_users.up.sql"
CREATE TABLE users (
    id            BIGSERIAL    PRIMARY KEY,
    email         TEXT         NOT NULL,
    name          TEXT         NOT NULL,
    password_hash TEXT         NOT NULL,
    role          TEXT         NOT NULL DEFAULT 'customer' CHECK (role IN ('customer', 'admin')),
    status        TEXT         NOT NULL DEFAULT 'active'   CHECK (status IN ('active', 'suspended')),
    created_at    TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ  NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX users_email_key ON users (email);
```

The unique index — not application code — guarantees two concurrent registrations cannot claim one email.

## Authentication, carefully

```go title="user-service/internal/service/user_service.go (excerpt)"
func (s *UserService) Authenticate(ctx context.Context, email, password string) (string, time.Duration, error) {
	u, err := s.repo.GetByEmail(ctx, normaliseEmail(email))
	if errors.Is(err, model.ErrNotFound) {
		_ = bcrypt.CompareHashAndPassword(s.dummyHash, []byte(password))
		return "", 0, model.ErrInvalidCredentials
	}
	if err != nil {
		return "", 0, fmt.Errorf("authenticate: %w", err)
	}
	if err := bcrypt.CompareHashAndPassword([]byte(u.PasswordHash), []byte(password)); err != nil {
		return "", 0, model.ErrInvalidCredentials
	}
	if u.Status != model.StatusActive {
		return "", 0, model.ErrSuspended
	}
	return s.tokens.Issue(u)
}
```

Three security details worth noticing:

1. **Same error for unknown email and wrong password** — no account enumeration.
2. **Dummy hash comparison** for unknown emails — response time does not reveal whether an account exists.
3. **bcrypt cost 12** — deliberately slow (tens of milliseconds) so stolen hashes are expensive to brute-force.

:::rule Passwords
Never store, log or return plaintext passwords. Use a slow, salted password hash (bcrypt, scrypt or Argon2id). Rate-limit login endpoints — bcrypt's cost also makes login an easy CPU-exhaustion target.
:::

## The internal contract

Order Service needs to know if a customer is active. Instead of exposing the full `User`, User Service exposes a deliberately small shape:

```go title="user-service/internal/handler/user_handler.go (excerpt)"
type internalUser struct {
	ID     int64        `json:"id"`
	Email  string       `json:"email"`
	Status model.Status `json:"status"`
}
```

Fewer fields exposed means fewer reasons for a breaking change.

## What can go wrong?

| Failure | Effect | Mitigation |
|---|---|---|
| Service down | Login fails; Order Service cannot validate customers | ≥2 replicas, readiness probes, callers with breakers |
| `users-db` down | Login and uncached profiles fail | Failover; cached profiles still served |
| Redis down | Profiles read from Postgres (slower) | Cache is optional by design |
| Credential stuffing | CPU spikes from bcrypt | Rate limits per IP and per account, CAPTCHA after failures |

:::quiz concept="service-design"
Why does `Authenticate` compare the password against a dummy hash when the email does not exist?
- [ ] To warm the bcrypt cache
- [x] So the response takes the same time whether or not the account exists, preventing account enumeration by timing
- [ ] Because bcrypt panics on empty hashes
- [ ] To count failed login attempts
> Without it, unknown emails would return in microseconds while real ones take ~70 ms — leaking which emails are registered.
:::

@@lesson order-service

Order Service owns the **order lifecycle**. It is where the hard distributed-systems problems of this course show up: idempotency, atomic event publishing, state transitions under concurrency, and a synchronous dependency.

## Responsibilities

- Create orders exactly once per client intent (idempotency keys).
- Enforce the lifecycle: who can move an order from which state to which.
- Serve the owner's orders with efficient pagination.
- Publish `order.*` events reliably for other services.

## The lifecycle as a state machine

::diagram{id="order-lifecycle"}

Encoding the lifecycle as data makes it impossible to write an illegal transition by accident and easy to test:

```go title="order-service/internal/model/order.go (excerpt)"
var transitions = map[Status][]Status{
	StatusPending:   {StatusConfirmed, StatusCancelled},
	StatusConfirmed: {StatusShipped, StatusCancelled},
	StatusShipped:   {StatusDelivered},
}
```

## API contract

| Method | Path | Notes | Success |
|---|---|---|---|
| POST | `/v1/orders` | **Requires `Idempotency-Key`** | 201 + `Location` (`Idempotent-Replayed: true` on retries) |
| GET | `/v1/orders/:id` | Owner only (others get 404) | 200 |
| GET | `/v1/orders?limit=20&before=8812` | Keyset pagination | 200 `{orders, next_before}` |
| POST | `/v1/orders/:id/cancel` | Idempotent; 409 if not cancellable | 200 |
| PATCH | `/v1/orders/:id/status` | Admin only | 200 / 409 |

## Data: four tables, one transaction

```sql title="order-service/migrations/000001_create_orders.up.sql (excerpt)"
CREATE TABLE outbox (
    id            BIGSERIAL    PRIMARY KEY,
    event_id      UUID         NOT NULL UNIQUE,
    event_type    TEXT         NOT NULL,
    aggregate_id  BIGINT       NOT NULL,
    payload       JSONB        NOT NULL,
    created_at    TIMESTAMPTZ  NOT NULL DEFAULT now(),
    published_at  TIMESTAMPTZ
);

CREATE TABLE idempotency_keys (
    user_id       BIGINT       NOT NULL,
    key           TEXT         NOT NULL,
    request_hash  TEXT         NOT NULL,
    order_id      BIGINT       REFERENCES orders (id),
    PRIMARY KEY (user_id, key)
);
```

`CreateWithOutbox` writes the idempotency key, the order, its items and the `order.created` event together. If any statement fails, none of them exist.

## Creating an order, step by step

```go title="order-service/internal/service/order_service.go (excerpt)"
func (s *OrderService) CreateOrder(ctx context.Context, in CreateOrderInput) (*model.Order, bool, error) {
	if err := validate(in); err != nil {
		return nil, false, err
	}
	hash := requestHash(in)

	// Fast path: a client retry of a request we already completed.
	if existing, storedHash, err := s.repo.FindByIdempotencyKey(ctx, in.UserID, in.IdempotencyKey); err != nil {
		return nil, false, err
	} else if existing != nil {
		if storedHash != hash {
			return nil, false, model.ErrIdempotencyMismatch
		}
		return existing, true, nil
	}

	// We need User Service's answer to decide, so this call is synchronous.
	cust, err := s.users.GetUser(ctx, in.UserID)
	...
	created, replayed, err := s.repo.CreateWithOutbox(ctx, model.CreateOrderParams{
		Order: o, IdempotencyKey: in.IdempotencyKey, RequestHash: hash,
	})
	...
}
```

Note the order: the idempotency check happens **before** calling User Service, so a retried request never repeats work or side effects.

## Concurrency on updates

Two admins mark the same order shipped and cancelled at the same moment. Optimistic concurrency resolves it:

```sql
UPDATE orders SET status = $1, version = version + 1, updated_at = now()
WHERE id = $2 AND version = $3   -- only if nobody changed it since we read it
```

One update succeeds; the other affects zero rows and returns `409 Conflict`.

## What can go wrong?

- **Duplicate orders** from client retries → mandatory Idempotency-Key.
- **Lost events** when the process crashes between commit and publish → transactional outbox.
- **Lost updates** under concurrency → version column.
- **User Service outage** blocks ordering → circuit breaker, and optionally a fallback (accept as pending verification).
- **Deep pagination** with `OFFSET` gets slower and slower → keyset pagination on `(user_id, id DESC)`.

## Practice it in Go

::widget{name="exercise" id="order-state-machine"}

:::quiz concept="idempotency"
A client retries `POST /v1/orders` with the same Idempotency-Key but a **different** body. What should Order Service do?
- [ ] Create a second order, since the body differs
- [ ] Return the original order silently
- [x] Reject the request (422) because the key was reused for a different request
- [ ] Update the original order with the new body
> The key identifies one intent. Returning the old order would hide a client bug; creating a new one defeats idempotency. Comparing a request hash detects the misuse.

@@lesson api-contracts

An **API contract** is the promise a service makes to its consumers: paths, methods, request and response shapes, status codes, error formats, and the events it publishes. In microservices, contracts are what allow teams to change their services independently.

## What should a contract specify?

- Resources and operations (`POST /v1/orders`).
- Request and response schemas, including which fields are required.
- Status codes and when each is returned.
- A consistent **error format**.
- Headers with semantics (`Idempotency-Key`, `Retry-After`, `Location`).
- Pagination, filtering and limits.
- For events: name, schema, version, ordering and delivery guarantees.

## Describe it with OpenAPI

```yaml title="openapi.yaml (example contract for Order Service)"
paths:
  /v1/orders:
    post:
      summary: Create an order
      parameters:
        - in: header
          name: Idempotency-Key
          required: true
          schema: { type: string, maxLength: 128 }
      requestBody:
        required: true
        content:
          application/json:
            schema: { $ref: '#/components/schemas/CreateOrder' }
      responses:
        '201': { description: Created, content: { application/json: { schema: { $ref: '#/components/schemas/Order' } } } }
        '422': { description: Validation failed, content: { application/problem+json: { schema: { $ref: '#/components/schemas/Problem' } } } }
        '503': { description: Dependency unavailable; retry after Retry-After seconds }
```

An OpenAPI document can generate client SDKs, server stubs (e.g. `oapi-codegen` for Go), documentation and contract tests.

## A consistent error format: problem details

Every service returns RFC 9457 problem details:

```json
{
  "type": "about:blank",
  "title": "Invalid status transition",
  "status": 409,
  "detail": "invalid status transition: SHIPPED → CANCELLED",
  "instance": "/v1/orders/8812/cancel",
  "request_id": "8f2c1e7a-4b0d-4a51-9a63-31c0a3d5f6b2"
}
```

Clients write one error handler for the whole platform, and `request_id` lets support find the logs.

## Evolving without breaking consumers

| Change | Backward compatible? |
|---|---|
| Add an optional request field | Yes |
| Add a response field | Yes — *if* consumers ignore unknown fields (Go's `encoding/json` does) |
| Add a new endpoint or event type | Yes |
| Remove or rename a field | **No** |
| Change a field's type or meaning | **No** |
| Make an optional field required | **No** |
| Add a new enum value | Risky — consumers with exhaustive switches may break |

::diagram{id="api-versioning"}

**Tolerant reader**: consumers should read only the fields they need and ignore the rest. Our Notification Service decodes events into a struct with just the fields it uses, so Order Service can add fields freely.

**Versioning strategies**: URL path (`/v2/users`), header (`Accept: application/vnd.oms.v2+json`) or a field in events (`schema_version`). Path versioning is the most explicit and the easiest to route at the gateway.

## Consumer-driven contract tests

The consumer (Order Service) writes down what it expects from the provider (User Service): "`GET /internal/users/42` returns 200 with `id`, `status`". The provider's CI verifies every consumer's expectations before deploying. Tools: Pact, or a shared set of recorded examples.

This replaces slow, flaky end-to-end environments with fast checks that answer the only question that matters before deploy: *will this change break anyone?*

:::rule Never break a published contract silently
Breaking changes need a new version served alongside the old one, a deprecation period with `Deprecation`/`Sunset` headers, and metrics proving no traffic remains before removal.
:::

:::quiz concept="api-contracts"
User Service wants to rename the response field `name` to `display_name`. Order Service reads `name`. What is the safe approach?
- [ ] Rename it and ask the Order team to deploy at the same time
- [x] Add `display_name` alongside `name`, migrate consumers, then remove `name` once no one reads it (expand and contract)
- [ ] Rename it; JSON decoding will map it automatically
- [ ] Keep both forever
> Expand and contract keeps every intermediate state compatible. Coordinated simultaneous deploys are exactly what independent deployment is supposed to eliminate.
:::

@@lesson service-discovery

In a static world you could hard-code `10.0.3.17:8081`. In a containerised world, instances start, stop and move constantly — every deploy changes IP addresses. **Service discovery** is how a caller finds a healthy instance of a service by name.

## What is it?

Two pieces:

1. A **registry** that knows which instances of each service exist and whether they are healthy.
2. A **lookup** mechanism callers use to resolve a name to instances.

::diagram{id="service-discovery"}

## Client-side vs server-side discovery

| | Client-side | Server-side |
|---|---|---|
| Who picks the instance | The calling service (library) | A load balancer / proxy |
| Examples | Consul + client library, gRPC with DNS resolver, Eureka | Kubernetes Service (kube-proxy), AWS ALB, service mesh sidecar |
| Pros | Smart load balancing, no extra hop | Callers stay simple and language-agnostic |
| Cons | Discovery logic in every client language | Extra hop or kernel-level forwarding |

## In this course's environments

- **Docker Compose**: an embedded DNS server resolves service names (`user-service`) to container IPs on the shared network. That is why `USER_SERVICE_URL=http://user-service:8081` works.
- **Kubernetes**: a `Service` named `user-service` gets a stable virtual IP and DNS name (`user-service.default.svc.cluster.local`). Only **ready** pods are added to its endpoints, so traffic avoids instances failing readiness.

The same URL works in both environments — configuration does not change between laptop and cluster.

## Health is part of discovery

Discovery is only useful if it returns *healthy* instances. Registries rely on health checks:

- Kubernetes readiness probes (`/readyz`) add or remove pods from endpoints.
- Consul runs HTTP/TCP checks and deregisters failing instances.

## What can go wrong?

- **DNS caching.** Some clients cache DNS results indefinitely (the JVM historically did). Go's resolver respects TTLs, but connection pools keep using old connections — set `IdleConnTimeout` and let connections recycle.
- **gRPC and long-lived connections.** HTTP/2 multiplexes many calls over one connection, so a Kubernetes ClusterIP balances *connections*, not *requests*. One client can pin all its traffic to one pod. Use client-side load balancing (gRPC `round_robin` with a headless Service) or a mesh.
- **Registry outage.** If discovery is down, nobody can find anyone. Clients should cache last-known instances.

:::quiz concept="service-discovery"
A Go service makes gRPC calls to `user-service` through a Kubernetes ClusterIP Service. One pod receives almost all traffic. Why?
- [ ] Kubernetes Services always route to the oldest pod
- [x] gRPC multiplexes requests over a long-lived HTTP/2 connection, and ClusterIP balances connections, not individual requests
- [ ] gRPC does not support load balancing at all
- [ ] The readiness probe failed on the other pods
> kube-proxy picks a backend per TCP connection. With one long-lived connection, every request goes to the same pod. Client-side balancing (headless Service + round_robin) or a service mesh fixes it.
:::

@@lesson inter-service

The OMS uses both communication styles on purpose. The rule of thumb: **synchronous when you need the answer to decide; asynchronous when the work is a consequence.**

::diagram{id="oms-comm"}

## Order → User: synchronous

Order Service cannot accept an order without knowing the customer is active, so it asks:

```go title="order-service/internal/client/user_client.go (excerpt)"
// GetUser returns the customer or model.ErrCustomerNotFound. When the breaker
// is open it fails immediately with gobreaker.ErrOpenState.
func (c *UserClient) GetUser(ctx context.Context, id int64) (*model.Customer, error) {
	return c.cb.Execute(func() (*model.Customer, error) { return c.getWithRetry(ctx, id) })
}
```

The cost: Order Service's availability now depends on User Service's. Every protection in that client — per-attempt timeouts, retry with jitter, a circuit breaker — exists to limit that coupling.

**Alternatives** if this dependency becomes a problem:

- Put the account status **in the JWT** (already verified by the gateway) and accept up to 15 minutes of staleness.
- Keep a **local replica** of user status, updated from `user.status_changed` events.
- **Fallback**: accept the order as pending verification and check asynchronously (try it in the [lab](#/lab) with *Fallbacks* enabled).

## Order → Notification: asynchronous

Sending an email does not change whether the order is valid. Order Service records an event in its outbox and moves on. If Notification Service is down for an hour, orders keep working and emails go out when it recovers.

## Comparing the two in this system

| | Order → User (sync HTTP) | Order → Notification (async RabbitMQ) |
|---|---|---|
| Caller waits? | Yes, up to 800 ms per attempt | No |
| Coupling | Temporal: both must be up | None at request time |
| Failure effect | Order creation fails (or degrades) | Email is delayed |
| Consistency | Immediate | Eventual |
| Debugging | Simple: one request, one response | Needs correlation IDs across the broker |

:::rec Default to async for side effects
Ask of every synchronous call: "what happens to the user if this dependency is down?" If the honest answer is "they could have continued", make it an event.
:::

:::quiz concept="event-driven"
Order Service needs to (a) check a customer's credit limit before accepting an order and (b) update the loyalty-points balance after an order. Which is the best split?
- [ ] Both synchronous, for consistency
- [ ] Both asynchronous, for availability
- [x] (a) synchronous, because the decision depends on it; (b) asynchronous via an event
- [ ] (a) asynchronous; (b) synchronous
> The credit check determines whether the order is accepted, so its result is needed now. Loyalty points are a consequence of the order and can be applied eventually.
:::

@@lesson independent-deployment

The whole point of microservices is that teams can **ship independently**. That only works if each service has its own pipeline, its own data, and changes that stay compatible with the versions of other services running beside it.

::diagram{id="deploy-pipelines"}

## What makes a service independently deployable?

1. **Its own build and pipeline.** A change to `user-service/` builds, tests and deploys only User Service.
2. **Its own database and migrations.** No other service's schema is affected.
3. **Backward- and forward-compatible contracts.** During a rolling update, old and new versions run side by side — and so do old consumers of your API.
4. **No release coordination.** "Deploy A, then B" is a red flag.

## Compatibility windows

During a rollout, three things coexist: old instances of your service, new instances of your service, and consumers on whatever version they are running. Every change must work in all combinations.

## Database changes: expand and contract

Renaming `users.name` to `display_name` without downtime:

| Step | Deploy | Database | Code |
|---|---|---|---|
| 1. Expand | migration | `ADD COLUMN display_name` (nullable) | — |
| 2. Dual write | app v2 | — | writes both columns, reads `name` |
| 3. Backfill | job | `UPDATE … SET display_name = name` in batches | — |
| 4. Switch reads | app v3 | — | reads `display_name`, still writes both |
| 5. Contract | app v4 + migration | `DROP COLUMN name` | writes only `display_name` |

Each step is safe to roll back. The old version of the app keeps working at every point.

```sql
-- Step 1 is cheap and non-blocking in PostgreSQL 11+ (no table rewrite):
ALTER TABLE users ADD COLUMN display_name TEXT;
-- Step 3: batch it to avoid long locks and WAL spikes
UPDATE users SET display_name = name
WHERE id IN (SELECT id FROM users WHERE display_name IS NULL LIMIT 5000);
```

## Event schema changes

The same idea: add fields, never repurpose them; bump `schema_version` for incompatible changes and publish both versions (or to a new routing key) until consumers migrate.

## Release techniques

- **Rolling update** — replace pods gradually (Kubernetes default).
- **Blue/green** — run the new version beside the old one, switch traffic at once, keep the old one for instant rollback.
- **Canary** — send 1–5% of traffic to the new version, watch error rates and latency, then increase.
- **Feature flags** — deploy code dark and enable it separately from the deploy.

:::rule Every deploy must be reversible
If a migration cannot be rolled back with the previous app version still working, split it into smaller expand/contract steps.
:::

:::quiz concept="independent-deployment"
Order Service v2 removes a response field that the mobile app (v5, still installed on many phones) reads. Order Service deploys with a rolling update. What happens?
- [ ] Nothing — rolling updates are backward compatible by definition
- [x] Mobile clients break as soon as they hit a v2 pod; removing a field is a breaking change regardless of rollout strategy
- [ ] The gateway automatically re-adds missing fields
- [ ] Only new mobile installs are affected
> Rollout strategies manage *your* instances; they cannot fix an incompatible contract. Removals require versioning and a deprecation period.
:::
