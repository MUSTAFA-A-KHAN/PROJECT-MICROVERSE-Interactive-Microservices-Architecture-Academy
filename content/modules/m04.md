@@lesson gateway-intro

An **API Gateway** is the single entry point between clients and your services. It receives every external request, applies cross-cutting policies, and routes it to the right service.

## What is it?

::diagram{id="gateway"}

Without a gateway, every client must know every service's address, and every service must implement TLS, authentication, rate limiting, CORS and request logging on its own — slightly differently each time.

## Why do we need one?

| Concern | Without a gateway | With a gateway |
|---|---|---|
| Client knowledge of topology | Clients call `users.internal:8081`, `orders.internal:8082` | Clients call `api.example.com` only |
| Authentication | Every service parses JWTs | Verified once at the edge |
| Rate limiting | Per service, inconsistent | Central, per user, across all routes |
| Refactoring | Splitting a service breaks clients | Change a route; clients don't notice |
| Cross-cutting policies | Duplicated code in every service | One implementation |
| Security surface | Every service exposed | Only the gateway exposed |

## What it does — and what it should not do

**Good gateway responsibilities:** TLS termination, routing, authentication, coarse authorisation, rate limiting, request size limits, request IDs, access logs, timeouts, circuit breaking, CORS, response compression.

**Bad gateway responsibilities:** business rules, data transformation specific to one service, orchestration of multi-step workflows. Business logic in the gateway turns it into a shared monolith every team must change.

## Related things it is often confused with

| Component | Layer | Main job |
|---|---|---|
| Load balancer (L4/L7) | Network / HTTP | Spread traffic over identical instances |
| Reverse proxy (nginx, Envoy) | HTTP | Forward requests; the building block of a gateway |
| API Gateway | Application edge | Policies + routing for many services |
| Backend for Frontend (BFF) | Application edge | A gateway per client type (web, mobile) that can aggregate calls |
| Service mesh (Istio, Linkerd) | Service-to-service | mTLS, retries, metrics *between* services (east–west traffic) |

The gateway handles **north–south** traffic (clients → system); a service mesh handles **east–west** traffic (service → service). Many platforms use both.

## Build or buy?

This course builds a gateway in Go so you can see every mechanism. In production you will often use Kong, Envoy-based gateways, AWS API Gateway, NGINX or Traefik — configured rather than coded. The concepts are identical.

:::warn The gateway is on every request
It must be stateless, horizontally scaled, and boringly reliable. A gateway outage is a total outage, and every millisecond it adds is paid by every request.
:::

:::quiz concept="api-gateway"
Which responsibility does **not** belong in an API Gateway?
- [ ] Verifying JWT signatures
- [ ] Enforcing per-user rate limits
- [x] Calculating order discounts based on loyalty tier
- [ ] Routing `/api/v1/orders/*` to Order Service
> Discounts are business logic owned by a domain service. Putting them in the gateway couples every team to one shared component.
:::

@@lesson reverse-proxy-routing

At its core, a gateway is a **reverse proxy** with a **route table**: it accepts a request, decides which upstream should handle it, rewrites what needs rewriting, forwards it, and streams the response back.

## What is a reverse proxy?

A *forward* proxy acts on behalf of clients (a corporate web proxy). A *reverse* proxy acts on behalf of servers: clients think they are talking to the proxy, which talks to the real servers behind it.

## The route table

```go title="api-gateway/internal/config/config.go (excerpt)"
Routes: []proxy.RouteConfig{
	{Prefix: "/api/v1/auth", Upstream: userURL, StripPrefix: "/api", Public: true, Timeout: 3 * time.Second},
	{Prefix: "/api/v1/users", Upstream: userURL, StripPrefix: "/api", PublicCalls: []string{"POST /api/v1/users"}, Timeout: 2 * time.Second},
	{Prefix: "/api/v1/orders", Upstream: orderURL, StripPrefix: "/api", Timeout: 2 * time.Second},
},
```

Matching uses the **longest prefix**, so `/api/v1/users/me` matches `/api/v1/users` rather than a hypothetical `/api/v1`. Unknown paths return 404 *before* authentication runs, which keeps scanners away from the auth code and upstreams.

## httputil.ReverseProxy

Go's standard library includes a production-grade reverse proxy. Since Go 1.20 the recommended hook is `Rewrite`:

```go title="api-gateway/internal/proxy/proxy.go (excerpt)"
Rewrite: func(pr *httputil.ProxyRequest) {
	pr.Out.URL.Scheme = r.target.Scheme
	pr.Out.URL.Host = r.target.Host
	pr.Out.URL.Path = strings.TrimPrefix(pr.In.URL.Path, r.StripPrefix) // /api/v1/orders → /v1/orders
	pr.Out.Host = r.target.Host
	pr.SetXForwarded() // X-Forwarded-For, -Host, -Proto

	// Never trust identity headers from the internet: strip, then set from the verified token.
	pr.Out.Header.Del("X-User-ID")
	pr.Out.Header.Del("X-User-Role")
	if id, ok := identity.From(pr.In.Context()); ok {
		pr.Out.Header.Set("X-User-ID", id.UserID)
		pr.Out.Header.Set("X-User-Role", id.Role)
	}
	if rid := identity.RequestID(pr.In.Context()); rid != "" {
		pr.Out.Header.Set("X-Request-ID", rid)
	}
},
```

`ReverseProxy` also removes hop-by-hop headers (`Connection`, `Keep-Alive`, `Upgrade`…), streams bodies without buffering them, and supports HTTP/2 and WebSockets.

## Forwarded headers

| Header | Meaning |
|---|---|
| `X-Forwarded-For` | Original client IP (and every proxy in between) |
| `X-Forwarded-Proto` | `https` when TLS was terminated at the gateway |
| `X-Forwarded-Host` | The host the client requested |
| `Forwarded` | The standardised (RFC 7239) combined form |

Services that build absolute URLs or log client IPs read these — and must only trust them from known proxies (`SetTrustedProxies` in Gin).

## Connection pooling to upstreams

```go title="api-gateway/internal/proxy/proxy.go (excerpt)"
transport := &http.Transport{
	DialContext:         (&net.Dialer{Timeout: 2 * time.Second, KeepAlive: 30 * time.Second}).DialContext,
	MaxIdleConns:        200,
	MaxIdleConnsPerHost: 50,
	IdleConnTimeout:     90 * time.Second,
}
```

Go's default `MaxIdleConnsPerHost` is **2**. Under load, a gateway with the default opens and closes thousands of connections per second, exhausting ephemeral ports (`TIME_WAIT`) and adding a TCP (and TLS) handshake to most requests.

## What can go wrong?

- **Path-rewrite bugs** (`/api/v1/ordersXYZ` matching `/api/v1/orders`): match on prefix + `/` boundary, as `Resolve` does.
- **Header spoofing** when identity headers are not stripped.
- **Buffering large bodies** in memory — let `ReverseProxy` stream, and cap sizes with `http.MaxBytesReader`.
- **Retrying non-idempotent requests** at the proxy can duplicate side effects. Our gateway does not retry; services decide.

:::quiz concept="reverse-proxy"
Why does the gateway delete any incoming `X-User-ID` header before forwarding?
- [ ] HTTP/2 does not allow custom headers
- [x] Upstream services trust `X-User-ID`; a client could otherwise impersonate any user by sending it
- [ ] To reduce request size
- [ ] Because Gin rejects duplicate headers
> Services rely on the gateway as the only source of identity headers. Stripping client-supplied values first, then setting them from the verified JWT, prevents impersonation.
:::

@@lesson gateway-auth

**Authentication** answers "who are you?"; **authorisation** answers "are you allowed to do this?". In a microservices system they happen in different places, on purpose.

::diagram{id="jwt-flow"}

## JWTs in one paragraph

A JSON Web Token is three base64url segments: `header.payload.signature`. The payload holds **claims** — `sub` (subject, the user ID), `role`, `iss` (issuer), `aud` (audience), `exp` (expiry), `iat`, `jti` (unique token ID). The signature proves the token was issued by someone holding the key and has not been modified. Anyone can *read* a JWT; only key holders can *create* a valid one.

```json
{
  "role": "customer",
  "sub": "42",
  "iss": "user-service",
  "aud": ["oms-api"],
  "exp": 1793440512,
  "iat": 1793439612,
  "jti": "1f0e6c1e-0d0b-4e57-9a5c-8b4c9a3f2e11"
}
```

## Verifying at the edge

```go title="api-gateway/middleware/auth.go (excerpt)"
parser := jwt.NewParser(
	jwt.WithValidMethods([]string{jwt.SigningMethodHS256.Alg()}), // reject "alg":"none" and algorithm confusion
	jwt.WithIssuer(issuer),
	jwt.WithAudience(audience),
	jwt.WithExpirationRequired(),
	jwt.WithLeeway(30*time.Second), // tolerate small clock skew between machines
)
...
claims := &Claims{}
if _, err := parser.ParseWithClaims(raw, claims, keyFunc); err != nil {
	if errors.Is(err, jwt.ErrTokenExpired) {
		unauthorized(c, "invalid_token", "token expired")
		return
	}
	unauthorized(c, "invalid_token", "token invalid")
	return
}
```

Verification is a local HMAC (or RSA/EdDSA) check — microseconds, no network call. That is the whole point of JWTs: User Service is not consulted on every request, so it is not a single point of failure for the read path.

## Symmetric vs asymmetric signing

| | HS256 (shared secret) | RS256 / EdDSA (key pair) |
|---|---|---|
| Who can verify | Anyone with the secret | Anyone with the public key |
| Who can sign | **Anyone with the secret** | Only the private-key holder |
| Key distribution | Secret copied to every verifier | Public keys published via JWKS endpoint |
| Rotation | Coordinated | `kid` header + overlapping keys |

This course uses HS256 for simplicity. In production, prefer asymmetric keys: only User Service can mint tokens, and the gateway fetches public keys from `/.well-known/jwks.json`.

## Authorisation stays in the service

The gateway knows *who* the caller is. Only Order Service knows *which orders belong to them*:

```go title="order-service/internal/service/order_service.go (excerpt)"
func (s *OrderService) GetOrder(ctx context.Context, userID, orderID int64) (*model.Order, error) {
	o, err := s.repo.GetByID(ctx, orderID)
	if err != nil {
		return nil, err
	}
	if o.UserID != userID {
		return nil, model.ErrNotFound // don't reveal that the order exists
	}
	return o, nil
}
```

Coarse checks (role `admin` for `PATCH /status`) can run in middleware; fine-grained, data-dependent checks belong next to the data. This is **defence in depth**: even if the gateway were bypassed, Order Service still enforces ownership.

## Token lifetime and revocation

JWTs cannot be revoked before they expire without extra infrastructure. Mitigate with:

- **Short access tokens** (5–15 minutes) and longer-lived **refresh tokens** stored server-side (revocable).
- A **deny list** of `jti` values in Redis for emergencies (checked at the gateway).
- Rotating signing keys if a key leaks.

:::rule Token security
Pin accepted algorithms. Validate `exp`, `iss` and `aud`. Never put secrets or personal data you would not want leaked into claims — JWTs are signed, not encrypted. Send them only over TLS, and keep them out of URLs and logs.
:::

:::quiz concept="jwt-auth"
Why can the gateway authenticate requests without calling User Service?
- [ ] The gateway has a copy of the users table
- [x] The JWT's signature can be verified locally with the key, proving it was issued by User Service and not modified
- [ ] JWTs are encrypted, so only valid users can create them
- [ ] User Service pushes a list of valid tokens to the gateway
> Signature verification is a local cryptographic check. That keeps authentication fast and removes User Service from the per-request critical path.
:::

:::quiz concept="authorization"
The gateway verified user 42's token. User 42 requests `GET /api/v1/orders/9000`, which belongs to user 7. Where must this be rejected?
- [ ] At the gateway, by checking the order owner in Redis
- [x] In Order Service, which owns the order data and compares `order.user_id` with the caller
- [ ] Nowhere — a valid token grants access to all orders
- [ ] In User Service
> Authentication at the edge does not replace authorisation in the service that owns the data.
:::

@@lesson rate-limiting

**Rate limiting** caps how many requests a client can make in a period. It protects capacity from abuse and accidents, keeps one tenant from starving others, and turns overload into fast, explicit `429` responses instead of slow failures for everyone.

## Algorithms

| Algorithm | How it works | Bursts | Notes |
|---|---|---|---|
| Fixed window | Count per minute; reset at the boundary | 2× at window edges | Simplest; uneven |
| Sliding window log | Store each request timestamp | Exact | Memory per request |
| Sliding window counter | Weighted current + previous window | Smooth | Good approximation, cheap |
| **Token bucket** | Bucket refills at *r* tokens/s up to capacity *b*; each request takes one | Up to *b* | Most common; burst-friendly |
| Leaky bucket | Requests drain at a fixed rate; queue overflow rejected | None (smooths) | Shapes traffic |

Play with a token bucket: change capacity and refill rate, then fire bursts.

::widget{name="token-bucket"}

## Distributed rate limiting with Redis

With several gateway replicas, each must see the same bucket. Our gateway keeps buckets in Redis and updates them with a Lua script, which Redis executes atomically:

```go title="api-gateway/middleware/ratelimit.go (excerpt)"
var tokenBucketScript = redis.NewScript(`
local key      = KEYS[1]
local capacity = tonumber(ARGV[1])
local rate     = tonumber(ARGV[2])          -- tokens per second
local t        = redis.call('TIME')
local now      = t[1] * 1000 + math.floor(t[2] / 1000)

local bucket = redis.call('HMGET', key, 'tokens', 'ts')
local tokens = tonumber(bucket[1]) or capacity
local ts     = tonumber(bucket[2]) or now

tokens = math.min(capacity, tokens + (math.max(0, now - ts) / 1000) * rate)
local allowed = 0
if tokens >= 1 then
  tokens = tokens - 1
  allowed = 1
end
redis.call('HSET', key, 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', key, math.ceil(capacity / rate * 1000) + 1000)
return { allowed, math.floor(tokens) }
`)
```

Why a script and not `GET` then `SET`? Two replicas could both read "1 token left" and both allow the request. The script makes read-modify-write atomic. It uses Redis `TIME` so replicas with skewed clocks cannot disagree.

## The response

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 1
RateLimit-Limit: 20
RateLimit-Remaining: 0
Content-Type: application/problem+json

{"type":"about:blank","title":"Too Many Requests","status":429}
```

Well-behaved clients back off for `Retry-After` seconds.

## What to key on

- **Authenticated user** (`ratelimit:user:42`) — fair per customer.
- **IP address** for anonymous routes like login — beware NAT (many users behind one IP) and spoofed `X-Forwarded-For`.
- **API key / tenant** for B2B APIs with plans.
- **Route-specific limits** for expensive endpoints (login, search, exports).

## When Redis is down

:::rec Fail open or fail closed?
- **Fail open** (our gateway): allow requests, log a warning. Availability wins; abuse protection is temporarily lost.
- **Fail closed**: reject requests. Safe against abuse; the API is down while Redis is.
- **Hybrid**: fall back to an in-memory limiter per replica — approximate (N replicas ≈ N× the limit) but still bounded.

Choose deliberately per route: a login endpoint might fail closed, a product catalogue fail open.
:::

## Request validation at the edge

Cheap checks belong at the gateway too: maximum body size (`http.MaxBytesReader`), allowed methods, content type, header size limits. They stop malformed or oversized requests before they consume upstream resources. Detailed schema validation (required fields, ranges) stays in the service that owns the contract.

:::quiz concept="rate-limiting"
Two gateway replicas each run `GET bucket` and `SET bucket - 1` as separate Redis commands. What can go wrong?
- [ ] Redis rejects concurrent GETs
- [x] A race: both read the same token count and both allow the request, exceeding the limit
- [ ] Nothing, Redis is single-threaded so separate commands are atomic together
- [ ] The bucket never refills
> Each command is atomic, but the read-modify-write sequence across two commands is not. A Lua script (or MULTI with WATCH) makes the whole update atomic.
:::

@@lesson gateway-resilience

The gateway sits in front of everything, so it must stay healthy even when the services behind it are not. Three mechanisms make that possible: **load balancing**, **circuit breaking** and **timeouts** — plus centralised logging so you can see what is happening.

## Load balancing at the gateway

Each upstream usually has several instances. Load balancing decides which one gets a request.

::diagram{id="p-load-balancing"}

In Kubernetes the gateway typically calls a Service name and kube-proxy balances connections; a mesh or client-side balancer can balance per request with smarter algorithms (least requests, latency-aware, consistent hashing for cache affinity). [Load Balancing](#/lesson/m07/pattern-load-balancing) covers the algorithms in depth.

## Circuit breaking per upstream

If Order Service is failing, every request to it waits for a timeout and occupies a gateway goroutine and connection. With enough traffic, the gateway itself runs out of resources and starts failing for `/users` too — a **cascading failure**.

A breaker per upstream contains the damage:

```go title="api-gateway/internal/proxy/proxy.go (simplified)"
func (p *Proxy) Forward(c *gin.Context) {
	route := c.MustGet(ctxRoute).(*Route)

	if err := route.breaker.Allow(); err != nil {
		retry := int(route.breaker.RetryAfter().Seconds()) + 1
		c.Header("Retry-After", strconv.Itoa(retry))
		writeProblem(c.Writer, http.StatusServiceUnavailable, "Service Unavailable",
			"circuit open for "+route.target.Host+"; failing fast", identity.RequestID(c.Request.Context()))
		c.Abort()
		return
	}

	ctx, cancel := context.WithTimeout(c.Request.Context(), route.Timeout)
	defer cancel()
	route.proxy.ServeHTTP(c.Writer, c.Request.WithContext(ctx))

	route.breaker.Record(c.Writer.Status() >= 500)
}
```

The gateway's breaker is hand-written in [breaker.go](#/playground?file=api-gateway/internal/breaker/breaker.go) so you can read every state transition; Order Service uses the `sony/gobreaker` library for the same job.

## Timeouts at the edge

Every route has a timeout shorter than the server's write timeout. When it fires, `ReverseProxy` closes the upstream connection — which cancels the upstream handler's request context — and the gateway returns `504`. Without it, a hung service would hold gateway resources indefinitely.

## Centralised access logging

Because every request passes through the gateway, its access log is the best single view of the system's external behaviour:

```json
{"level":"INFO","msg":"access","service":"api-gateway","request_id":"8f2c1e7a-…","method":"POST","path":"/api/v1/orders","status":201,"duration_ms":41,"client_ip":"203.0.113.9","user_id":"42"}
```

From these lines alone you can build request rate, error rate and latency dashboards per route, and find every log in every service for one request via `request_id`.

## What can go wrong?

- A breaker shared across *all* upstreams — one bad service blocks everyone. Keep one per upstream (per route or per host).
- Retries at the gateway *and* in services — multiplicative retry storms. Retry at one layer.
- Logging full request bodies at the gateway — personal data and secrets in logs.

:::quiz concept="circuit-breaker"
Order Service hangs. Without circuit breakers or timeouts at the gateway, what is the most likely outcome under heavy traffic?
- [ ] Only order requests fail; user requests are unaffected
- [x] Gateway goroutines and connections pile up waiting on Order Service until the gateway itself fails for all routes
- [ ] The gateway automatically routes order requests to User Service
- [ ] Clients receive 429 responses
> Unbounded waiting turns one slow dependency into resource exhaustion in the caller — a cascading failure. Timeouts bound the wait; breakers stop calling a dependency that keeps failing.
:::

## Experiments to run

1. **No token** on `GET /api/v1/orders/8812` → rejected at *JWT verification* with `401` and a `WWW-Authenticate` header.
2. **Expired token** → also `401`, with `error_description="token expired"` so the client knows to refresh.
3. **Customer token** on `PATCH /api/v1/orders/8812/status` → passes the gateway (authenticated) but Order Service's role check returns `403`. Authentication at the edge, authorisation in the service.
4. **Unknown route** `/api/v1/payments` → `404` at route matching, before any auth work is done.
5. **Burst** 25 requests → the token bucket empties and you get `429` with `Retry-After`.
6. **Order Service down** → `502`, and after repeated failures the circuit opens and requests fail fast with `503`.
7. **Login** with no token → passes, because `/api/v1/auth/*` is a public route.

## Reading the response inspector

For every request the simulator shows the headers the gateway **adds** upstream (`X-Request-ID`, `X-User-ID`, `X-Forwarded-For`) and **removes** (`Authorization`, client-supplied `X-User-ID`), plus the response headers clients rely on (`RateLimit-Remaining`, `Retry-After`, `WWW-Authenticate`).
