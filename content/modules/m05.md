@@lesson sync-vs-async

Services talk in two fundamentally different ways. Choosing between them for each interaction is one of the most consequential design decisions you make.

## Synchronous: request/response

The caller sends a request and **waits** for the response: HTTP/REST, gRPC.

- Simple mental model; immediate answer; easy to debug.
- **Temporal coupling**: both sides must be up at the same moment.
- The caller's latency includes the callee's latency (and its callees').

## Asynchronous: messages and events

The sender publishes a message to a broker and **continues**. Receivers process it when they can: RabbitMQ, Kafka, SQS, NATS.

- The sender does not need the receiver to be up; the broker buffers.
- Natural load levelling: spikes queue up instead of overwhelming consumers.
- Eventual consistency; harder to trace; you need idempotent consumers and dead-letter handling.

## The availability arithmetic

::diagram{id="sync-chain"}

If a request synchronously touches *n* services, each 99.9% available, the request succeeds only when all are up:

| Services in chain | Availability | Downtime per year |
|---|---|---|
| 1 | 99.9% | 8.8 hours |
| 2 | 99.8% | 17.5 hours |
| 4 | 99.6% | 35 hours |
| 8 | 99.2% | 70 hours |

And latency compounds the same way: the slowest dependency sets the pace, and tail latencies add up. With fan-out to 10 services each having a 1% chance of a slow response, about 10% of requests are slow.

## Choosing

| Use synchronous when | Use asynchronous when |
|---|---|
| The caller needs the answer to proceed (validate, price, authorise) | The work is a consequence (send email, update analytics, award points) |
| The user is waiting for a result that depends on it | The work can happen seconds later without harm |
| The operation is a query | Many consumers care about the same fact |
| Strong consistency is required now | Load spikes must be absorbed |

:::rec Hybrid is normal
Most systems use synchronous calls for queries and decisions on the request path, and events for everything that follows. The OMS does exactly that: Order → User is synchronous, Order → Notification is asynchronous.
:::

## What can go wrong?

- **Sync chains** that grow over time until availability and latency degrade.
- **Async everywhere**, including for queries ("request/reply over a queue"), adding complexity without decoupling.
- **Hidden synchronous coupling**: a consumer that calls back into the producer for data on every event. Put the data the consumer needs in the event (event-carried state transfer).

:::quiz concept="sync-communication"
A checkout request synchronously calls 5 services, each 99.9% available. Roughly what is the availability of checkout from these dependencies alone?
- [ ] 99.9%
- [x] About 99.5%
- [ ] 95%
- [ ] 99.99%
> 0.999⁵ ≈ 0.995. Every synchronous dependency multiplies the failure probability — about 44 hours of downtime a year instead of 9.
:::

@@lesson rest-http

REST over HTTP with JSON is the default for synchronous service-to-service calls: universal, debuggable with `curl`, and supported by every language. Doing it *well* in Go comes down to configuring the client carefully.

## The zero-value trap

```go
resp, err := http.Get("http://user-service:8081/internal/users/42") // DON'T
```

`http.Get` uses `http.DefaultClient`, which has **no timeout at all**. If User Service accepts the connection and never responds, this goroutine waits forever. Under load, those goroutines and their sockets accumulate until the caller falls over.

## A production client

```go title="order-service/internal/client/user_client.go (excerpt)"
transport := &http.Transport{
	DialContext:           (&net.Dialer{Timeout: 500 * time.Millisecond, KeepAlive: 30 * time.Second}).DialContext,
	MaxIdleConns:          100,
	MaxIdleConnsPerHost:   20, // default is 2 — far too low for service-to-service traffic
	IdleConnTimeout:       90 * time.Second,
	TLSHandshakeTimeout:   2 * time.Second,
	ResponseHeaderTimeout: cfg.AttemptTimeout,
}
c := &UserClient{
	// No Client.Timeout: each attempt gets its own context deadline instead,
	// so retries and the caller's deadline compose correctly.
	http: &http.Client{Transport: transport},
}
```

Timeouts exist at several layers:

| Timeout | Bounds | Set via |
|---|---|---|
| Dial | TCP connect | `net.Dialer.Timeout` |
| TLS handshake | TLS negotiation | `Transport.TLSHandshakeTimeout` |
| Response header | Time until the first response byte | `Transport.ResponseHeaderTimeout` |
| Whole request | Everything including body read | `Client.Timeout` **or** context deadline |

## Each attempt, carefully

```go title="order-service/internal/client/user_client.go (excerpt)"
func (c *UserClient) getOnce(ctx context.Context, id int64) (*model.Customer, error) {
	ctx, cancel := context.WithTimeout(ctx, c.cfg.AttemptTimeout)
	defer cancel()

	req, err := http.NewRequestWithContext(ctx, http.MethodGet, c.cfg.BaseURL+"/internal/users/"+strconv.FormatInt(id, 10), nil)
	if err != nil {
		return nil, err
	}
	req.Header.Set("Accept", "application/json")
	if rid := reqctx.RequestID(ctx); rid != "" {
		req.Header.Set("X-Request-ID", rid) // correlation across services
	}

	resp, err := c.http.Do(req)
	if err != nil {
		return nil, err
	}
	defer resp.Body.Close()
	// Drain so the connection can be reused by the pool.
	defer func() { _, _ = io.Copy(io.Discard, io.LimitReader(resp.Body, 64<<10)) }()

	switch {
	case resp.StatusCode == http.StatusOK:
		var cust model.Customer
		if err := json.NewDecoder(io.LimitReader(resp.Body, 1<<20)).Decode(&cust); err != nil {
			return nil, fmt.Errorf("decode user: %w", err)
		}
		return &cust, nil
	case resp.StatusCode == http.StatusNotFound:
		return nil, model.ErrCustomerNotFound
	default:
		return nil, &statusError{code: resp.StatusCode}
	}
}
```

Details that matter:

- **Always close the body** — otherwise the connection leaks.
- **Drain the body** before closing so the connection returns to the pool for reuse.
- **Limit reads** (`io.LimitReader`) so a misbehaving service cannot exhaust your memory.
- **Propagate the request ID** for cross-service log correlation.
- **Translate status codes** into domain errors at the boundary.

## REST design conventions

- Nouns for resources (`/orders/8812`), HTTP methods for verbs.
- Safe and idempotent methods: `GET`, `HEAD` are safe; `PUT`, `DELETE` are idempotent; `POST` and `PATCH` are not (unless you add idempotency keys).
- Use status codes precisely (see [Error handling](#/lesson/m02/errors)).
- Paginate lists; never return unbounded collections.

:::quiz concept="timeouts"
A service uses `http.Get(url)` to call a dependency that sometimes accepts connections but never responds. What happens over time?
- [ ] Go's default client times out after 30 seconds
- [x] Calls hang indefinitely, goroutines and sockets accumulate, and the caller eventually exhausts resources
- [ ] The kernel closes the connection after 1 second
- [ ] The call returns an empty response
> `http.DefaultClient` has no timeout. Always use a configured client and a context deadline on every outbound call.
:::

@@lesson grpc

**gRPC** is a high-performance RPC framework: you define services and messages in Protocol Buffers, generate typed clients and servers, and talk over HTTP/2 with binary encoding.

## What is it?

::diagram{id="grpc"}

```proto title="proto/user/v1/user.proto"
syntax = "proto3";

package user.v1;
option go_package = "github.com/microverse/order-management/gen/user/v1;userv1";

service UserService {
  rpc GetUser(GetUserRequest) returns (GetUserResponse);
  rpc WatchUserStatus(WatchUserStatusRequest) returns (stream UserStatusEvent);
}

message GetUserRequest {
  int64 id = 1;
}

message GetUserResponse {
  int64 id = 1;
  string email = 2;
  Status status = 3;
}

enum Status {
  STATUS_UNSPECIFIED = 0;
  STATUS_ACTIVE = 1;
  STATUS_SUSPENDED = 2;
}
```

Field **numbers**, not names, go over the wire. That is what makes protobuf evolution safe: add new fields with new numbers; never reuse or renumber old ones (mark removed ones `reserved`).

## Why use it?

| | REST + JSON | gRPC + Protobuf |
|---|---|---|
| Contract | OpenAPI (optional, often drifts) | `.proto` (required, generates code) |
| Encoding | Text JSON | Binary, typically 3–10× smaller |
| Transport | HTTP/1.1 or 2 | HTTP/2 (multiplexed) |
| Streaming | Awkward (SSE, WebSockets) | Built in (server, client, bidirectional) |
| Deadlines | Convention | Propagated automatically (`grpc-timeout`) |
| Browser support | Native | Needs gRPC-Web or a gateway |
| Debugging | `curl` | `grpcurl`, reflection |

gRPC shines for internal, high-volume, polyglot service-to-service calls. REST remains better for public APIs and browser clients.

## Server and client in Go

```go title="user-service/internal/grpcserver/server.go"
type Server struct {
	userv1.UnimplementedUserServiceServer // forward compatibility for new RPCs
	svc *service.UserService
}

func (s *Server) GetUser(ctx context.Context, req *userv1.GetUserRequest) (*userv1.GetUserResponse, error) {
	u, err := s.svc.GetProfile(ctx, req.GetId())
	switch {
	case errors.Is(err, model.ErrNotFound):
		return nil, status.Error(codes.NotFound, "user not found")
	case err != nil:
		return nil, status.Error(codes.Internal, "internal error")
	}
	return &userv1.GetUserResponse{Id: u.ID, Email: u.Email, Status: toProtoStatus(u.Status)}, nil
}
```

```go title="order-service/internal/client/user_grpc.go"
conn, err := grpc.NewClient("dns:///user-service:9090",
	grpc.WithTransportCredentials(insecure.NewCredentials()), // use mTLS in production
	grpc.WithDefaultServiceConfig(`{"loadBalancingConfig":[{"round_robin":{}}]}`),
)
client := userv1.NewUserServiceClient(conn)

ctx, cancel := context.WithTimeout(ctx, 800*time.Millisecond)
defer cancel()
resp, err := client.GetUser(ctx, &userv1.GetUserRequest{Id: 42})
if status.Code(err) == codes.DeadlineExceeded {
	// the server's context was cancelled too
}
```

:::note These two files are illustrative
The reference OMS uses REST between services so you can inspect calls with `curl`. The snippets above show how the same call looks with gRPC; they are not part of the compiled codebase.
:::

## Status codes

gRPC has its own codes. Map them deliberately: `NotFound`, `InvalidArgument`, `AlreadyExists`, `FailedPrecondition` (like HTTP 409), `Unavailable` (retryable), `DeadlineExceeded`, `ResourceExhausted` (like 429), `Internal`.

## What can go wrong?

- **Load balancing** with long-lived HTTP/2 connections: a ClusterIP Service balances connections, not calls. Use client-side `round_robin` with a headless Service, or a mesh.
- **Breaking changes** by renumbering fields or changing types. Use `buf breaking` in CI to catch them.
- **Missing deadlines**: a gRPC call without a context deadline can wait forever, just like HTTP.
- **Large messages**: default max receive size is 4 MB; stream or paginate instead of raising it blindly.

:::quiz concept="grpc"
Which protobuf change is **backward compatible**?
- [ ] Changing field `email = 2` to `email = 4`
- [ ] Changing `int64 id = 1` to `string id = 1`
- [x] Adding `string display_name = 4;` to the response message
- [ ] Reusing the number of a deleted field for a new field
> New fields with new numbers are ignored by old clients and defaulted for old servers. Renumbering, retyping or reusing numbers corrupts data between versions.
:::

@@lesson timeouts-retries

Timeouts and retries are the two most important resilience tools — and, misconfigured, two of the most common causes of outages. Get them right together.

## Timeouts: bound every wait

A timeout converts "maybe forever" into a bounded, observable failure. Without one, a slow dependency consumes your goroutines, connections and memory until you fail too.

**Budget timeouts top-down.** The edge sets the total budget; each layer must fit inside what is left:

```text
Client gives up at 10 s
└── Gateway route timeout: 2 s
    └── Order Service → User Service: 800 ms per attempt, max 3 attempts
        └── User Service → Postgres: statement timeout 500 ms
```

Go's context makes this automatic: `context.WithTimeout(ctx, 800*time.Millisecond)` yields the *earlier* of the parent's deadline and 800 ms from now.

## Retries: recover from transient failures

Many failures are transient: a pod being replaced during a rolling deploy, a dropped connection, a brief overload. One more attempt often succeeds.

**But retries multiply load.** If 1,000 clients each retry 3 times against a struggling service, it receives up to 4,000 requests exactly when it can handle fewest. Layered retries make it worse: 3 retries at the gateway × 3 in Order Service × 3 in User Service = 27 attempts per original request.

## Exponential backoff with jitter

Wait longer after each failure, and randomise the wait so clients don't retry in synchronised waves:

```go title="order-service/internal/client/user_client.go (excerpt)"
// backoff returns a random duration in [0, base·2^(attempt-1)] ("full jitter"),
// which spreads retries out so clients do not retry in synchronised waves.
func backoff(base time.Duration, attempt int) time.Duration {
	ceiling := base << (attempt - 1)
	return time.Duration(rand.Int64N(int64(ceiling) + 1))
}
```

Compare strategies below. Watch the request rate the dependency receives when 50 clients retry at once.

::widget{name="retry-backoff"}

## What to retry

```go title="order-service/internal/client/user_client.go (excerpt)"
func retryable(err error) bool {
	if errors.Is(err, context.Canceled) {
		return false // the caller gave up
	}
	var se *statusError
	if errors.As(err, &se) {
		return se.code == http.StatusTooManyRequests || se.code >= 500
	}
	return true // timeouts and network errors are usually transient
}
```

| Retry | Don't retry |
|---|---|
| Connection refused / reset, timeouts | 400, 401, 403, 404, 409, 422 — they will fail again |
| 503, 502, 504 | Non-idempotent requests without an idempotency key |
| 429 (after `Retry-After`) | When the caller's context is already cancelled |

## Retry budgets

A **retry budget** caps retries to a fraction of normal traffic (for example, at most 10% extra). When the budget is exhausted, failures are returned immediately. This prevents retries from amplifying an outage. Pair retries with a [circuit breaker](#/lesson/m07/pattern-circuit-breaker), which stops retries entirely when a dependency is clearly down.

:::rule Only retry idempotent operations
A retried `POST /charges` without an idempotency key can charge a customer twice. Make operations idempotent first, then make them retryable.
:::

:::quiz concept="retries"
Why add random jitter to exponential backoff?
- [ ] To make retries faster on average
- [x] To prevent many clients from retrying at exactly the same moments, which would create synchronised load spikes
- [ ] Because Go's timers are imprecise
- [ ] To guarantee the request succeeds eventually
> Without jitter, every client that failed at the same time retries at the same time — repeatedly hammering the dependency in waves. Randomising spreads the load.
:::

:::quiz concept="timeouts"
The gateway's route timeout is 2 s. Order Service calls User Service with an 800 ms per-attempt timeout and up to 3 attempts plus backoff. What is the problem?
- [ ] 800 ms is too short for an HTTP call
- [x] The worst case (≈2.4 s + backoff) exceeds the gateway's 2 s budget, so later attempts are wasted work cancelled by the outer deadline
- [ ] Retries are never allowed for GET requests
- [ ] The gateway should have a longer timeout than the client
> Inner timeout × attempts must fit inside the caller's deadline. Otherwise the gateway returns 504 while Order Service is still retrying.
:::

@@lesson messaging

A **message broker** decouples producers from consumers in time. RabbitMQ is the classic choice for task-style messaging: routing, per-message acknowledgements, retries and dead-letter queues.

## Core concepts

::diagram{id="rabbitmq"}

| Concept | Meaning |
|---|---|
| **Producer** | Publishes messages to an exchange (never directly to a queue) |
| **Exchange** | Routes messages to queues by rules: `direct` (exact key), `topic` (patterns like `order.*`), `fanout` (all bound queues), `headers` |
| **Binding** | A rule connecting an exchange to a queue (`order.*` → `q.notifications`) |
| **Queue** | Stores messages until consumed |
| **Consumer** | Receives messages and **acknowledges** them after processing |
| **Prefetch (QoS)** | Max unacknowledged messages per consumer — back-pressure and fair dispatch |
| **DLX / DLQ** | Dead-letter exchange/queue for rejected or expired messages |

## Delivery guarantees in practice

RabbitMQ gives you **at-least-once** delivery when you:

1. Publish **persistent** messages to **durable** queues (quorum queues for replication).
2. Use **publisher confirms**: the broker acknowledges that it has stored the message.
3. Use **manual consumer acks**: acknowledge only after the work is done.

If a consumer crashes before acking, the message is redelivered to another consumer — so the same message can be processed twice. Consumers must be **idempotent**.

## Publishing with confirms

```go title="order-service/internal/events/rabbitmq.go (excerpt)"
conf, err := ch.PublishWithDeferredConfirmWithContext(ctx, p.exchange, e.Type,
	true,  // mandatory: return the message if no queue is bound
	false, // immediate (unsupported by RabbitMQ)
	amqp.Publishing{
		ContentType:  "application/json",
		DeliveryMode: amqp.Persistent,
		MessageId:    e.ID.String(),
		Type:         e.Type,
		Timestamp:    e.OccurredAt,
		Body:         e.Payload,
	})
...
ok, err := conf.WaitContext(ctx)
if !ok {
	return errors.New("broker nacked event " + e.ID.String())
}
```

## Consuming safely

```go title="notification-service/internal/consumer/consumer.go (excerpt)"
func (c *Consumer) handle(ctx context.Context, d amqp.Delivery) {
	var evt OrderEvent
	if err := json.Unmarshal(d.Body, &evt); err != nil || evt.EventID == "" {
		_ = d.Reject(false) // poison: never retry → dead-letter queue
		return
	}
	seen, err := c.dedupe.Seen(ctx, evt.EventID)
	...
	if seen {
		_ = d.Ack(false) // duplicate delivery: acknowledge and skip
		return
	}
	if err := c.sender.Send(ctx, evt.UserID, subject, body); err != nil {
		if d.Redelivered {
			_ = d.Reject(false) // failed twice → DLQ
			return
		}
		_ = d.Nack(false, true) // requeue once
		return
	}
	_ = c.dedupe.MarkSeen(ctx, evt.EventID)
	_ = d.Ack(false)
}
```

## Topology declaration

The consumer declares the queue it owns, with a dead-letter exchange:

```go title="notification-service/cmd/worker/main.go (excerpt)"
args := amqp.Table{"x-dead-letter-exchange": dlx, "x-queue-type": "quorum"}
if _, err := ch.QueueDeclare(queue, true, false, false, false, args); err != nil {
	return fmt.Errorf("declare queue: %w", err)
}
return ch.QueueBind(queue, "order.*", exchange, false, nil)
```

Order Service only knows the exchange. Adding an Analytics consumer means binding a new queue — no change to the producer.

## What can go wrong?

- **Auto-ack**: messages are lost if the consumer crashes mid-processing.
- **Requeue loops**: a poison message nacked with requeue=true is redelivered forever. Use a DLQ and a retry limit.
- **Unbounded prefetch**: one consumer grabs thousands of messages and others sit idle; memory grows.
- **Queue growth** when consumers are down: alert on queue depth and message age, not just on consumer errors.
- **Ordering assumptions**: with several consumers, messages are processed concurrently; design for out-of-order handling.

:::quiz concept="messaging"
A consumer uses auto-ack and crashes while sending an email. What happens to that message?
- [ ] It is redelivered to another consumer
- [x] It is lost: auto-ack told the broker it was handled when it was delivered
- [ ] It moves to the dead-letter queue
- [ ] RabbitMQ pauses the queue until the consumer returns
> With auto-ack the broker deletes the message on delivery. Manual acks after successful processing are required for at-least-once semantics.
:::

@@lesson kafka

**Apache Kafka** is a distributed, partitioned, replicated **log**. Where RabbitMQ is a smart broker that routes and deletes messages once consumed, Kafka is a durable record of events that consumers read at their own pace — and can re-read.

## Core concepts

::diagram{id="kafka"}

| Concept | Meaning |
|---|---|
| **Topic** | A named stream of records (`orders`) |
| **Partition** | An ordered, append-only shard of a topic. Order is guaranteed **within** a partition only |
| **Key** | Determines the partition (`hash(key) % partitions`). Same key → same partition → ordered |
| **Offset** | A record's position in its partition; consumers track how far they have read |
| **Consumer group** | Consumers sharing work; each partition is assigned to exactly one consumer in the group |
| **Retention** | Records are kept for a time or size limit (or forever with compaction), regardless of consumption |
| **Replication** | Each partition has a leader and followers; `acks=all` + `min.insync.replicas` for durability |

## Ordering by key

Publish all events for order 8812 with key `"8812"` and they land in one partition, so `OrderCreated` is always read before `OrderCancelled`. Events for different orders may be processed in parallel on different partitions.

## Consumer groups and parallelism

A topic with 12 partitions can be consumed by up to 12 consumers in one group in parallel. A 13th consumer sits idle. Partition count is a capacity decision — increasing it later changes key-to-partition mapping.

Different groups are independent: `billing` and `analytics` each read every record at their own offset.

## Producing and consuming in Go

```go title="Kafka with segmentio/kafka-go (illustrative)"
w := &kafka.Writer{
	Addr:         kafka.TCP("kafka:9092"),
	Topic:        "orders",
	Balancer:     &kafka.Hash{},     // partition by key
	RequiredAcks: kafka.RequireAll,  // wait for in-sync replicas
}
err := w.WriteMessages(ctx, kafka.Message{
	Key:   []byte(strconv.FormatInt(order.ID, 10)),
	Value: payload,
	Headers: []kafka.Header{{Key: "event_type", Value: []byte("order.created")}},
})

r := kafka.NewReader(kafka.ReaderConfig{
	Brokers: []string{"kafka:9092"},
	GroupID: "billing",
	Topic:   "orders",
})
for {
	m, err := r.FetchMessage(ctx) // does not commit
	if err != nil {
		return err
	}
	if err := handle(ctx, m); err != nil {
		return err // offset not committed → reprocessed after restart
	}
	if err := r.CommitMessages(ctx, m); err != nil { // commit after processing
		return err
	}
}
```

Committing **after** processing gives at-least-once semantics: a crash between processing and commit reprocesses the record, so handlers must be idempotent.

## RabbitMQ or Kafka?

| | RabbitMQ | Kafka |
|---|---|---|
| Model | Queue: messages removed when acked | Log: records retained; consumers track offsets |
| Replay | No (once consumed, gone) | Yes — reset offsets, add new consumers later |
| Routing | Rich (topic, headers, fanout) | By topic and key only |
| Ordering | Per queue, single consumer | Per partition |
| Per-message retry / DLQ | Built in | Build it (retry topics) |
| Throughput | High | Very high (millions/s) |
| Best for | Task queues, commands, work distribution | Event streams, event sourcing, analytics, CDC |

:::rec Pick by access pattern, not by hype
Notifications, background jobs and commands to a specific service fit RabbitMQ well. A durable stream of business events that many teams consume, replay and analyse fits Kafka. Many organisations run both.
:::

:::quiz concept="kafka"
You need every event for a given order to be processed in order, while processing different orders in parallel. What do you do in Kafka?
- [ ] Use a topic with one partition
- [x] Use the order ID as the record key so all of an order's events go to the same partition
- [ ] Use one consumer group per order
- [ ] Sort events by timestamp in each consumer
> Kafka guarantees order within a partition, and the key decides the partition. Different keys spread across partitions for parallelism.
:::

@@lesson event-driven

In an **event-driven architecture**, services announce facts — "an order was placed" — and other services react. The producer doesn't know who is listening; new reactions can be added without changing it.

::diagram{id="event-driven"}

## Commands vs events

| | Command | Event |
|---|---|---|
| Meaning | "Do this" (`SendEmail`) | "This happened" (`OrderPlaced`) |
| Tense | Imperative | Past |
| Receivers | One, specific | Zero to many, unknown to the sender |
| Can be refused? | Yes | No — it already happened |

## Two styles of events

**Event notification** — minimal: `{"event_type":"order.created","order_id":8812}`. Consumers call back to Order Service for details. Small events, but every consumer creates synchronous load on the producer and couples to its API.

**Event-carried state transfer** — the event contains what consumers typically need:

```json
{
  "event_id": "0b6f3c3e-8d1e-4c43-9a8f-6f1b2a5c9d10",
  "event_type": "order.created",
  "schema_version": 1,
  "order_id": 8812,
  "user_id": 42,
  "status": "PENDING",
  "total_cents": 4200,
  "currency": "USD",
  "occurred_at": "2026-10-31T09:41:12.481Z"
}
```

Consumers need no callbacks; they can even keep local read models. This is what our OMS publishes.

## Designing event schemas

- **Name events as past-tense business facts**: `order.created`, `order.cancelled` — not `order.updated` with a diff of columns.
- **Include an `event_id`** (for de-duplication), **`occurred_at`**, the **aggregate ID**, and a **`schema_version`**.
- **Only add fields; never change meaning.** For incompatible changes, publish a new version (`order.created.v2` or `schema_version: 2`) alongside the old one until consumers migrate.
- **Don't leak internals**: an event is a public contract, not a dump of your table row.
- Consider a **schema registry** (Avro/Protobuf/JSON Schema) to enforce compatibility in CI.

## Choreography vs orchestration

- **Choreography**: each service reacts to events and emits its own. No central coordinator. Highly decoupled, but the overall flow is implicit and can be hard to follow.
- **Orchestration**: a coordinator (often a saga orchestrator) tells each participant what to do next. The flow is explicit and observable, at the cost of a central component.

Both appear in [the Saga pattern](#/lesson/m07/pattern-saga).

## What can go wrong?

- **Event storms**: one event triggers cascades of others that are hard to reason about. Map flows explicitly (event storming, diagrams).
- **Lost visibility**: "why didn't the email go out?" requires tracing across the broker. Propagate trace context in message headers.
- **Duplicate and out-of-order delivery**: consumers must be idempotent and tolerant of reordering (use versions or timestamps per aggregate).
- **Dual writes**: publishing outside the database transaction loses events. Use the outbox.

:::quiz concept="event-driven"
A new Loyalty Service must award points when orders are placed. In an event-driven OMS, what changes in Order Service?
- [ ] Order Service must call Loyalty Service's API after creating an order
- [x] Nothing — Loyalty Service subscribes to the existing `order.created` events
- [ ] Order Service must add Loyalty to its list of event recipients
- [ ] Order Service must publish a new `award_points` command
> Producers publish facts without knowing consumers. New consumers bind their own queues, which is the main extensibility benefit of event-driven design.

@@lesson comm-lab

Compare the communication styles side by side. The simulator runs the same order flow three ways — REST, gRPC and asynchronous messaging for the notification step — and records what each one costs.

::widget{name="comm-sim"}

:::sim About the numbers
Latencies, payload sizes and failure outcomes are generated by a model in your browser using realistic proportions (protobuf payloads smaller than JSON, broker publish faster than a full synchronous call). They are illustrative, not benchmarks.
:::

## Experiments

1. **Baseline.** Send a few orders in each mode and compare end-to-end latency. Synchronous notification adds the email provider's latency to every order.
2. **Notification Service down.** In REST and gRPC modes, order creation fails (or slows to the timeout). In async mode, orders succeed and the queue depth grows — then drains when you bring the service back.
3. **User Service slow.** All modes suffer, because validating the customer is synchronous in all of them. Async messaging does not fix dependencies you *need* to decide.
4. **Payload size.** Compare JSON vs protobuf bytes for the same message.

## What the comparison shows

| | REST (sync) | gRPC (sync) | Messaging (async) |
|---|---|---|---|
| Coupling | Temporal + schema | Temporal + generated schema | Schema only |
| Latency added to the request | Full callee latency | Callee latency, less overhead | Publish only (~1 ms) |
| Notification Service down | Order fails / degrades | Order fails / degrades | Order succeeds; email delayed |
| Ordering & duplicates | N/A | N/A | Must handle redelivery |
| Debuggability | Simple | Needs tooling | Needs tracing across the broker |

:::quiz concept="sync-communication"
In the simulator, which change makes order creation keep working while Notification Service is down?
- [ ] Switching from REST to gRPC
- [ ] Increasing the notification timeout
- [x] Publishing an event to the broker instead of calling Notification Service synchronously
- [ ] Adding retries to the notification call
> gRPC is still synchronous; longer timeouts and retries only delay the failure. Messaging removes the temporal coupling: the broker holds the event until the consumer returns.
:::
