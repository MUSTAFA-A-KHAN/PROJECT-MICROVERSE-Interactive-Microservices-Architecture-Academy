@@lesson data-ownership

The rule is simple to state and hard to keep under deadline pressure: **a service's database is private**. This lesson is about why — told through the kind of incident that makes teams adopt the rule.

## An incident

The Reporting team needs order totals per customer email. User and Order data live in one shared Postgres cluster, so they write:

```sql
SELECT u.email, sum(o.total_cents)
FROM orders o JOIN users u ON u.id = o.user_id
GROUP BY u.email;
```

It works. Six months later:

1. The User team splits `users` into `accounts` and `profiles` for GDPR reasons. Their migration passes their tests. Reporting breaks at 2 a.m.
2. The Order team adds a covering index; the reporting query's plan changes and it now scans 40 million rows during peak hours, holding locks and starving Order Service's connection pool. Checkout latency triples.
3. Nobody can tell from the schema who depends on which column.

Every problem is a form of **coupling through the database**: schema coupling, runtime coupling and invisible contracts.

::diagram{id="db-per-service"}

## What ownership means

- **Only the owning service connects** to its database, with its own credentials.
- **The schema is an implementation detail**, free to change without notice.
- **Other services use the owner's API or events** — published, versioned contracts.

## How the reporting need should be met

| Option | How | Trade-off |
|---|---|---|
| API composition | Reporting calls both APIs and joins in memory | Fine for small result sets; slow for analytics |
| Events into a warehouse | Each service publishes events; a pipeline loads them into BigQuery/Snowflake | Eventually consistent; designed for analytics |
| Change data capture (CDC) | Debezium streams each database's changes to Kafka | Low effort for producers; still a contract to maintain |
| Read replica owned by the team | The owner publishes a *documented* reporting view | Owner explicitly supports it as a contract |

:::rule Shared databases are a contract you didn't write down
If another team needs your data, give them an API, an event stream or an explicitly supported export. Never hand out credentials to your tables.
:::

## Physical layouts

Ownership is logical; the physical layout is a cost decision:

- **Database per service on separate instances** — strongest isolation, highest cost.
- **Separate databases on a shared cluster** — good isolation, shared hardware; noisy neighbours possible.
- **Separate schemas with separate users** — cheapest; isolation by permissions only.

Start with what you can operate; keep the ownership boundary either way.

:::quiz concept="database-per-service"
Which practice most directly prevents another team's query from breaking when you rename a column?
- [ ] Adding database comments describing each column
- [x] Not granting other services access to your database, and exposing data through an API or events instead
- [ ] Running migrations at night
- [ ] Using an ORM
> If nobody else can read your tables, your schema is private and renames affect only your code. Contracts live at the API or event level.
:::

@@lesson postgres-go

`pgx` is the de-facto PostgreSQL driver for Go. Its native API is faster and more featureful than `database/sql`, and `pgxpool` provides a concurrency-safe connection pool.

## Opening a pool

```go title="order-service/cmd/server/main.go (excerpt)"
pc, err := pgxpool.ParseConfig(cfg.DatabaseURL)
if err != nil {
	return nil, fmt.Errorf("parse DATABASE_URL: %w", err)
}
pc.MaxConns = cfg.DBMaxConns          // replicas × MaxConns < Postgres max_connections
pc.MinConns = 2
pc.MaxConnLifetime = 30 * time.Minute // recycle (failovers, rebalancing)
pc.MaxConnIdleTime = 5 * time.Minute
pc.HealthCheckPeriod = 30 * time.Second

pool, err := pgxpool.NewWithConfig(ctx, pc)
if err != nil {
	return nil, fmt.Errorf("create pool: %w", err)
}
pingCtx, cancel := context.WithTimeout(ctx, 5*time.Second)
defer cancel()
if err := pool.Ping(pingCtx); err != nil { // fail fast at startup
	pool.Close()
	return nil, fmt.Errorf("connect to database: %w", err)
}
```

Create **one pool per process** at startup and share it. Never open a connection per request.

## Querying

```go title="user-service/internal/repository/user_repository.go (excerpt)"
func (r *UserRepository) GetByEmail(ctx context.Context, email string) (*model.User, error) {
	u, err := scanUser(r.pool.QueryRow(ctx, `SELECT `+userColumns+` FROM users WHERE email = $1`, email))
	if err != nil && !errors.Is(err, model.ErrNotFound) {
		return nil, fmt.Errorf("get user by email: %w", err)
	}
	return u, err
}
```

- **Placeholders (`$1`)** — the driver sends values separately from SQL, which prevents SQL injection. Never concatenate user input into SQL.
- **`ctx`** — cancels the query (pgx sends a cancel request to Postgres) when the request ends.
- **`pgx.ErrNoRows`** — translated to a domain error at the repository boundary.

## Collecting rows

pgx v5 has generic helpers that remove boilerplate and close rows for you:

```go title="order-service/internal/repository/order_repository.go (excerpt)"
rows, err := q.Query(ctx,
	`SELECT product_id, quantity, unit_price_cents FROM order_items WHERE order_id = $1 ORDER BY product_id`, id)
if err != nil {
	return nil, fmt.Errorf("get items for order %d: %w", id, err)
}
items, err := pgx.CollectRows(rows, pgx.RowToStructByPos[model.Item])
```

## Transactions

```go
tx, err := r.pool.Begin(ctx)
if err != nil {
	return err
}
// Rollback is a no-op once Commit has succeeded, so it is always safe to defer.
defer func() { _ = tx.Rollback(ctx) }()

// ... tx.Exec / tx.QueryRow ...

return tx.Commit(ctx)
```

A transaction holds one connection from the pool until it ends — keep transactions short and **never make network calls to other services inside one**.

## Bulk inserts with COPY

```go title="order-service/internal/repository/order_repository.go (excerpt)"
if _, err := tx.CopyFrom(ctx, pgx.Identifier{"order_items"},
	[]string{"order_id", "product_id", "quantity", "unit_price_cents"}, pgx.CopyFromRows(rows)); err != nil {
	return nil, false, fmt.Errorf("insert items: %w", err)
}
```

`COPY` is dramatically faster than many `INSERT` statements for bulk data.

## What can go wrong?

- **Forgetting `rows.Close()`** with manual iteration leaks connections (CollectRows handles it).
- **Long transactions** hold locks and connections, blocking vacuum and other writers.
- **N+1 queries**: loading 100 orders then querying items once per order. Batch with `WHERE order_id = ANY($1)`.
- **No statement timeout**: set `statement_timeout` on the role or per transaction so a runaway query cannot run for hours.

:::quiz concept="connection-pooling"
Why is `pgxpool.New` called once in `main` rather than inside each request handler?
- [ ] pgx does not allow more than one pool
- [x] Pools are expensive to create and are meant to be shared; per-request pools would open new connections constantly and exhaust Postgres
- [ ] Handlers cannot import pgx
- [ ] To make the binary smaller
> A pool amortises connection setup across requests and caps concurrency. Creating pools per request defeats both purposes.
:::

@@lesson migrations

Your schema changes as your service evolves. **Migrations** are versioned, ordered scripts that move the database from one schema version to the next — reviewed in pull requests and applied automatically, the same way everywhere.

## How golang-migrate works

```text
order-service/migrations/
├── 000001_create_orders.up.sql
├── 000001_create_orders.down.sql
├── 000002_add_orders_channel.up.sql
└── 000002_add_orders_channel.down.sql
```

The tool records the current version in a `schema_migrations` table and applies pending `up` files in order. In our Compose file a one-shot container runs before the service starts:

```yaml title="docker-compose.yml (excerpt)"
orders-migrate:
  image: migrate/migrate:v4.18.1
  command: ["-path=/migrations", "-database=postgres://orders:${ORDERS_DB_PASSWORD}@orders-db:5432/orders?sslmode=disable", "up"]
  volumes: ["./order-service/migrations:/migrations:ro"]
  depends_on:
    orders-db: { condition: service_healthy }
order-service:
  depends_on:
    orders-migrate: { condition: service_completed_successfully }
```

In Kubernetes the equivalent is a Job (or an init container, or a step in the deploy pipeline) that runs before the new pods roll out.

## Zero-downtime rules

During a rolling deploy, the **old** application version runs against the **new** schema. Every migration must be compatible with the code currently running.

| Safe (online) | Dangerous (locks or breaks old code) |
|---|---|
| `ADD COLUMN` nullable (no default rewrite in PG 11+) | `ADD COLUMN ... NOT NULL` without default on old PG |
| `CREATE INDEX CONCURRENTLY` | `CREATE INDEX` (blocks writes for the duration) |
| Add a new table | `DROP COLUMN` still read by running code |
| `ADD CONSTRAINT ... NOT VALID` then `VALIDATE CONSTRAINT` | `ADD CONSTRAINT` (full scan under lock) |
| Backfill in small batches | One giant `UPDATE` (long locks, WAL spike) |
| | `ALTER COLUMN TYPE` (table rewrite) |
| | `RENAME COLUMN` (breaks old code instantly) |

Changes that look atomic are done as **expand → migrate → contract** across several deploys (see [Independent deployment](#/lesson/m03/independent-deployment)).

## Lock timeouts protect you

Even a fast `ALTER TABLE` needs a brief exclusive lock. If a long-running query holds a conflicting lock, the `ALTER` waits — and every query behind it queues up. Set a lock timeout so the migration fails fast instead of freezing the table:

```sql
SET lock_timeout = '3s';
SET statement_timeout = '15min';
CREATE INDEX CONCURRENTLY IF NOT EXISTS orders_status_created_idx
    ON orders (status, created_at);
```

Note: `CREATE INDEX CONCURRENTLY` cannot run inside a transaction block — configure your migration tool accordingly (golang-migrate runs each file as given; keep such statements in their own file).

## What can go wrong?

- **Editing an applied migration.** Environments diverge. Migrations are append-only; fix forward with a new one.
- **App runs migrations on startup in every replica.** Ten pods race to migrate. Use a single job, or a migration lock.
- **Down migrations that destroy data.** Useful locally; rarely run in production. Prefer forward fixes.
- **Long backfills in a migration.** Run them as a separate, resumable batch job.

:::quiz concept="sql-migrations"
You need to add an index to a 200-million-row `orders` table that receives constant writes. Which statement avoids blocking writes for the duration of the build?
- [ ] `CREATE INDEX orders_status_idx ON orders (status);`
- [x] `CREATE INDEX CONCURRENTLY orders_status_idx ON orders (status);`
- [ ] `REINDEX TABLE orders;`
- [ ] `VACUUM FULL orders;`
> `CONCURRENTLY` builds the index without holding a lock that blocks inserts and updates. It takes longer and cannot run in a transaction, but keeps the table writable.
:::

@@lesson transactions

A **transaction** groups operations so they succeed or fail as one. Understanding *isolation* — what concurrent transactions can see of each other — is what separates correct concurrent code from code that loses money under load.

## ACID

| Property | Guarantee |
|---|---|
| **Atomicity** | All statements commit, or none do |
| **Consistency** | Constraints (unique, foreign key, check) hold after commit |
| **Isolation** | Concurrent transactions don't see each other's partial work (to a configurable degree) |
| **Durability** | Once committed, data survives crashes (WAL) |

## Isolation levels in PostgreSQL

| Level | Prevents | Still allows |
|---|---|---|
| Read Committed (default) | Dirty reads | Non-repeatable reads, phantoms, **lost updates** with read-then-write |
| Repeatable Read | + non-repeatable reads, phantoms | Serialization failures you must retry |
| Serializable | All anomalies (as if transactions ran one at a time) | More serialization failures under contention |

## The lost update

Two requests cancel the same order and refund at once, each doing *read → check → write*:

::widget{name="tx-visualizer"}

Under Read Committed both transactions read `status = 'CONFIRMED'`, both decide the cancel is allowed, and both write — two refunds. Three standard fixes:

**1. Atomic conditional update** — let the database check and write in one statement:

```sql
UPDATE orders SET status = 'CANCELLED'
WHERE id = $1 AND status IN ('PENDING', 'CONFIRMED')
RETURNING id;   -- zero rows means someone else won
```

**2. Pessimistic locking** — lock the row while deciding:

```sql
BEGIN;
SELECT status FROM orders WHERE id = $1 FOR UPDATE;  -- second transaction waits here
-- check status in application code, then:
UPDATE orders SET status = 'CANCELLED' WHERE id = $1;
COMMIT;
```

**3. Optimistic concurrency** — what our Order Service does:

```go title="order-service/internal/repository/order_repository.go (excerpt)"
tag, err := tx.Exec(ctx,
	`UPDATE orders SET status = $1, version = version + 1, updated_at = now()
	 WHERE id = $2 AND version = $3`,
	to, o.ID, o.Version)
if err != nil {
	return fmt.Errorf("update status: %w", err)
}
if tag.RowsAffected() == 0 {
	return model.ErrConcurrentUpdate // someone changed it since we read it → 409
}
```

| Approach | Best when |
|---|---|
| Conditional update | The rule fits in a `WHERE` clause |
| `SELECT ... FOR UPDATE` | High contention on the same rows; short transactions |
| Optimistic (version) | Low contention; decisions involve application logic; long user "think time" between read and write |

## Keep transactions short

- Never call another service inside a transaction — a slow HTTP call holds row locks and a pool connection.
- Do validation and remote calls *before* `BEGIN`; do only database work inside.
- Retry on `serialization_failure` (SQLSTATE 40001) and `deadlock_detected` (40P01) with backoff when using stricter isolation.

:::quiz concept="transactions"
Two transactions under Read Committed both run `SELECT balance` then `UPDATE accounts SET balance = <value computed in Go>`. What anomaly can occur?
- [ ] Dirty read
- [x] Lost update — one transaction's write overwrites the other's
- [ ] Phantom read
- [ ] Nothing; Read Committed prevents this
> Read Committed does not prevent read-modify-write races. Use an atomic `UPDATE ... SET balance = balance - $1`, `SELECT ... FOR UPDATE`, or optimistic version checks.
:::

@@lesson distributed-transactions

Inside one database, a transaction makes several changes atomic. Across services — each with its own database — there is no such thing for free. This lesson covers why the classic solution is avoided and what replaces it.

## Two-phase commit (2PC)

A coordinator asks all participants to **prepare** (write durably and hold locks), then tells them all to **commit**.

::diagram{id="two-phase-commit"}

Why microservices avoid it:

- **Blocking**: if the coordinator fails after prepare, participants hold locks until it recovers.
- **Availability**: the transaction needs *every* participant up at the same time.
- **Latency**: two round trips to every participant, with locks held throughout.
- **Support**: message brokers, most NoSQL stores and HTTP APIs don't participate in XA transactions.

## What replaces it: local transactions + messaging

1. Each service makes **local** ACID changes.
2. Services coordinate through **events** (or commands), delivered reliably via the **transactional outbox**.
3. Multi-step business processes are **sagas**: a sequence of local transactions with **compensating actions** to semantically undo earlier steps if a later one fails.

The result is **eventual consistency**: the system is temporarily inconsistent (paid but not yet reserved), and converges to a consistent state.

## Designing for eventual consistency

- **Make intermediate states explicit** in the domain: `PENDING`, `PAYMENT_AUTHORISED`, `CONFIRMED` — not a boolean flipped at the end.
- **Show honest UX**: "We've received your order and are confirming payment" instead of pretending everything is final.
- **Read your own writes**: after creating an order, read it from the owner (Order Service), not from a lagging projection.
- **Reconcile**: periodic jobs detect stuck states (an order in `PENDING` for an hour) and repair or alert.
- **Idempotency everywhere**: retries and redeliveries are normal in an eventually consistent system.

## Where the outbox fits

The saga and every event-driven flow depend on one primitive: *change my database and emit an event, atomically*. That's the [Transactional Outbox](#/lesson/m07/pattern-outbox). Our Order Service writes the order and its `order.created` event in one transaction; a relay publishes it.

:::rec Consistency is a business decision
Ask domain experts how long an inconsistency is acceptable and what happens if it lasts. "The email is a few seconds late" is fine. "Stock is oversold for an hour" may not be — that might justify keeping stock reservation and order creation in one service.
:::

:::quiz concept="distributed-transactions"
Why do most microservice architectures avoid two-phase commit across services?
- [ ] 2PC is not supported by PostgreSQL
- [x] It blocks participants holding locks if the coordinator fails, needs every participant available at once, and many components (brokers, APIs) can't participate
- [ ] It only works with Kafka
- [ ] It makes data eventually consistent
> 2PC gives atomicity at the cost of availability and blocking. Sagas with local transactions and reliable messaging trade atomicity for availability, with compensations instead of rollbacks.
:::

:::quiz concept="eventual-consistency"

- [ ] Make the projection update synchronously inside the order transaction
- [x] Read the just-created order from Order Service (the source of truth) or show it optimistically from the create response
- [ ] Tell the user to refresh
- [ ] Remove the projection
> Read-your-own-writes: for data the user just changed, read from the owner or use the response you already have. Projections are for everything else.
:::

@@lesson indexing

Most "the database is slow" incidents are missing or misused indexes. Knowing how a B-tree index works lets you predict which queries it helps — and read `EXPLAIN ANALYZE` to confirm.

## How a B-tree index works

A B-tree keeps keys sorted in a balanced tree of pages. Finding a key takes O(log n) page reads instead of scanning every row. Because keys are sorted, the same index also serves **range** queries and **ORDER BY** on its leading columns.

The cost: every `INSERT`, `UPDATE` of indexed columns and `DELETE` must update every index. Indexes speed reads and slow writes.

## Composite indexes: column order matters

An index on `(user_id, id DESC)` is sorted by `user_id`, then by `id` within each user. It serves:

- `WHERE user_id = 42` ✓
- `WHERE user_id = 42 ORDER BY id DESC LIMIT 20` ✓ (no sort needed)
- `WHERE user_id = 42 AND id < 8812 ORDER BY id DESC` ✓ (keyset pagination)
- `WHERE id = 8812` ✗ (leading column not constrained — use the primary key)

**Rule of thumb**: equality columns first, then the range/sort column.

## Reading EXPLAIN ANALYZE

```text
Limit  (cost=0.43..8.71 rows=20) (actual time=0.031..0.074 rows=20 loops=1)
  ->  Index Scan using orders_user_id_id_idx on orders  (cost=0.43..1652.91 rows=4002)
        Index Cond: ((user_id = 42) AND (id < 8812))
Planning Time: 0.112 ms
Execution Time: 0.093 ms
```

Look for:

- **Seq Scan** on a large table with a selective `WHERE` → a missing index.
- **actual rows ≫ estimated rows** → stale statistics; run `ANALYZE`.
- **Sort** with `external merge` → `ORDER BY` not served by an index, spilling to disk.
- **Rows Removed by Filter** large → the index doesn't cover the predicate.

## Partial and covering indexes

```sql
-- Partial: index only the rows queries care about (stays tiny).
CREATE INDEX outbox_unpublished_idx ON outbox (id) WHERE published_at IS NULL;

-- Covering: INCLUDE extra columns so the query never touches the table (index-only scan).
CREATE INDEX orders_user_status_idx ON orders (user_id, status) INCLUDE (total_cents);
```

Our outbox uses the partial index: millions of published events, but the relay only ever scans the handful that are pending.

## Keyset vs OFFSET pagination

`OFFSET 100000 LIMIT 20` reads and throws away 100,000 rows. Keyset pagination (`WHERE id < $last_seen ORDER BY id DESC LIMIT 20`) jumps straight there via the index — constant time at any depth. That's what `ListByUser` does.

:::quiz concept="indexing"

- [ ] `CREATE INDEX ON orders (created_at)`
- [x] `CREATE INDEX ON orders (user_id, created_at DESC)`
- [ ] `CREATE INDEX ON orders (created_at, user_id)`
- [ ] `CREATE INDEX ON orders (total_cents)`
> Equality column first, then the sort column. The planner can jump to user_id = $1 and read the first 20 entries already in the right order — no sort, no scan.
:::

@@lesson connection-pooling

Every PostgreSQL connection is a separate server process using several megabytes of memory. A database can serve only a limited number concurrently — and in a horizontally scaled microservice, the number of connections grows with every replica you add.

## The arithmetic that causes outages

```text
max_connections (Postgres)              = 100
order-service replicas                  = 6
pgxpool MaxConns per replica            = 20
------------------------------------------------
potential connections                   = 120   ✗ exceeds the limit
```

During a traffic spike the autoscaler adds replicas, each opens its pool, and new connections fail with `FATAL: sorry, too many clients already` — in the middle of the spike.

::diagram{id="connection-pool"}

## Sizing the pool

- A pool larger than the database can **actively** work on doesn't increase throughput; it adds contention. A common starting point for the *database side* is around `(2 × CPU cores) + effective_spindle_count`, then measure.
- Budget across services: `Σ (replicas_max × MaxConns) + admin headroom < max_connections`.
- Align the HPA's `maxReplicas` with the pool budget (our manifest caps Order Service at 12 replicas × 10 connections).

## pgxpool settings that matter

| Setting | Why |
|---|---|
| `MaxConns` | Upper bound per replica — the key budget number |
| `MinConns` | Warm connections to avoid cold-start latency |
| `MaxConnLifetime` | Recycle connections (after failover, to rebalance across replicas) |
| `MaxConnIdleTime` | Release idle connections back to the database |
| `HealthCheckPeriod` | Detect dead connections proactively |

Expose pool metrics (`pool.Stat()`: acquired, idle, waiting, acquire duration). **Acquire wait time** rising is an early warning that the pool or database is saturated.

## PgBouncer

A connection pooler between services and Postgres multiplexes many client connections onto few server connections.

| Mode | Server connection held for | Notes |
|---|---|---|
| Session | The whole client session | Least benefit; full compatibility |
| **Transaction** | One transaction | Big win; incompatible with session state (session-level advisory locks, `SET` without `LOCAL`) |
| Statement | One statement | Rarely used; no multi-statement transactions |

pgx works with transaction pooling; disable automatic prepared statement caching or use PgBouncer ≥ 1.21 with `max_prepared_statements` configured.

:::warn A pool hides a slow database until it doesn't
When queries slow down, connections are held longer, the pool empties, and requests queue waiting for a connection. Latency looks like an application problem. Always check pool wait time and database query latency together.
:::

:::quiz concept="connection-pooling"
Postgres has `max_connections = 200` (keep 20 for admin). Order Service's pool is 15 per replica and User Service runs 4 replicas × 10. What is the safe `maxReplicas` for Order Service?
- [ ] 13
- [x] 9
- [ ] 12
- [ ] 20
> Available: 200 − 20 admin − 40 (User Service) = 140. 140 ÷ 15 ≈ 9.3, so at most 9 replicas. More would risk "too many clients" during scale-out.
:::

@@lesson redis-caching

A cache stores the results of expensive reads in fast memory so most requests never reach the database. Used well, it cuts latency and database load dramatically; used carelessly, it serves wrong data or collapses the database when it misses.

::diagram{id="cache-aside"}

## Cache-aside (lazy loading)

The most common pattern — and what User Service uses for profiles:

```go title="user-service/internal/service/user_service.go (excerpt)"
func (s *UserService) GetProfile(ctx context.Context, id int64) (*model.User, error) {
	cached, err := s.cache.Get(ctx, id)
	switch {
	case err != nil:
		s.log.WarnContext(ctx, "profile cache read failed; using database", "user_id", id, "err", err)
	case cached != nil:
		return cached, nil
	}

	u, err := s.repo.GetByID(ctx, id)
	if err != nil {
		return nil, err
	}
	if err := s.cache.Set(ctx, u); err != nil {
		s.log.WarnContext(ctx, "profile cache write failed", "user_id", id, "err", err)
	}
	return u, nil
}
```

Note: a Redis error is **logged and ignored** — the cache is an optimisation, never a dependency for correctness.

## Invalidation

> There are only two hard things in Computer Science: cache invalidation and naming things. — Phil Karlton

| Strategy | How | Staleness |
|---|---|---|
| TTL only | Entries expire after N seconds | Up to N seconds |
| Delete on write (+ TTL) | `UPDATE` then `DEL user:42` | Small window; TTL as a safety net |
| Write-through | Write DB and cache together | Low, but complex on failure |
| Event-driven | Invalidate on `user.updated` events | Bounded by event latency |

Prefer **delete** over **update** on writes: two concurrent writers updating the cache can leave the older value behind; deleting forces the next read to load the latest.

## Stampedes (thundering herd)

A popular key expires; 5,000 concurrent requests miss at once and all query Postgres. Mitigations:

```go
import "golang.org/x/sync/singleflight"

var group singleflight.Group

func (s *UserService) getProfileOnce(ctx context.Context, id int64) (*model.User, error) {
	v, err, _ := group.Do(strconv.FormatInt(id, 10), func() (any, error) {
		return s.repo.GetByID(ctx, id) // only ONE in-flight load per key per process
	})
	if err != nil {
		return nil, err
	}
	return v.(*model.User), nil
}
```

Also: add **TTL jitter** (e.g. 300 s ± 10%) so keys don't expire together, and for very hot keys refresh early in the background.

## What (not) to cache

| Good candidates | Poor candidates |
|---|---|
| Read-heavy, rarely changing data (profiles, catalogues, config) | Data that must be strictly current (balances, stock at checkout) |
| Expensive computations (aggregates) | Per-request unique data (low hit ratio) |
| Results of slow external APIs | Security decisions that must reflect revocations immediately |

## Operating Redis

- Set `maxmemory` and an eviction policy (`allkeys-lru` for pure caches).
- Monitor hit ratio, evictions, memory and latency.
- Size the **database** for cache-miss traffic — when Redis restarts, every request misses at once.
- Never cache sensitive fields (our `User.PasswordHash` is excluded via `json:"-"`).

:::quiz concept="caching"
A hot product's cache entry expires and thousands of requests simultaneously query the database for it. What is this, and what is one fix?
- [ ] Cache poisoning; fix with TLS
- [x] A cache stampede; fix with singleflight (or locking) so one request reloads while others wait, plus TTL jitter
- [ ] A memory leak; fix with a larger Redis instance
- [ ] Write skew; fix with SERIALIZABLE isolation
> Stampedes happen when many misses for the same key reach the database at once. Coalescing loads per key and spreading expirations prevents them.
:::
