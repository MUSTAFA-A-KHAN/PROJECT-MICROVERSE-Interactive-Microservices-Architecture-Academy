@@lesson pattern-api-gateway

## The problem

Clients need many services, but each service exposes its own host, auth scheme and conventions. Every client — web, iOS, Android, partners — must know the internal topology, and every service must implement TLS, authentication, rate limiting and logging itself.

## Why it occurs

Decomposing a system into services multiplies endpoints. Without a single entry point, cross-cutting concerns are duplicated (and drift), internal refactors become breaking client changes, and the attack surface grows with every service.

## Architecture

::diagram{id="gateway"}

## Request flow

1. The client sends `POST https://api.example.com/api/v1/orders` with a bearer token.
2. The gateway assigns `X-Request-ID`, enforces the body size limit and matches the route.
3. It verifies the JWT locally and checks the caller's rate limit.
4. It forwards to Order Service with identity headers, a timeout and a circuit breaker.
5. It streams the response back, adding rate-limit headers, and writes one access-log line.

## Go implementation

The full gateway is in the playground; the pipeline is assembled in `main`:

```go title="api-gateway/cmd/gateway/main.go (excerpt)"
api := r.Group("/api",
	middleware.BodyLimit(cfg.MaxBodyBytes),
	p.Resolve(),
	middleware.JWTAuth(cfg.JWTSecret, cfg.JWTIssuer, cfg.JWTAudience, proxy.IsPublic),
	middleware.RateLimit(rdb, middleware.RateLimitConfig{Capacity: cfg.RateCapacity, PerSecond: cfg.RatePerSecond}, log),
)
api.Any("/*path", p.Forward)
```

## Real-world scenario

A mobile app shipped with `orders.internal.example.com` hard-coded must keep working for two years of installs. When the Order team splits out a Returns service, the gateway routes `/api/v1/orders/*/returns` to the new service — and no app update is needed.

## Advantages and disadvantages

| Advantages | Disadvantages |
|---|---|
| One stable public surface; internal topology can change | Another critical component to run and scale |
| Cross-cutting policies implemented once | Extra network hop and latency |
| Smaller attack surface | Risk of becoming a bottleneck owned by one team |
| Central observability of external traffic | Temptation to add business logic |

## Common mistakes

- Putting business logic or orchestration in the gateway.
- One gateway shared by every client type when their needs diverge (consider BFFs).
- Retrying non-idempotent requests at the gateway.
- Not stripping client-supplied identity headers.

:::quiz concept="api-gateway"
When does a **Backend for Frontend** (BFF) make more sense than a single general-purpose gateway?
- [ ] When there is only one client application
- [x] When different clients (web, mobile, partners) need differently shaped or aggregated APIs
- [ ] When services use gRPC internally
- [ ] When you need TLS termination
> A BFF is a gateway per client type, owned by that client's team, free to aggregate and shape responses for it — without polluting a shared gateway with client-specific logic.
:::

@@lesson pattern-service-discovery

## The problem

Order Service must call User Service, but User Service runs as several instances whose IP addresses change on every deploy, scale event and failure.

## Why it occurs

Containers are ephemeral and scheduled dynamically. Static configuration (`USER_SERVICE=10.0.3.17`) is wrong within minutes, and a hard-coded single instance is a single point of failure.

## Architecture

::diagram{id="service-discovery"}

## Request flow

1. Each healthy instance is registered (automatically in Kubernetes via readiness; explicitly in Consul).
2. The caller resolves a stable name (`user-service`).
3. Server-side discovery: the name resolves to a virtual IP and the platform forwards to a healthy instance. Client-side discovery: the caller gets the instance list and picks one.
4. When an instance fails its health check, it is removed; callers stop reaching it without any configuration change.

## Go implementation

With platform DNS, the code is just a URL from configuration:

```go title="order-service/internal/config/config.go (excerpt)"
UserServiceURL: getEnv("USER_SERVICE_URL", "http://user-service:8081"),
```

For gRPC with client-side balancing against a headless Kubernetes Service (DNS returns all pod IPs):

```go
conn, err := grpc.NewClient("dns:///user-service-headless.default.svc.cluster.local:9090",
	grpc.WithDefaultServiceConfig(`{"loadBalancingConfig":[{"round_robin":{}}]}`),
	grpc.WithTransportCredentials(creds),
)
```

## Real-world scenario

During a rolling deploy of User Service, pods are replaced one at a time. Old pods fail readiness as they shut down and leave the endpoints list; new pods join once `/readyz` returns 200. Order Service's calls continue uninterrupted against the same name.

## Advantages and disadvantages

| Advantages | Disadvantages |
|---|---|
| Location transparency; no hard-coded addresses | Registry becomes critical infrastructure |
| Health-aware routing | Propagation delays (DNS TTLs, endpoint updates) |
| Enables autoscaling and rolling updates | Client-side discovery needs a library per language |

## Common mistakes

- Caching DNS forever or holding connections to dead instances indefinitely.
- Relying on ClusterIP for gRPC load balancing (connection-level, not request-level).
- Registering instances before they are ready to serve.

:::quiz concept="service-discovery"
In Kubernetes, what removes a pod that is shutting down from the list of instances that receive traffic?
- [ ] The pod deletes its own DNS record
- [x] Its readiness status (and termination) causes the endpoint controller to remove it from the Service's endpoints
- [ ] The Ingress controller polls each pod
- [ ] Callers detect connection errors and blacklist it
> Service endpoints include only ready pods. Failing readiness — or entering termination — removes the pod, so the stable Service name never routes to it.
:::

@@lesson pattern-circuit-breaker

## The problem

User Service is failing or hanging. Every call from Order Service waits for the full timeout, holds a goroutine, a connection and memory, and returns an error anyway. The struggling service receives even more traffic and can't recover.

## Why it occurs

Callers have no memory: each request rediscovers the failure independently. Timeouts bound the damage per call, but at thousands of calls per second, "bounded" waits still exhaust resources and amplify load on the failing dependency — a cascading failure.

## Architecture

::diagram{id="p-circuit-breaker"}

## Request flow

1. **Closed**: calls pass through; the breaker counts consecutive failures (or failure rate in a window).
2. When failures cross a threshold, the breaker **opens**.
3. **Open**: calls fail immediately (`ErrOpenState`) — microseconds, no network.
4. After a cool-down it goes **half-open** and lets a limited number of probe calls through.
5. Probes succeed → **closed**. Probes fail → **open** again for another cool-down.

Explore the state machine interactively:

::widget{name="circuit-breaker"}

## Go implementation

A hand-written breaker (from the gateway) makes the mechanics explicit:

```go title="api-gateway/internal/breaker/breaker.go (excerpt)"
func (b *Breaker) Allow() error {
	b.mu.Lock()
	defer b.mu.Unlock()
	switch b.state {
	case Open:
		if b.now().Sub(b.openedAt) < b.cooldown {
			return ErrOpen
		}
		b.setState(HalfOpen)
		fallthrough
	case HalfOpen:
		if b.probes >= b.maxProbes {
			return ErrOpen
		}
		b.probes++
	}
	return nil
}
```

In Order Service, the `sony/gobreaker` library wraps the retrying client — note which errors **don't** count as failures:

```go title="order-service/internal/client/user_client.go (excerpt)"
c.cb = gobreaker.NewCircuitBreaker[*model.Customer](gobreaker.Settings{
	Name:        "user-service",
	MaxRequests: 1,                // probes allowed while half-open
	Timeout:     30 * time.Second, // stay open this long before probing
	ReadyToTrip: func(c gobreaker.Counts) bool { return c.ConsecutiveFailures >= 5 },
	// "Not found" and cancellations are not signs of an unhealthy dependency.
	IsSuccessful: func(err error) bool { return err == nil || errors.Is(err, model.ErrCustomerNotFound) },
	IsExcluded:   func(err error) bool { return errors.Is(err, context.Canceled) },
})
```

When it is open, the handler turns the error into `503 Service Unavailable` with `Retry-After`.

## Real-world scenario

A payment provider has a 10-minute outage. Without a breaker, checkout threads wait 5 seconds each, the checkout service's pods saturate, and even customers paying by gift card can't check out. With a breaker, payment calls fail in microseconds, checkout stays responsive, and the UI offers "pay later" — a fallback — until probes succeed.

## Advantages and disadvantages

| Advantages | Disadvantages |
|---|---|
| Stops cascading failure; frees caller resources | Per-instance state: each replica learns separately |
| Gives the dependency room to recover | Tuning thresholds is workload-specific |
| Fast, explicit failures enable fallbacks | Can reject requests that would have succeeded during half-open |

## Common mistakes

- Counting client errors (404, 422) or caller cancellations as failures.
- One breaker for all dependencies — a failing one blocks healthy ones.
- No fallback: an open breaker that just returns errors faster still fails the user.
- Retries *outside* the breaker that keep hammering while it is open.
- No metrics or alerts on state changes.

:::quiz concept="circuit-breaker"
What happens to a call while the breaker is **open**?
- [ ] It is queued until the dependency recovers
- [ ] It is sent with a shorter timeout
- [x] It fails immediately without calling the dependency
- [ ] It is retried with exponential backoff
> Failing fast is the point: no socket, no goroutine waiting, no load on the dependency. After the cool-down, a probe decides whether to close again.
:::

@@lesson pattern-retry

## The problem

A call fails because of something temporary: a pod being replaced mid-deploy, a dropped TCP connection, a brief overload returning 503. Failing the user's request for a blip that would have passed in 100 ms is a poor experience.

## Why it occurs

Distributed systems constantly experience transient faults: rolling updates, autoscaling, network hiccups, leader elections, garbage-collection pauses. Most last milliseconds.

## Architecture

::diagram{id="p-retry"}

## Request flow

1. Attempt the call with a per-attempt timeout.
2. On a **retryable** failure, wait `random(0, base × 2^(attempt−1))`.
3. Retry, up to a maximum number of attempts and within the caller's overall deadline.
4. Stop immediately on non-retryable errors or when the caller's context is done.

Compare backoff strategies under load:

::widget{name="retry-backoff"}

## Go implementation

```go title="order-service/internal/client/user_client.go (excerpt)"
func (c *UserClient) getWithRetry(ctx context.Context, id int64) (*model.Customer, error) {
	var lastErr error
	for attempt := 1; attempt <= c.cfg.MaxAttempts; attempt++ {
		cust, err := c.getOnce(ctx, id)
		if err == nil || !retryable(err) {
			return cust, err
		}
		lastErr = err
		if attempt == c.cfg.MaxAttempts {
			break
		}
		wait := backoff(c.cfg.BaseBackoff, attempt)
		timer := time.NewTimer(wait)
		select {
		case <-ctx.Done():
			timer.Stop()
			return nil, ctx.Err() // the caller gave up — stop retrying
		case <-timer.C:
		}
	}
	return nil, fmt.Errorf("after %d attempts: %w", c.cfg.MaxAttempts, lastErr)
}
```

## Real-world scenario

During every User Service deploy, about 0.3% of calls hit a pod that just started shutting down and get `503`. With 3 jittered attempts, the error rate seen by Order Service drops to effectively zero, and no alert fires for routine deploys.

## Advantages and disadvantages

| Advantages | Disadvantages |
|---|---|
| Masks transient faults cheaply | Multiplies load during real outages |
| Improves availability without code in the callee | Adds latency (backoff time) |
| Simple to implement | Unsafe for non-idempotent operations |

## Common mistakes

- **Retry storms**: retries at every layer (3 × 3 × 3 = 27 attempts).
- **No jitter**: synchronised waves of retries.
- Retrying 4xx errors that will never succeed.
- Retrying non-idempotent operations without idempotency keys (double charges).
- Ignoring the caller's deadline and retrying after nobody is waiting.

:::quiz concept="retries"
Which combination is safest for retrying `POST /payments`?
- [ ] Retry on any error, immediately, up to 10 times
- [ ] Never retry POST requests
- [x] Retry transient failures with jittered backoff, a small attempt limit, and an Idempotency-Key so the server can de-duplicate
- [ ] Retry only on 400 Bad Request
> Retries are safe only for idempotent operations. An Idempotency-Key makes a POST idempotent from the server's perspective; jittered backoff and limits keep retries from amplifying an outage.
:::

@@lesson pattern-timeout

## The problem

A dependency stops responding without closing the connection. The caller waits — indefinitely, or for some huge default — while holding resources.

## Why it occurs

Networks and processes fail silently: a hung database lock, a GC pause, a dead load balancer, a half-open TCP connection. Without a deadline, nothing tells the caller to stop waiting. Go's `http.DefaultClient` has **no** timeout.

## Architecture

::diagram{id="p-timeout"}

## Request flow

1. The edge sets an overall deadline on the request context.
2. Each outbound call derives a shorter per-call deadline from it.
3. When a deadline passes, the call is abandoned, resources are freed, and an error is returned (`504` at the gateway).
4. Cancellation propagates downstream through `ctx`, so the callee stops working on an answer nobody will read.

## Go implementation

```go title="api-gateway/internal/proxy/proxy.go (excerpt)"
// The deadline travels with the request context: when it fires the
// upstream connection is closed and the upstream handler's ctx is cancelled.
ctx, cancel := context.WithTimeout(c.Request.Context(), route.Timeout)
defer cancel()
route.proxy.ServeHTTP(c.Writer, c.Request.WithContext(ctx))
```

Server-side timeouts protect the service from slow *clients*:

```go title="order-service/cmd/server/main.go (excerpt)"
srv := &http.Server{
	Addr:              cfg.HTTPAddr,
	Handler:           r,
	ReadHeaderTimeout: 5 * time.Second, // slowloris protection
	ReadTimeout:       10 * time.Second,
	WriteTimeout:      15 * time.Second,
	IdleTimeout:       60 * time.Second,
}
```

And databases need their own: `SET statement_timeout = '2s'` on the role or per transaction.

## Choosing values

- Base timeouts on measured latency: a common starting point is a little above the dependency's **p99.9**.
- Budget top-down so inner timeouts × attempts fit inside outer ones.
- Prefer deadline propagation (context) over independent fixed timeouts at every layer.

## Real-world scenario

A migration takes an `ACCESS EXCLUSIVE` lock on `orders` for 40 seconds. Without timeouts, every checkout request piles up behind it; the gateway runs out of goroutines and `/users` fails too. With a 2-second route timeout and a statement timeout, checkout returns `504` quickly, other routes stay healthy, and alerts point straight at the lock.

## Advantages and disadvantages

| Advantages | Disadvantages |
|---|---|
| Bounds resource usage per request | Too short: false failures under normal load |
| Turns silent hangs into visible errors | Too long: little protection |
| Enables retries and breakers to work | A timeout does not tell you whether the work happened |

## Common mistakes

- No timeout at all (default HTTP client, missing context).
- Timeouts longer at inner layers than outer layers.
- Treating a timeout as "the operation failed" and retrying a non-idempotent call.
- Forgetting server-side timeouts, leaving the service open to slow-client attacks.

:::quiz concept="timeouts"
After a timeout calling Payment Service, what can Order Service safely conclude?
- [ ] The payment failed
- [ ] The payment succeeded
- [x] It did not get an answer in time; the payment may or may not have happened
- [ ] Payment Service is down
> A timeout reports the caller's waiting, not the callee's outcome. Use idempotency keys and status checks to resolve the ambiguity.
:::

@@lesson pattern-bulkhead

## The problem

Order Service calls both User Service and Payment Service. User Service becomes slow (5 seconds per call). Soon every goroutine and connection in Order Service is waiting on User Service — and payment calls, which are perfectly healthy, can't get a connection either.

## Why it occurs

Shared resource pools — goroutines, HTTP connection pools, database connections, worker threads — let one slow dependency consume all of them. A ship with no internal walls sinks from a single hole.

## Architecture

::diagram{id="p-bulkhead"}

## Request flow

1. Each dependency gets its own bounded pool (a semaphore, a separate client with its own connection limit, or a separate worker pool).
2. A call first acquires a slot in its dependency's pool.
3. If the pool is full, the call fails fast (or waits briefly) instead of consuming shared resources.
4. Other dependencies' pools are unaffected.

## Go implementation

A semaphore per dependency with a short acquisition timeout:

```go
// Bulkhead limits concurrent calls to one dependency.
type Bulkhead struct {
	slots chan struct{}
	wait  time.Duration
}

var ErrBulkheadFull = errors.New("bulkhead full")

func NewBulkhead(max int, wait time.Duration) *Bulkhead {
	return &Bulkhead{slots: make(chan struct{}, max), wait: wait}
}

func (b *Bulkhead) Do(ctx context.Context, fn func(context.Context) error) error {
	timer := time.NewTimer(b.wait)
	defer timer.Stop()
	select {
	case b.slots <- struct{}{}: // acquire
	case <-timer.C:
		return ErrBulkheadFull // fail fast instead of piling up
	case <-ctx.Done():
		return ctx.Err()
	}
	defer func() { <-b.slots }() // release
	return fn(ctx)
}

// Wiring: one bulkhead per dependency.
userCalls := NewBulkhead(20, 50*time.Millisecond)
paymentCalls := NewBulkhead(40, 50*time.Millisecond)
```

Separate `http.Transport`s with `MaxConnsPerHost` give connection-level bulkheads, and separate pgx pools per workload (API vs batch jobs) protect the database path.

## Real-world scenario

A recommendations widget calls a slow ML service. With a 10-slot bulkhead and a fallback to "popular items", the widget degrades gracefully while checkout — on its own pool — is unaffected.

## Advantages and disadvantages

| Advantages | Disadvantages |
|---|---|
| Contains the blast radius of slow dependencies | More pools to size and monitor |
| Predictable resource usage | Idle capacity in one compartment can't help another |
| Pairs naturally with fallbacks | Wrong sizes reject legitimate traffic |

## Common mistakes

- One shared pool for all dependencies (the default for most clients).
- Unbounded waiting for a slot — the queue becomes the new resource leak.
- Sizing bulkheads without measuring concurrency (`concurrency ≈ throughput × latency`, Little's law).

:::quiz concept="bulkhead"
Order Service's single HTTP client pool is exhausted by slow calls to User Service, so payment calls also fail. Which pattern addresses this specifically?
- [ ] Retry with backoff
- [x] Bulkhead: separate, bounded resource pools per dependency
- [ ] CQRS
- [ ] Event sourcing
> Bulkheads isolate resources per dependency, so one slow dependency can only exhaust its own compartment.
:::

@@lesson pattern-saga

## The problem

Placing an order needs Payment Service to charge, Inventory Service to reserve stock and Shipping Service to schedule delivery — each with its own database. If reserving stock fails after the charge succeeded, there is no `ROLLBACK` across services.

## Why it occurs

Database per service removes cross-service ACID transactions, and two-phase commit is impractical (blocking, availability, lack of support). A business transaction still spans services.

## Architecture

::diagram{id="p-saga"}

## Request flow

A saga is a sequence of **local transactions**. Each step has a **compensating transaction** that semantically undoes it:

| Step | Action | Compensation |
|---|---|---|
| 1 | Create order (`PENDING`) | Mark order `CANCELLED` |
| 2 | Charge payment | Refund payment |
| 3 | Reserve inventory | Release reservation |
| 4 | Schedule shipment | Cancel shipment |
| 5 | Confirm order | — (pivot: after this, the saga only moves forward) |

If step *k* fails, the saga runs compensations for steps *k−1 … 1* in reverse.

Run the saga, inject failures at each step, and watch compensation:

::widget{name="saga"}

## Orchestration vs choreography

- **Orchestration**: a coordinator (here, in Order Service) sends commands and tracks state. Explicit, observable, easier to change; the orchestrator is a central dependency.
- **Choreography**: each service reacts to the previous service's event (`PaymentCaptured` → Inventory reserves → `StockReserved` → Shipping…). No central component, but the flow is implicit and cyclic dependencies creep in.

## Go implementation (orchestrated, persisted)

```go
type Step struct {
	Name       string
	Action     func(ctx context.Context, s *SagaState) error
	Compensate func(ctx context.Context, s *SagaState) error
}

func (o *Orchestrator) Run(ctx context.Context, s *SagaState) error {
	for i := s.NextStep; i < len(o.steps); i++ {
		step := o.steps[i]
		if err := step.Action(ctx, s); err != nil {
			o.log.Warn("saga step failed; compensating", "saga", s.ID, "step", step.Name, "err", err)
			return o.compensate(ctx, s, i-1)
		}
		s.NextStep = i + 1
		if err := o.store.Save(ctx, s); err != nil { // persist progress: survive crashes
			return err
		}
	}
	return nil
}

func (o *Orchestrator) compensate(ctx context.Context, s *SagaState, from int) error {
	for i := from; i >= 0; i-- {
		step := o.steps[i]
		if step.Compensate == nil {
			continue
		}
		// Compensations must eventually succeed: retry with backoff, then alert a human.
		if err := retry(ctx, func() error { return step.Compensate(ctx, s) }); err != nil {
			s.Status = "COMPENSATION_FAILED"
			_ = o.store.Save(ctx, s)
			return fmt.Errorf("compensate %s: %w", step.Name, err)
		}
	}
	s.Status = "CANCELLED"
	return o.store.Save(ctx, s)
}
```

Each `Action` and `Compensate` call must be **idempotent**, because a crash-and-resume can repeat them. Commands and replies typically travel over the broker, written through the outbox.

## Real-world scenario

A travel booking saga reserves a flight, a hotel and a car. The car rental API is down, so the saga cancels the hotel and flight reservations and tells the customer — instead of leaving them with a flight to nowhere. Durable workflow engines (Temporal, AWS Step Functions) implement exactly this with persistence and retries built in.

## Advantages and disadvantages

| Advantages | Disadvantages |
|---|---|
| Consistency across services without distributed locks | Temporary inconsistency between steps |
| Each service keeps local ACID transactions | Compensations are business logic, not free undo |
| Survives partial failures with persistence | Complex: state, idempotency, monitoring of stuck sagas |

## Common mistakes

- Treating compensation as rollback — you can't un-send an email; you send an apology.
- Non-idempotent steps that misbehave when retried after a crash.
- Not persisting saga state, so a crash leaves money charged and nothing reserved.
- Not handling **compensation failure** (alert, manual intervention queue).
- Isolation anomalies: other requests can see intermediate states (use semantic locks such as `PENDING` statuses).

:::quiz concept="saga"
In an orchestrated saga, payment succeeded and inventory reservation failed. What happens next?
- [ ] The database rolls back the payment automatically
- [x] The orchestrator runs the payment step's compensating action (refund) and marks the order cancelled
- [ ] The saga retries the inventory step forever
- [ ] The customer is charged and the order stays pending
> There is no cross-service rollback. The saga semantically undoes completed steps in reverse order using compensations.
:::

@@lesson pattern-outbox

## The problem

After creating an order, Order Service must publish `order.created`. Two writes — the database and the broker — can't be made atomic:

- Commit, then publish: if the process crashes (or the broker is down) after commit, the event is **lost**.
- Publish, then commit: if the commit fails, consumers act on an order that **doesn't exist**.

## Why it occurs

A database transaction can't include an external system. This is the **dual-write problem**, and it silently corrupts event-driven systems: confirmation emails never sent, stock never reserved, analytics wrong — with nothing in the logs at the time.

## Architecture

::diagram{id="p-outbox"}

## Request flow

1. In one local transaction: write the business change **and** insert the event into an `outbox` table.
2. Commit. Both exist, or neither does.
3. A relay reads unpublished outbox rows in order and publishes them to the broker, waiting for confirms.
4. It marks rows as published. If publishing fails, rows stay pending and are retried.
5. Consumers de-duplicate by event ID, because a relay crash between publish and mark causes a re-publish (at-least-once).

## Go implementation

Writing the event in the order's transaction:

```go title="order-service/internal/repository/order_repository.go (excerpt)"
// 5. The event, in the same transaction. A relay publishes it later.
if err := insertOutbox(ctx, tx, "order.created", o); err != nil {
	return nil, false, err
}
if err := tx.Commit(ctx); err != nil {
	return nil, false, fmt.Errorf("commit: %w", err)
}
```

Claiming and publishing pending events safely with several relay instances:

```go title="order-service/internal/repository/order_repository.go (excerpt)"
rows, err := tx.Query(ctx,
	`SELECT id, event_id, event_type, aggregate_id, payload, created_at
	 FROM outbox WHERE published_at IS NULL
	 ORDER BY id LIMIT $1 FOR UPDATE SKIP LOCKED`, limit)
...
for _, p := range batch {
	if publishErr = publish(ctx, p.event); publishErr != nil {
		break // keep order: retry the rest next tick
	}
	published = append(published, p.rowID)
}
if len(published) > 0 {
	_, err = tx.Exec(ctx, `UPDATE outbox SET published_at = now() WHERE id = ANY($1)`, published)
}
```

## Variants

- **Polling relay** (our implementation): simple; latency up to one interval.
- **Change Data Capture**: Debezium tails the Postgres WAL and publishes outbox inserts to Kafka — lower latency, no polling load.
- **Listen/Notify**: Postgres `NOTIFY` wakes the relay immediately after commit.

## Real-world scenario

RabbitMQ is down for 20 minutes during a cluster upgrade. Orders keep being accepted; 3,400 events accumulate in the outbox. When the broker returns, the relay drains them in order within seconds and every customer gets their confirmation — late, but correct. Try it in the [Architecture Lab](#/lab) with *RabbitMQ down*.

## Advantages and disadvantages

| Advantages | Disadvantages |
|---|---|
| Atomic state change + event — no lost or phantom events | Extra table, relay process and monitoring |
| Broker outages delay events instead of losing them | At-least-once: consumers must be idempotent |
| Preserves event order per producer | Added latency (polling interval) |

## Common mistakes

- Publishing directly "right after commit" and calling it good enough.
- Unbounded outbox growth — delete or archive published rows.
- Not alerting on the age of the oldest unpublished event.
- Parallel publishing that breaks ordering for the same aggregate.

:::quiz concept="outbox"
Order Service commits an order, then crashes before publishing `order.created` directly to RabbitMQ. With the transactional outbox, what happens?
- [ ] The event is lost; the outbox only helps when the broker is down
- [x] The event row was committed with the order, so the relay publishes it after the service restarts
- [ ] The order is rolled back
- [ ] RabbitMQ replays the event automatically
> The event lives in the same database transaction as the order. Whatever happens after commit, the relay will eventually publish it.
:::

@@lesson pattern-cqrs

## The problem

The order screen needs orders joined with customer names, shipment status and payment state, filtered and sorted many ways, at thousands of requests per second. The write model — normalised tables with constraints optimised for correct updates — is a poor fit for those queries, and the data spans several services.

## Why it occurs

Reads and writes have different shapes and scales. A single model compromises both: write-optimised schemas need expensive joins to read; read-optimised (denormalised) schemas make writes complex and error-prone. In microservices, the data for one screen is spread across services.

## Architecture

::diagram{id="p-cqrs"}

## Request flow

1. **Commands** (`CreateOrder`, `CancelOrder`) go to the write model, which enforces invariants transactionally.
2. Changes are published as events (via the outbox or CDC).
3. **Projectors** consume events from one or many services and update **read models** shaped for specific queries (a denormalised table, a search index, a cache).
4. **Queries** read only from read models.

## Go implementation

A projector keeping an `order_summaries` table in a read-optimised store:

```go
func (p *Projector) Handle(ctx context.Context, e OrderEvent) error {
	// Idempotent upsert guarded by version: out-of-order or duplicate events are harmless.
	_, err := p.db.Exec(ctx, `
		INSERT INTO order_summaries (order_id, user_id, customer_name, status, total_cents, version, updated_at)
		VALUES ($1, $2, $3, $4, $5, $6, $7)
		ON CONFLICT (order_id) DO UPDATE SET
			status      = EXCLUDED.status,
			total_cents = EXCLUDED.total_cents,
			version     = EXCLUDED.version,
			updated_at  = EXCLUDED.updated_at
		WHERE order_summaries.version < EXCLUDED.version`,
		e.OrderID, e.UserID, p.names.Lookup(e.UserID), e.Status, e.TotalCents, e.Version, e.OccurredAt)
	return err
}
```

The `WHERE version <` clause makes the projection idempotent and resilient to reordering.

## Real-world scenario

Customer support needs to search orders by email, product, status and date across three services. A projector builds an Elasticsearch index from `order.*`, `user.*` and `shipment.*` events. Support search is fast and never touches the transactional databases.

## Advantages and disadvantages

| Advantages | Disadvantages |
|---|---|
| Read models optimised per query; scale reads independently | Eventual consistency between write and read |
| Cross-service views without runtime joins | More moving parts: projectors, extra stores |
| Write model stays simple and correct | Rebuilding projections requires replayable events |

## Common mistakes

- Applying CQRS to simple CRUD where one model works fine.
- Ignoring read-your-own-writes (users don't see what they just did).
- Non-idempotent projectors that double-count on redelivery.
- No way to rebuild a corrupted projection.

:::quiz concept="cqrs"
What is the defining idea of CQRS?
- [ ] Every service must use event sourcing
- [x] Separating the model that handles commands (writes) from the models that serve queries (reads)
- [ ] Using a different database vendor for each service
- [ ] Caching all queries in Redis
> CQRS separates write and read responsibilities, letting each be modelled and scaled for its job. Event sourcing is often combined with it but is not required.
:::

@@lesson pattern-event-sourcing

## The problem

The business asks: "What was this order's state last Tuesday at 14:00, and who changed it?" Your table only holds the current state; each `UPDATE` destroyed the previous one. Audit logs are incomplete and drift from reality.

## Why it occurs

CRUD models store **state**, not the **changes** that produced it. History is lost by default, and reconstructing it later is unreliable.

## Architecture

::diagram{id="p-event-sourcing"}

## Request flow

1. Load the aggregate by reading its event stream (`OrderCreated`, `ItemAdded`, `OrderPaid`) and folding the events into state — optionally starting from a snapshot.
2. Run business logic against that state to decide.
3. Append new events with an **expected version** (optimistic concurrency). A conflicting concurrent append fails and is retried.
4. Projections subscribe to the stream to build read models (usually with CQRS).

## Go implementation

```go
type Order struct {
	ID      int64
	Status  Status
	Total   int64
	Version int
}

func (o *Order) Apply(e Event) {
	switch ev := e.Data.(type) {
	case OrderCreated:
		o.ID, o.Status, o.Total = ev.OrderID, StatusPending, ev.TotalCents
	case OrderPaid:
		o.Status = StatusConfirmed
	case OrderCancelled:
		o.Status = StatusCancelled
	}
	o.Version = e.Version
}

func (s *Service) Cancel(ctx context.Context, id int64, reason string) error {
	events, err := s.store.Load(ctx, id)
	if err != nil {
		return err
	}
	var o Order
	for _, e := range events {
		o.Apply(e)
	}
	if !o.Status.CanTransitionTo(StatusCancelled) {
		return ErrInvalidTransition
	}
	// Fails with ErrVersionConflict if someone appended since we loaded.
	return s.store.Append(ctx, id, o.Version, OrderCancelled{OrderID: id, Reason: reason})
}
```

```sql
CREATE TABLE events (
    aggregate_id BIGINT      NOT NULL,
    version      INTEGER     NOT NULL,
    type         TEXT        NOT NULL,
    data         JSONB       NOT NULL,
    occurred_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (aggregate_id, version)   -- optimistic concurrency: duplicate version = conflict
);
```

## Real-world scenario

A bank ledger is naturally event-sourced: the balance is the sum of transactions, never an overwritten number. Auditors can replay any account to any point in time, and new reports ("monthly interest") are built by replaying history into a new projection.

## Advantages and disadvantages

| Advantages | Disadvantages |
|---|---|
| Complete, reliable audit history | Steep learning curve; unusual for most teams |
| Temporal queries and debugging by replay | Event schema evolution is permanent (events are immutable) |
| New projections from existing history | Querying current state requires projections |
| Natural fit with event-driven integration | Long streams need snapshots |

## Common mistakes

- Event-sourcing the whole system instead of the few aggregates that benefit.
- Using the event store as a message queue for other services (publish integration events separately).
- Storing "update" events with field diffs instead of meaningful business events.
- Deleting or editing events to fix bugs instead of appending corrective events.

:::quiz concept="event-sourcing"
In an event-sourced system, how do you fix an order that was wrongly cancelled?
- [ ] Delete the `OrderCancelled` event
- [ ] Update the `OrderCancelled` event's data
- [x] Append a new corrective event (for example `OrderReinstated`) that records the fix
- [ ] Restore a database backup
> Events are immutable facts. Corrections are new facts, which keeps the audit trail truthful about what happened and when.
:::

@@lesson pattern-idempotency

## The problem

A customer taps **Place order**. The request reaches Order Service, which creates the order — but the response is lost to a flaky mobile connection. The app retries. Without protection, the customer now has two orders and two charges.

## Why it occurs

Retries are everywhere: users double-click, apps retry on timeout, gateways and clients retry on 503, brokers redeliver messages. With at-least-once delivery, **duplicates are normal**, not exceptional.

## Architecture

::diagram{id="p-idempotency"}

## Request flow

1. The client generates a unique **Idempotency-Key** per logical operation and sends it with every attempt.
2. The server atomically claims the key (unique constraint) in the same transaction as the work.
3. It stores a fingerprint of the request and the result.
4. A repeat with the same key returns the stored result without redoing the work.
5. The same key with a different request body is rejected (`422`).

Click "Place order" as impatiently as you like:

::widget{name="idempotency"}

## Go implementation

The handler requires the key; the service checks it first; the repository makes the claim atomic:

```go title="order-service/internal/repository/order_repository.go (excerpt)"
tag, err := tx.Exec(ctx,
	`INSERT INTO idempotency_keys (user_id, key, request_hash) VALUES ($1, $2, $3)
	 ON CONFLICT (user_id, key) DO NOTHING`,
	o.UserID, p.IdempotencyKey, p.RequestHash)
if err != nil {
	return nil, false, fmt.Errorf("claim idempotency key: %w", err)
}
if tag.RowsAffected() == 0 {
	// Key already used: verify the same request, return the original order.
	...
	return existing, true, nil
}
```

Two concurrent requests with the same key can't both insert: the second blocks on the primary key until the first transaction finishes, then sees the conflict.

For **message consumers**, the event ID plays the same role:

```go title="notification-service/internal/consumer/consumer.go (excerpt)"
if seen {
	log.Info("duplicate event skipped")
	_ = d.Ack(false)
	return
}
```

## Naturally idempotent operations

Sometimes no key is needed: `PUT /users/42/name` with the same body twice gives the same result; `UPDATE ... SET status='CANCELLED' WHERE id=$1 AND status IN (...)` is safe to repeat; `DELETE` of an already-deleted resource can return success. Design operations to be idempotent where possible.

## Real-world scenario

Stripe's API requires `Idempotency-Key` on POST requests and stores the response for 24 hours. A merchant's server retries a charge after a timeout; Stripe returns the original charge object instead of charging the card twice.

## Advantages and disadvantages

| Advantages | Disadvantages |
|---|---|
| Retries become safe everywhere | Storage for keys and results (with expiry) |
| Enables at-least-once messaging without duplicates | Clients must generate and persist keys |
| Simple mental model for API consumers | Concurrent duplicate handling needs care |

## Common mistakes

- Checking "does the key exist?" then inserting, in two steps (a race).
- Storing the key in a different transaction from the work.
- Calling external dependencies *before* checking the key, so retries repeat side effects.
- Generating a new key per retry on the client (defeats the purpose).
- Accepting a reused key with a different body.

:::quiz concept="idempotency"
Where should the client generate the Idempotency-Key for "Place order"?
- [ ] Freshly on every HTTP attempt
- [x] Once per logical order (e.g. when the checkout screen loads) and reused for every retry of that order
- [ ] On the server, after the order is created
- [ ] From the current timestamp in seconds
> The key identifies the user's intent, not the HTTP attempt. Reusing it across retries is what lets the server recognise duplicates.
:::

@@lesson pattern-tracing

## The problem

A checkout request takes 2.3 seconds. Logs from five services each look normal. Which hop was slow, and why?

## Why it occurs

A single user action fans out across services, queues and databases. Each service only sees its own part. Without a shared identifier and timing for every hop, you cannot reconstruct the request's path or find where time was spent.

## Architecture

::diagram{id="p-tracing"}

## Request flow

1. The first service (gateway) starts a **trace** with a unique trace ID and a root **span**.
2. Every outgoing call carries the context in the W3C `traceparent` header (`00-<trace-id>-<parent-span-id>-<flags>`).
3. Each service creates child spans for its work (handlers, DB queries, outbound calls), recording timing and attributes.
4. Spans are exported asynchronously to a collector and assembled by trace ID into a waterfall.

::widget{name="trace-waterfall"}

## Go implementation

With OpenTelemetry, instrumentation is mostly wiring:

```go
import (
	"go.opentelemetry.io/contrib/instrumentation/github.com/gin-gonic/gin/otelgin"
	"go.opentelemetry.io/contrib/instrumentation/net/http/otelhttp"
	"go.opentelemetry.io/otel"
	"go.opentelemetry.io/otel/exporters/otlp/otlptrace/otlptracegrpc"
	"go.opentelemetry.io/otel/propagation"
	sdktrace "go.opentelemetry.io/otel/sdk/trace"
)

func setupTracing(ctx context.Context, service string) (func(context.Context) error, error) {
	exp, err := otlptracegrpc.New(ctx) // OTEL_EXPORTER_OTLP_ENDPOINT from env
	if err != nil {
		return nil, err
	}
	tp := sdktrace.NewTracerProvider(
		sdktrace.WithBatcher(exp),
		sdktrace.WithSampler(sdktrace.ParentBased(sdktrace.TraceIDRatioBased(0.1))), // 10%
		sdktrace.WithResource(newResource(service)),
	)
	otel.SetTracerProvider(tp)
	otel.SetTextMapPropagator(propagation.TraceContext{}) // W3C traceparent
	return tp.Shutdown, nil
}

// Incoming requests: one span per request.
r.Use(otelgin.Middleware("order-service"))

// Outgoing requests: inject traceparent automatically.
httpClient := &http.Client{Transport: otelhttp.NewTransport(transport)}

// Custom spans around important work.
ctx, span := otel.Tracer("order-service").Start(ctx, "CreateOrder")
defer span.End()
span.SetAttributes(attribute.Int64("order.items", int64(len(in.Items))))
```

For messages, inject the trace context into AMQP/Kafka headers when publishing and extract it when consuming, so the email span links back to the order request.

## Real-world scenario

The waterfall for a slow checkout shows Order Service waiting 1.9 s on `GET /internal/users/42`, inside which User Service spent 1.8 s on a cache miss followed by a sequential scan. A missing index on a newly added query — found in minutes instead of hours.

## Advantages and disadvantages

| Advantages | Disadvantages |
|---|---|
| End-to-end latency breakdown per request | Instrumentation effort across every service |
| Shows dependencies and call patterns | Storage cost (mitigated by sampling) |
| Links to logs and metrics via trace ID | Broken propagation anywhere breaks the trace |

## Common mistakes

- Forgetting to propagate context through goroutines and message headers.
- 100% sampling in high-traffic production (cost) — or sampling so low that errors are never captured (use tail-based sampling for errors and slow traces).
- High-cardinality or sensitive data in span attributes.

:::quiz concept="tracing"
Spans from Order Service and User Service for the same request appear as two separate traces. What is the most likely cause?
- [ ] The two services use different log levels
- [x] Trace context (the `traceparent` header) is not being propagated on the outbound HTTP call
- [ ] The collector is down
- [ ] Sampling is set to 100%
> Without context propagation, User Service starts a new trace. Wrapping the HTTP client's transport with `otelhttp` injects `traceparent` automatically.
:::

@@lesson pattern-rate-limiting

## The problem

A buggy client loops and sends 3,000 requests per second; a scraper hammers search; a partner's batch job floods your API at 9:00 every morning. Shared capacity is consumed by a few callers, and everyone else sees errors.

## Why it occurs

Capacity is finite and shared, while demand is unbounded and uneven. Without limits, the most aggressive caller determines everyone's experience — and an overloaded service often fails completely rather than gracefully.

## Architecture

::diagram{id="rate-limit"}

## Request flow

1. Identify the caller (user ID, API key, IP).
2. Atomically check and update their allowance (token bucket in Redis).
3. Allowed → forward, with `RateLimit-Remaining` headers. Denied → `429 Too Many Requests` with `Retry-After`.
4. Clients back off and retry later.

::widget{name="token-bucket"}

## Go implementation

The gateway's Redis-backed token bucket is covered in detail in [Rate limiting and request validation](#/lesson/m04/rate-limiting). For per-instance limits (protecting a single service from its callers, or as a fallback when Redis is down), Go's `golang.org/x/time/rate` is a token bucket in one line:

```go
limiter := rate.NewLimiter(rate.Limit(100), 200) // 100 req/s sustained, bursts of 200

func limit(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		if !limiter.Allow() {
			w.Header().Set("Retry-After", "1")
			http.Error(w, "too many requests", http.StatusTooManyRequests)
			return
		}
		next.ServeHTTP(w, r)
	})
}
```

## Rate limiting vs load shedding

- **Rate limiting** enforces fairness per caller.
- **Load shedding** protects the service as a whole: reject (or degrade) work when the service itself is near capacity — e.g. when in-flight requests exceed a threshold — regardless of who sent it. Shed low-priority traffic first.

## Real-world scenario

A ticketing site opens sales for a popular concert. Per-user limits stop bots from monopolising checkout; a virtual waiting room (queue-based admission) plus load shedding keeps the purchase flow responsive for the users who are admitted.

## Advantages and disadvantages

| Advantages | Disadvantages |
|---|---|
| Fairness and abuse protection | Legitimate bursts may be rejected |
| Predictable load on services | Distributed limits need shared state (Redis) |
| Explicit back-pressure (429 + Retry-After) | Keying is tricky (NAT, spoofed IPs, shared keys) |

## Common mistakes

- Limiting only at one layer, while internal callers can still overwhelm a service.
- Returning 500 or 503 instead of 429, so clients don't know to back off.
- Non-atomic distributed counters (races).
- Keying by an IP read from an untrusted `X-Forwarded-For`.

:::quiz concept="rate-limiting"
What is the difference between rate limiting and load shedding?
- [ ] They are the same thing
- [x] Rate limiting caps each caller's usage for fairness; load shedding rejects work when the service as a whole is overloaded, regardless of caller
- [ ] Load shedding happens only at the database
- [ ] Rate limiting is only for unauthenticated users
> Both protect capacity, from different angles. Use rate limits for fairness and abuse; use load shedding to keep the service alive under aggregate overload.
:::

@@lesson pattern-load-balancing

## The problem

Order Service runs on six instances. Requests must be spread across them so no instance is overwhelmed, slow or failed instances are avoided, and capacity can be added by adding instances.

## Why it occurs

Horizontal scaling only works if traffic is distributed well. Naive distribution ignores that requests differ in cost, instances differ in health and warm-up, and connections can be long-lived.

## Architecture

::diagram{id="p-load-balancing"}

## Request flow

1. A request (or connection) arrives at the balancer.
2. The balancer chooses a healthy backend according to its algorithm.
3. Health checks continuously remove failing backends and restore recovered ones.

Compare algorithms with uneven request costs and a slow instance:

::widget{name="load-balancer"}

## Algorithms

| Algorithm | Chooses | Good for | Weakness |
|---|---|---|---|
| Round robin | Next in turn | Uniform, cheap requests | Ignores load and slowness |
| Weighted round robin | In proportion to weights | Mixed instance sizes; canaries | Static weights |
| Least connections / requests | Fewest in-flight | Variable request cost | Needs shared view per balancer |
| Power of two choices | Better of two random picks | Large fleets; nearly as good as least-requests, cheap | Randomness |
| Consistent hashing | By key (user, session) | Cache affinity, sticky state | Uneven load with hot keys |
| Latency-aware (EWMA) | Fastest recently | Heterogeneous performance | Can herd onto one instance |

## Go implementation

A least-requests picker with power-of-two-choices:

```go
type Backend struct {
	URL      *url.URL
	inFlight atomic.Int64
	healthy  atomic.Bool
}

func (b *Balancer) Pick() *Backend {
	healthy := b.healthySnapshot()
	switch len(healthy) {
	case 0:
		return nil
	case 1:
		return healthy[0]
	}
	a := healthy[rand.IntN(len(healthy))]
	c := healthy[rand.IntN(len(healthy))]
	if c.inFlight.Load() < a.inFlight.Load() {
		return c
	}
	return a
}

func (b *Balancer) Do(req *http.Request) (*http.Response, error) {
	be := b.Pick()
	if be == nil {
		return nil, ErrNoHealthyBackends
	}
	be.inFlight.Add(1)
	defer be.inFlight.Add(-1)
	return b.client.Do(rewrite(req, be.URL))
}
```

## L4 vs L7

- **L4 (TCP)**: balances connections; fast; protocol-agnostic. kube-proxy ClusterIP is L4. Long-lived HTTP/2 connections defeat per-request balancing.
- **L7 (HTTP)**: balances individual requests, can route by path/header, retry, and read status codes. Envoy, NGINX, service meshes.

## Real-world scenario

After a deploy, new pods are cold (empty caches, JIT-less but still warming connection pools). Round robin sends them a full share immediately and their latency spikes. Least-requests naturally sends them less until they catch up; some balancers add a **slow start** ramp for new instances.

## Advantages and disadvantages

| Advantages | Disadvantages |
|---|---|
| Horizontal scale and redundancy | The balancer itself must be highly available |
| Health-aware routing hides failures | Sticky sessions undermine even distribution |
| Smooth rolling deploys | Wrong algorithm creates hot spots |

## Common mistakes

- Relying on L4 balancing for gRPC/HTTP2 traffic.
- Health checks that only test "process up", not "can serve".
- Sticky sessions to cover for state that should live in a shared store.

:::quiz concept="load-balancing"
Requests to Order Service vary from 5 ms (reads) to 2 s (exports). Which algorithm avoids piling slow requests onto one instance?
- [ ] Round robin
- [x] Least outstanding requests (or power-of-two-choices on in-flight count)

> Round robin ignores how busy each instance is. Choosing by in-flight requests adapts to uneven request cost.
:::
