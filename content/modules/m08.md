@@lesson docker-fundamentals

Containers package a service with everything it needs to run — binary, libraries, CA certificates, configuration defaults — into an artifact that behaves the same on a laptop, in CI and in production.

## What is a container?

A container is a normal Linux process with isolation provided by the kernel:

- **Namespaces** give it its own view of process IDs, network interfaces, mount points and hostname.
- **cgroups** limit how much CPU, memory and I/O it may use.
- A **root filesystem** comes from an image.

There is no guest operating system, which is why containers start in milliseconds and are much lighter than virtual machines.

| | Virtual machine | Container |
|---|---|---|
| Isolation | Hypervisor, full guest kernel | Kernel namespaces and cgroups |
| Start time | Seconds to minutes | Milliseconds |
| Size | Gigabytes | Megabytes |
| Security boundary | Strong | Weaker (shared kernel) — harden accordingly |

## Images and layers

An **image** is a read-only, layered filesystem plus metadata (entrypoint, environment, exposed ports). Each Dockerfile instruction that changes files creates a layer, identified by a content hash. Layers are cached and shared: ten images built on the same base store that base once.

A **container** is a running instance of an image with a thin writable layer on top. Anything written there disappears when the container is removed — persistent data belongs in volumes.

## Registries and tags

Images are pushed to a **registry** (Docker Hub, GHCR, ECR, Artifact Registry) and pulled by name and tag: `registry.example.com/oms/order-service:2.3.1`.

:::rule Never deploy :latest
Tags are mutable pointers. `:latest` can change between two pods of the same deployment, making rollbacks and debugging impossible. Deploy immutable tags (a version or git SHA) — or pin by digest (`@sha256:…`).
:::

## The build–ship–run loop

```bash
docker build -t order-service:dev ./order-service
docker run --rm -p 8082:8082 \
  -e DATABASE_URL=postgres://... -e RABBITMQ_URL=amqp://... \
  order-service:dev
docker push registry.example.com/oms/order-service:2.3.1
```

## Why containers for microservices?

- **One artifact per service**, with its dependencies, built once and promoted through environments.
- **Uniform operations**: every service starts, stops, logs to stdout and reports health the same way, whatever it is written in.
- **Density**: many small services share machines efficiently.
- **The foundation for orchestration**: schedulers like Kubernetes manage containers.

:::quiz concept="docker"
A service writes uploaded files to `/data` inside its container. The container is replaced during a deploy. What happens to the files?
- [ ] They are copied into the new container automatically
- [x] They are lost, because the container's writable layer is discarded — unless `/data` is a mounted volume
- [ ] They are stored in the image registry
- [ ] Docker keeps them in a snapshot for 24 hours
> Containers are disposable. Durable data must live in volumes or external storage (databases, object storage).
:::

@@lesson dockerfiles

Go is ideal for containers: it compiles to a single static binary. A good Dockerfile builds that binary in one stage and ships it alone in a minimal image.

::diagram{id="docker-build"}

## The multi-stage Dockerfile

```dockerfile title="order-service/Dockerfile"
# syntax=docker/dockerfile:1.7
# ---- Stage 1: build a static binary ------------------------------------------
FROM golang:1.26-alpine AS builder
WORKDIR /src

# Dependencies first: this layer is cached until go.mod/go.sum change.
COPY go.mod go.sum ./
RUN --mount=type=cache,target=/go/pkg/mod go mod download

COPY . .
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 GOOS=linux go build -trimpath -ldflags="-s -w" -o /out/app ./cmd/server

# ---- Stage 2: minimal runtime ------------------------------------------------
# distroless/static: CA certificates and tzdata, no shell, no package manager.
FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=builder /out/app /app
EXPOSE 8082
USER nonroot:nonroot
ENTRYPOINT ["/app"]
```

## Line by line: why

| Instruction | Why |
|---|---|
| `FROM golang:… AS builder` | Full toolchain only in the build stage (~300 MB, never shipped) |
| `COPY go.mod go.sum` then `go mod download` | Dependency layer is cached until dependencies change; code edits rebuild in seconds |
| `--mount=type=cache` | BuildKit keeps module and build caches across builds |
| `CGO_ENABLED=0` | Produces a static binary with no libc dependency, required for `distroless/static` |
| `-trimpath -ldflags="-s -w"` | Reproducible paths; strip debug symbols (smaller binary) |
| `FROM distroless/static:nonroot` | Runtime has no shell, package manager or compiler — tiny attack surface |
| `USER nonroot` | A container breakout doesn't start as root |
| `ENTRYPOINT ["/app"]` (exec form) | The binary is PID 1 and receives `SIGTERM` directly for graceful shutdown |

The final image is roughly 15–25 MB: the binary plus CA certificates.

## Health checks without a shell

Distroless has no `curl`, so the binary checks itself:

```go title="order-service/cmd/server/main.go (excerpt)"
healthcheck := flag.Bool("healthcheck", false, "probe the local /healthz endpoint and exit")
flag.Parse()
if *healthcheck {
	os.Exit(probe()) // GET http://127.0.0.1:8082/healthz → exit 0 or 1
}
```

Compose then uses `test: ["CMD", "/app", "-healthcheck"]`.

## .dockerignore

```text
.git
*.md
Dockerfile
.dockerignore
```

Keeps the build context small and stops secrets or local artifacts from leaking into layers.

## What can go wrong?

- **Shell-form entrypoints** (`ENTRYPOINT /app`) run under `/bin/sh -c`, which may not forward signals — no graceful shutdown.
- **Secrets in build args or layers** stay in the image history forever. Use BuildKit secret mounts.
- **Running as root** by default.
- **Fat images** with compilers and shells: slower pulls, larger attack surface, more CVEs to patch.
- **Debugging distroless**: no shell to `exec` into. Use `kubectl debug` with an ephemeral container.

:::quiz concept="dockerfile"
Why does the Dockerfile copy `go.mod` and `go.sum` and download modules **before** copying the rest of the source?
- [ ] Go requires go.mod to be in its own layer
- [x] So the dependency download layer stays cached when only source code changes, making rebuilds fast
- [ ] To make the final image smaller
- [ ] Because COPY can only copy two files at a time
> Docker reuses a layer if its inputs are unchanged. Separating dependency files means code-only changes skip the slow download step.
:::

@@lesson compose

Docker Compose describes a multi-container application in one YAML file and runs it with one command. It's how every developer runs the full Order Management System locally.

::diagram{id="compose"}

## The file, explained

```yaml title="docker-compose.yml (excerpt)"
name: order-management

x-go-healthcheck: &go-healthcheck
  # Distroless images have no curl: the binary probes itself.
  test: ["CMD", "/app", "-healthcheck"]
  interval: 10s
  timeout: 3s
  retries: 3
  start_period: 10s

services:
  api-gateway:
    build: ./api-gateway
    ports: ["8080:8080"]                 # the only API port published to your machine
    environment:
      USER_SERVICE_URL: http://user-service:8081   # resolved by Compose DNS
      ORDER_SERVICE_URL: http://order-service:8082
      REDIS_ADDR: redis:6379
      JWT_SECRET: ${JWT_SECRET:?set JWT_SECRET in .env}   # fail if unset
    healthcheck: *go-healthcheck
    depends_on:
      redis: { condition: service_healthy }
      user-service: { condition: service_healthy }
      order-service: { condition: service_healthy }

  order-service:
    build: ./order-service
    environment:
      DATABASE_URL: postgres://orders:${ORDERS_DB_PASSWORD}@orders-db:5432/orders?sslmode=disable
      RABBITMQ_URL: amqp://${RABBITMQ_USER}:${RABBITMQ_PASSWORD}@rabbitmq:5672/
    depends_on:
      orders-db: { condition: service_healthy }
      orders-migrate: { condition: service_completed_successfully }
      # No dependency on rabbitmq being healthy: the outbox lets Order Service
      # accept orders while the broker is down.
      rabbitmq: { condition: service_started }

  orders-migrate:
    image: migrate/migrate:v4.18.1
    command: ["-path=/migrations", "-database=postgres://orders:${ORDERS_DB_PASSWORD}@orders-db:5432/orders?sslmode=disable", "up"]
    volumes: ["./order-service/migrations:/migrations:ro"]
    depends_on:
      orders-db: { condition: service_healthy }
    restart: "no"

  orders-db:
    image: postgres:16-alpine
    volumes: [orders-data:/var/lib/postgresql/data]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U orders -d orders"]
      interval: 5s
      retries: 10

volumes:
  orders-data:
```

The [full file](#/playground?file=docker-compose.yml) defines 11 services: gateway, three Go services, two migration jobs, two databases, Redis and RabbitMQ.

## Start and stop it (simulated)

Start services in different orders, stop dependencies, and watch health checks and `depends_on` conditions at work.

::widget{name="compose-sim"}

:::sim What is simulated
Container states, health-check timing and log lines are modelled in your browser to mirror what `docker compose up` does with this file. To run the real system: `cp .env.example .env && docker compose up --build` in `codebase/order-management`.
:::

## Everyday commands

```bash
docker compose up --build -d          # build and start in the background
docker compose ps                     # status and health
docker compose logs -f order-service  # follow one service's logs
docker compose stop rabbitmq          # simulate a broker outage
docker compose start rabbitmq
docker compose down                   # stop and remove containers (keeps volumes)
docker compose down -v                # ... and delete the data volumes
```

## What can go wrong?

- `depends_on` **without conditions** only orders container *creation*; the database may not be ready. Use `condition: service_healthy`, and still make services retry connections.
- Secrets in the committed compose file. Use `.env` (git-ignored) locally.
- Treating Compose as production orchestration: it is single-host with no rescheduling or rolling updates.

:::quiz concept="compose"
`order-service` has `depends_on: orders-migrate: { condition: service_completed_successfully }`. What does this guarantee?
- [ ] Migrations run every time order-service restarts
- [x] order-service starts only after the migration container has exited with code 0
- [ ] The database is backed up before migrating
- [ ] The migration runs inside the order-service container
> The condition waits for the one-shot migration job to finish successfully, so the service never starts against an outdated schema.
:::

@@lesson networking-config

Containers need to find each other, the outside world needs to reach some of them, and every one needs configuration. Compose and Kubernetes solve these the same way conceptually.

## Container networking

Compose creates a **user-defined bridge network** for the project. On it:

- Each container gets an IP address.
- An **embedded DNS server** resolves service names (`orders-db`, `user-service`) to those IPs.
- Containers on the network talk to each other on any port — `expose` is documentation only.
- Containers on *other* networks can't reach them unless you attach them.

### Published vs internal ports

```yaml
api-gateway:
  ports: ["8080:8080"]   # HOST:CONTAINER — reachable from your machine
user-service:
  # no ports: reachable only from inside the oms network
```

Publishing only the gateway mirrors production: services are private, and the edge is the only way in. A frequent mistake is `ports: ["5432:5432"]` on databases "for convenience" — on a shared machine that exposes your database.

### `localhost` inside a container

Inside a container, `localhost` is the container itself — not your machine and not other containers. Use service names (`http://user-service:8081`), or `host.docker.internal` to reach the host.

## Configuration through the environment

```yaml
environment:
  HTTP_ADDR: ":8082"
  DATABASE_URL: postgres://orders:${ORDERS_DB_PASSWORD}@orders-db:5432/orders?sslmode=disable
  USER_SERVICE_TIMEOUT: 800ms
```

- **`${VAR}`** is interpolated from your shell or `.env`.
- **`${VAR:?message}`** fails `compose up` with a clear message if unset — use it for required secrets.
- **`${VAR:-default}`** provides a fallback.

The service parses and validates these at startup (see [Configuration and logging](#/lesson/m02/config-logging)).

## Secrets

| Approach | Use |
|---|---|
| `.env` file (git-ignored) | Local development |
| Compose `secrets:` (files mounted at `/run/secrets/...`) | Avoids secrets in `docker inspect` output |
| Kubernetes Secrets | Cluster deployments (enable encryption at rest) |
| External secret managers (Vault, AWS/GCP secret managers) | Production: rotation, audit, fine-grained access |

:::rule Secrets never go into images
Anything copied into an image layer is readable by anyone who can pull the image — forever, even if a later layer deletes it.
:::

:::quiz concept="container-networking"
Inside the order-service container, which URL reaches User Service in the Compose setup?
- [ ] `http://localhost:8081`
- [x] `http://user-service:8081`
- [ ] `http://127.0.0.1:8081`
- [ ] `http://host.docker.internal:8080`
> On the shared network, Compose DNS resolves the service name. `localhost` would be order-service's own container.
:::

@@lesson healthchecks-volumes

Two features turn "a bunch of containers" into a dependable local system: **health checks**, so services start in the right order and broken ones are visible, and **volumes**, so data survives restarts.

## Health checks

```yaml
orders-db:
  image: postgres:16-alpine
  healthcheck:
    test: ["CMD-SHELL", "pg_isready -U orders -d orders"]
    interval: 5s       # how often
    timeout: 3s        # how long one check may take
    retries: 10        # consecutive failures before "unhealthy"
    start_period: 0s   # grace period during startup
```

A container moves through `starting → healthy` (or `unhealthy`). Other services can wait for `healthy` with `depends_on: { condition: service_healthy }`.

### What should a health check test?

| Check | Good for | Avoid |
|---|---|---|
| Process responds (`/healthz`) | Liveness, container health | Including dependency checks |
| Can serve requests (`/readyz`) | Readiness, traffic routing | Expensive queries every few seconds |
| Dependency reachable | Readiness of the dependent service | Restarting on dependency failure |

Our Go services expose both: `/healthz` (process alive) and `/readyz` (database reachable and not shutting down). Compose uses `/healthz`; Kubernetes uses both (see [Health checks, readiness and liveness](#/lesson/m09/health-probes)).

## Volumes

| Type | Example | Use |
|---|---|---|
| Named volume | `orders-data:/var/lib/postgresql/data` | Database data; managed by Docker; survives `down` |
| Bind mount | `./order-service/migrations:/migrations:ro` | Source files and config from your machine |
| tmpfs | `tmpfs: /tmp` | Scratch data in memory |

```yaml
services:
  orders-db:
    volumes: [orders-data:/var/lib/postgresql/data]
volumes:
  orders-data:
```

- `docker compose down` keeps named volumes; `docker compose down -v` deletes them.
- Mount read-only (`:ro`) whenever the container only reads.
- Redis in our setup has no volume and persistence disabled — it holds only rebuildable data, so losing it on restart is fine.

:::warn Volumes are not backups
A volume protects data from container restarts, not from disk failure, corruption or `down -v`. Production databases need managed backups, point-in-time recovery, and restore drills.
:::

:::quiz concept="healthchecks"
Why do the databases in our Compose file have health checks if the Go services also retry connections?
- [ ] Health checks replace the need for retries
- [x] So dependent containers start only when the database accepts connections, avoiding a burst of startup failures — retries still handle later outages
- [ ] Postgres refuses connections from containers without health checks
- [ ] Health checks back up the database
> Health checks plus `condition: service_healthy` give clean startup ordering. Runtime retries are still needed because dependencies can fail at any time after startup.
:::

:::quiz concept="volumes"
You run `docker compose down -v`. What happens to the orders in `orders-db`?
- [ ] They are kept in the named volume
- [x] They are deleted, because `-v` removes named volumes
- [ ] They are exported to a backup file
- [ ] Only migrations are reset
> `-v` removes the volumes declared in the compose file. Use it to reset local state, never against data you need.
:::

@@lesson orchestration

Compose is perfect for one machine. Production needs more: many machines, failures handled without humans, scaling with load, and deploys without downtime. That is what an **orchestrator** provides.

## What Compose doesn't do

| Need | Compose | Orchestrator (Kubernetes) |
|---|---|---|
| Run across many hosts | No | Yes — schedules containers onto a cluster |
| Replace failed containers on other machines | No (restarts on the same host) | Yes — reschedules elsewhere |
| Scale with load | Manual `--scale` | Horizontal Pod Autoscaler |
| Zero-downtime deploys | No | Rolling updates, surge/unavailable controls |
| Traffic only to ready instances | No | Readiness-gated Service endpoints |
| Service discovery across hosts | Single-host DNS | Cluster DNS + Services |
| Config and secrets management | `.env` | ConfigMaps, Secrets, external secret operators |
| Resource guarantees | Basic limits | Requests, limits, QoS, quotas |

## The orchestrator's core idea: desired state

You declare *what* you want — "3 replicas of order-service:2.3.1, each with 250m CPU, ready when `/readyz` returns 200" — and controllers continuously reconcile reality to match:

```text
observe current state → diff with desired state → act → repeat
```

A node dies: the Deployment controller notices 2 of 3 replicas and starts a new pod elsewhere. You change the image tag: it rolls pods one by one, waiting for readiness. No scripts, no pager at 3 a.m. for routine failures.

## Choosing a platform

| Option | When it fits |
|---|---|
| Managed Kubernetes (EKS, GKE, AKS) | Many services and teams; you want the ecosystem and portability |
| Serverless containers (Cloud Run, Fargate, Container Apps) | Fewer services; you'd rather not operate a cluster |
| Nomad, ECS | Simpler orchestration needs; existing cloud commitment |

:::rec Platform effort is real
Kubernetes is powerful and complex. A small team may be better served by a serverless container platform until the number of services and the need for control justify a cluster. Module 10 covers Kubernetes in depth.
:::

:::quiz concept="orchestration"
A node running two order-service containers loses power. With Kubernetes, what happens?
- [ ] Nothing until an operator redeploys
- [x] The controller sees fewer ready replicas than desired and schedules replacement pods on healthy nodes
- [ ] Compose restarts them on the same node
- [ ] Traffic keeps going to the dead node until DNS expires
> Kubernetes reconciles toward the declared replica count, rescheduling pods elsewhere, and readiness-gated endpoints route traffic only to pods that are up.
:::
