@@lesson observability-intro

In a monolith, you debug by reading one log file or attaching a debugger. In a distributed system, a single click touches five services, two databases and a broker. **Observability** is the ability to answer questions about that system's behaviour from the outside — including questions you didn't anticipate.

## Monitoring vs observability

- **Monitoring** checks known failure modes: "is error rate above 1%?", "is the disk 90% full?". Dashboards and alerts for things you predicted.
- **Observability** lets you investigate unknown ones: "why are checkouts slow only for users in Brazil using the Android app since 14:05?" It requires rich, correlated telemetry.

## The three pillars (and how they connect)

| Signal | Answers | Strength | Cost |
|---|---|---|---|
| **Metrics** | *Is something wrong? How much?* | Cheap to store, great for alerts and trends | Aggregated — no individual request detail |
| **Logs** | *What exactly happened in this service?* | Rich detail, arbitrary context | Volume; hard to correlate without IDs |
| **Traces** | *Where did this request spend its time across services?* | End-to-end causality and latency breakdown | Instrumentation effort; sampled |

They are most powerful **linked**: a latency alert (metric) → an exemplar trace for a slow request → the logs for that trace ID in each service.

::diagram{id="obs-pipeline"}

## The golden signals

Google SRE's four golden signals for any user-facing service:

1. **Latency** — time to serve requests (separate successful from failed requests).
2. **Traffic** — demand (requests per second).
3. **Errors** — rate of failed requests (explicit 5xx, wrong content, slow-as-failure).
4. **Saturation** — how full the service is (CPU, memory, pool usage, queue depth).

Two shorthand methods:

- **RED** for request-driven services: **R**ate, **E**rrors, **D**uration.
- **USE** for resources: **U**tilisation, **S**aturation, **E**rrors.

## What makes telemetry useful

- **Consistent identifiers** across services: `request_id`, `trace_id`, `service`, `user_id`.
- **Structured** data (JSON logs, labelled metrics) rather than free text.
- **Low cardinality** where it matters (metric labels) and **high detail** where it's cheap (logs, trace attributes).
- **SLOs** (service-level objectives) that turn signals into decisions: "99.9% of `POST /orders` succeed within 300 ms over 28 days".

:::quiz concept="observability"
Which signal is best for answering "which of the five services made this specific checkout slow?"
- [ ] A CPU utilisation metric
- [ ] An error-rate dashboard
- [x] A distributed trace of that request
- [ ] The gateway's access log alone
> Traces record the timing of every hop for one request, across services. Metrics are aggregated; a single service's log only shows its own part.
:::

@@lesson structured-logging

Logs are the most detailed record of what a service did. In a distributed system they're only useful if every line is **structured** and every service tags it with the same **correlation IDs**.

## Structured logs with slog

```go title="order-service/cmd/server/main.go (excerpt)"
log := slog.New(slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{Level: lvl})).
	With("service", "order-service")
```

```json
{"time":"2026-10-31T09:41:12.481Z","level":"INFO","msg":"order created","service":"order-service","request_id":"8f2c1e7a-4b0d-4a51-9a63-31c0a3d5f6b2","order_id":8812,"total_cents":4200}
```

Every field is queryable: `service="order-service" level="ERROR"`, `request_id="8f2c…"`, `order_id=8812`.

## Correlation IDs across services

1. The **gateway** generates `X-Request-ID` for each external request.
2. Each **service** reads it, stores it in the request context and echoes it in responses.
3. Every **outbound call** forwards it.
4. Every **log line** includes it via a request-scoped logger.

```go title="order-service/internal/middleware/middleware.go (excerpt)"
func RequestID() gin.HandlerFunc {
	return func(c *gin.Context) {
		id := c.GetHeader(HeaderRequestID)
		if id == "" || len(id) > 64 {
			id = uuid.NewString()
		}
		c.Header(HeaderRequestID, id)
		c.Request = c.Request.WithContext(reqctx.WithRequestID(c.Request.Context(), id))
		c.Next()
	}
}
```

```go title="order-service/internal/client/user_client.go (excerpt)"
if rid := reqctx.RequestID(ctx); rid != "" {
	req.Header.Set("X-Request-ID", rid) // correlation across services
}
```

Now one query finds every line from every service for one user action. With OpenTelemetry, use the **trace ID** as the correlation ID — or log both.

## Messages need correlation too

Asynchronous flows break naive correlation. Put the request ID (and trace context) in message headers when publishing, and attach it to the consumer's logger when handling. The notification email's log line then links back to the HTTP request that created the order.

## What to log

| Log | Don't log |
|---|---|
| One access line per request (method, route, status, duration) | Passwords, tokens, API keys, full card numbers |
| State changes (`order created`, `circuit opened`) | Full request/response bodies by default |
| Handled failures with context (`fallback used`) | The same error at every layer |
| Startup config summary (non-secret) | High-volume debug output in production |

:::rule Personal data
Logs are copied to many systems and kept for a long time. Treat them as sensitive: avoid personal data, mask what you must log, and set retention deliberately (GDPR and similar laws apply).
:::

## Operating logs

- Write to **stdout**; the platform ships logs (Fluent Bit, Vector, the cloud agent).
- **Sample** noisy success logs at very high volume; never sample errors.
- Set **retention** per environment; cold-store older logs if you need them for audits.

:::quiz concept="logging"
A request flows gateway → Order Service → User Service. What lets you find all log lines for it across the three services?
- [ ] Logging at DEBUG level everywhere
- [x] A correlation ID (request or trace ID) generated at the edge, propagated in headers and included in every log line
- [ ] Synchronising the clocks of all servers
- [ ] Writing all services' logs to one file
> Correlation requires a shared identifier carried across every hop and attached to every log entry.
:::

@@lesson metrics-prometheus

Metrics are numeric time series — cheap to collect, cheap to store, ideal for dashboards and alerts. **Prometheus** scrapes them from your services; **Grafana** visualises them.

## Metric types

| Type | Goes | Example | Query with |
|---|---|---|---|
| **Counter** | Only up (resets on restart) | `http_requests_total` | `rate()`, `increase()` |
| **Gauge** | Up and down | `db_pool_acquired_conns`, `queue_depth` | as-is, `avg_over_time()` |
| **Histogram** | Buckets of observations | `http_request_duration_seconds` | `histogram_quantile()` |
| Summary | Client-side quantiles | (rarely used in microservices) | can't be aggregated across instances |

Prefer **histograms** for latency: they can be aggregated across replicas, unlike summaries.

## Instrumenting a Go service

```go
import (
	"github.com/prometheus/client_golang/prometheus"
	"github.com/prometheus/client_golang/prometheus/promauto"
	"github.com/prometheus/client_golang/prometheus/promhttp"
)

var (
	httpRequests = promauto.NewCounterVec(prometheus.CounterOpts{
		Name: "http_requests_total",
		Help: "HTTP requests by route, method and status code.",
	}, []string{"route", "method", "code"})

	httpDuration = promauto.NewHistogramVec(prometheus.HistogramOpts{
		Name:    "http_request_duration_seconds",
		Help:    "HTTP request latency.",
		Buckets: []float64{.005, .01, .025, .05, .1, .25, .5, 1, 2.5, 5},
	}, []string{"route", "method"})
)

func Metrics() gin.HandlerFunc {
	return func(c *gin.Context) {
		start := time.Now()
		c.Next()
		route := c.FullPath() // "/v1/orders/:id" — NOT the raw path
		if route == "" {
			route = "unmatched"
		}
		httpRequests.WithLabelValues(route, c.Request.Method, strconv.Itoa(c.Writer.Status())).Inc()
		httpDuration.WithLabelValues(route, c.Request.Method).Observe(time.Since(start).Seconds())
	}
}

// In main:
r.Use(Metrics())
r.GET("/metrics", gin.WrapH(promhttp.Handler()))
```

Add domain and dependency metrics too: `orders_created_total`, `outbox_pending_events`, `circuit_breaker_state{dependency="user-service"}`, pgx pool stats.

## Cardinality: the classic mistake

Each unique combination of label values is a separate time series. `route="/v1/orders/8812"` creates one series *per order*; `user_id` creates one per user. Prometheus's memory explodes and queries crawl.

:::rule Labels must have bounded values
Use route templates, status codes, method, dependency name, region. Never IDs, emails, raw paths or error messages. Put high-cardinality detail in logs and traces instead.
:::

## PromQL you'll use daily

```promql
# Request rate per route (RED: Rate)
sum by (route) (rate(http_requests_total{service="order-service"}[5m]))

# Error ratio (RED: Errors)
sum(rate(http_requests_total{service="order-service", code=~"5.."}[5m]))
  / sum(rate(http_requests_total{service="order-service"}[5m]))

# p99 latency per route (RED: Duration)
histogram_quantile(0.99,
  sum by (le, route) (rate(http_request_duration_seconds_bucket{service="order-service"}[5m])))
```

## Alerting on symptoms, not causes

Alert on what users feel — error ratio and latency against SLOs — rather than on every CPU spike. A good SLO alert uses **burn rate**: "we are consuming the monthly error budget 14× faster than sustainable over the last hour". Cause-level metrics (CPU, pool usage) belong on dashboards for diagnosis.

:::quiz concept="metrics"
Why is `user_id` a bad Prometheus label on `http_requests_total`?
- [ ] Prometheus labels must be numeric
- [x] It creates a separate time series per user (unbounded cardinality), exhausting Prometheus memory
- [ ] User IDs are personal data and Prometheus encrypts labels
- [ ] Counters cannot have labels
> Every distinct label combination is a new series. Bounded labels (route, method, code) keep the series count manageable; per-user detail belongs in logs or traces.
:::

@@lesson tracing-otel

A trace shows one request's journey through the system as a tree of timed **spans**. It is the fastest way to answer "where did the time go?" and "which service failed?" for a specific request.

## Concepts

- **Trace** — all spans for one request, sharing a `trace_id`.
- **Span** — one unit of work (an HTTP handler, a DB query, an outbound call) with start, duration, status and attributes. Each span has a parent, except the root.
- **Context propagation** — passing `trace_id` and the current span ID to the next service, using the W3C `traceparent` header:

```text
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             ver  trace-id (16 bytes)              parent span id   sampled
```

## OpenTelemetry

OpenTelemetry (OTel) is the vendor-neutral standard for traces, metrics and logs: one SDK, instrumentation libraries for common packages, and the **OTLP** protocol to export to any backend (Tempo, Jaeger, Honeycomb, Datadog…).

```go
// Incoming HTTP: a server span per request, continuing any incoming traceparent.
r.Use(otelgin.Middleware("order-service"))

// Outgoing HTTP: client spans + traceparent injection.
client := &http.Client{Transport: otelhttp.NewTransport(baseTransport)}

// Database: one span per query.
pc.ConnConfig.Tracer = otelpgx.NewTracer()

// Your own spans around meaningful work.
ctx, span := tracer.Start(ctx, "outbox.publishBatch")
defer span.End()
if err != nil {
	span.RecordError(err)
	span.SetStatus(codes.Error, "publish failed")
}
```

The full setup (exporter, sampler, propagator) is shown in [Distributed Tracing](#/lesson/m07/pattern-tracing).

## Sampling

Tracing every request at high volume is expensive. Options:

| Strategy | How | Trade-off |
|---|---|---|
| Head-based (e.g. 10%) | Decide at the root; children follow | Cheap; may miss rare errors |
| Parent-based | Respect the caller's decision | Keeps traces complete |
| Tail-based | Collector buffers spans and keeps traces with errors or high latency | Captures what matters; needs collector resources |

A common setup: parent-based 5–10% head sampling, plus tail sampling in the OTel Collector to keep all errors and slow traces.

## What can go wrong?

- **Broken propagation** at one hop (a client without instrumentation, a message without headers) splits traces in two.
- **Goroutines** started without the request `ctx` lose the span parent.
- **Sensitive attributes** (tokens, personal data) captured by over-eager auto-instrumentation.

:::quiz concept="tracing"
What does the W3C `traceparent` header carry between services?
- [ ] The full list of spans recorded so far
- [x] The trace ID, the parent span ID and sampling flags
- [ ] The request body hash
- [ ] The user's identity
> Only the minimal context travels in-band; spans are exported out-of-band to the collector and joined by trace ID.
:::

@@lesson health-probes

Health endpoints tell the platform whether to **send traffic** to an instance and whether to **restart** it. Getting them wrong is a classic way to turn a small incident into a total outage.

::diagram{id="probes"}

## Three kinds of probe

| Probe | Question | Failure action | Should check |
|---|---|---|---|
| **Startup** | Has the app finished starting? | Keep waiting (then restart if it never does) | Same as liveness, with a generous budget |
| **Liveness** | Is the process alive and not wedged? | **Restart the container** | Only the process itself |
| **Readiness** | Can it serve requests right now? | **Remove from load balancing** (no restart) | Critical dependencies, warm-up, shutdown state |

## Our implementation

```go title="order-service/cmd/server/main.go (excerpt)"
r.GET("/healthz", func(c *gin.Context) { c.JSON(http.StatusOK, gin.H{"status": "ok"}) })
r.GET("/readyz", func(c *gin.Context) {
	if !ready.Load() {
		c.JSON(http.StatusServiceUnavailable, gin.H{"status": "shutting down"})
		return
	}
	pingCtx, cancel := context.WithTimeout(c.Request.Context(), time.Second)
	defer cancel()
	if err := repo.Ping(pingCtx); err != nil {
		c.JSON(http.StatusServiceUnavailable, gin.H{"status": "database unavailable"})
		return
	}
	// RabbitMQ is deliberately NOT checked: thanks to the outbox, orders can
	// be accepted while the broker is down.
	c.JSON(http.StatusOK, gin.H{"status": "ready"})
})
```

## The probe designs that cause outages

:::danger Dependencies in liveness
If `/healthz` checks Postgres and Postgres has a 30-second failover, **every** pod fails liveness, Kubernetes restarts all of them at once, and they come back to a thundering herd of reconnects and cold caches. Restarting your service cannot fix the database. Liveness checks the process only.
:::

- **Readiness that checks non-critical dependencies** takes the whole fleet out of rotation for something you could have degraded around (Order Service doesn't check RabbitMQ for this reason).
- **Readiness that checks downstream services' readiness** creates cascades: one slow service makes everything upstream unready.
- **Expensive probes** (a heavy query every 5 seconds × 50 pods) add real load.
- **Too-aggressive thresholds** restart pods during GC pauses or brief CPU starvation.

## Readiness during shutdown

Flipping readiness to `503` on `SIGTERM` (before draining) is part of [graceful shutdown](#/lesson/m02/graceful-shutdown): it removes the pod from rotation while in-flight requests complete.

:::quiz concept="probes"
Postgres is briefly unavailable. What should Order Service's probes do?
- [ ] Fail liveness, so Kubernetes restarts the pods
- [x] Fail readiness (stop receiving traffic) but keep liveness passing (no restart)
- [ ] Pass both and let requests fail
- [ ] Fail both
> Restarting cannot fix the database and causes a thundering herd. Readiness removes the pod from rotation until it can serve again.
:::

## A method for any incident

1. **Scope the symptom** with RED metrics at the edge: which routes, since when, how bad? (Gateway error rate and latency.)
2. **Follow the dependency graph**: which service's errors or latency rose *first*? Downstream causes usually show up before upstream symptoms.
3. **Check saturation**: pool usage, queue depth, CPU. A full connection pool explains latency without errors; a growing queue explains delays without failures.
4. **Pick an exemplar**: open a failed or slow trace and see exactly which span failed.
5. **Read the logs** for that trace/request ID in the failing service.
6. **Mitigate first** (roll back, fail over, shed load, open a breaker), then find the root cause.

## Scenarios to practise

| Incident | Signals to look for |
|---|---|
| User Service crash | Order Service 503s rise with it; User Service request rate drops to zero; breaker opens |
| Slow orders-db | Order Service p99 climbs, pool *waiting* rises, gateway 504s follow; no errors in User Service |
| Broker outage | Orders still succeed; outbox pending events grow; notification throughput drops to zero |
| Bad deploy (500s) | Error rate jumps for one service at a deploy marker; latency normal |
| Traffic spike | Request rate ×4; latency and pool usage up; rate-limit 429s rise |

:::quiz concept="metrics"
Gateway p99 latency for `POST /orders` triples, with no rise in errors. Order Service's DB pool shows many requests *waiting* for a connection. What is the most likely cause?
- [ ] User Service is down
- [x] orders-db queries became slow (or a long transaction holds connections), exhausting the pool so requests queue
- [ ] The rate limiter is rejecting requests
- [ ] RabbitMQ is down
> Waiting on the pool signals saturation: connections are held longer than usual. Latency rises before errors (timeouts) appear. Check slow queries and locks in orders-db.
:::
