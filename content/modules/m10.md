@@lesson k8s-core

Three Kubernetes objects run almost every stateless service: a **Pod** runs the containers, a **Deployment** keeps the right number of identical Pods running and updates them safely, and a **Service** gives them a stable network identity.

::diagram{id="k8s-objects"}

## Pods

A Pod is the smallest deployable unit: one or more containers sharing a network namespace (one IP, `localhost` between them) and volumes. Pods are **ephemeral** — they get new IPs when replaced, and you almost never create them directly.

## Deployments

```yaml title="deploy/k8s/order-service.yaml (excerpt)"
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
  labels: { app: order-service, tier: backend }
spec:
  replicas: 3
  revisionHistoryLimit: 5
  selector:
    matchLabels: { app: order-service }   # which pods this Deployment owns
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1          # at most one extra pod during a rollout
      maxUnavailable: 0    # never drop below the desired replica count
  template:                # the pod blueprint
    metadata:
      labels: { app: order-service, tier: backend }
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: order-service
          image: registry.example.com/oms/order-service:2.3.1   # immutable tag
          ports:
            - { name: http, containerPort: 8082 }
```

How it works: the Deployment creates a **ReplicaSet** for each version of the pod template; the ReplicaSet creates Pods. Changing the template (e.g. the image tag) creates a new ReplicaSet and gradually scales the old one down — a rolling update. `kubectl rollout undo` scales the previous ReplicaSet back up.

## Services

```yaml title="deploy/k8s/order-service.yaml (excerpt)"
apiVersion: v1
kind: Service
metadata:
  name: order-service      # DNS: order-service.<namespace>.svc.cluster.local
spec:
  type: ClusterIP
  selector: { app: order-service }
  ports:
    - { name: http, port: 8082, targetPort: http }
```

A Service selects Pods by **label** and keeps an **EndpointSlice** of the ready ones. Other pods call `http://order-service:8082`; kube-proxy routes the connection to one ready Pod.

| Service type | Reachable from |
|---|---|
| ClusterIP (default) | Inside the cluster |
| NodePort | Each node's IP on a high port |
| LoadBalancer | A cloud load balancer (public or internal) |
| Headless (`clusterIP: None`) | DNS returns pod IPs directly (client-side balancing, StatefulSets) |

## Everyday commands

```bash
kubectl apply -f deploy/k8s/
kubectl get deploy,rs,pods -l app=order-service
kubectl rollout status deploy/order-service
kubectl logs -l app=order-service --tail=50 -f
kubectl describe pod order-service-7d9f…        # events: scheduling, probes, OOMKills
kubectl rollout undo deploy/order-service
```

:::quiz concept="k8s-workloads"
How does a Kubernetes Service know which Pods to send traffic to?
- [ ] It is configured with a list of pod IPs
- [x] It selects Pods by labels and routes only to the ready ones in its endpoints
- [ ] Pods register themselves via an API call
- [ ] It sends traffic to every pod in the namespace
> Label selectors decouple the Service from individual Pods. As Pods come and go, the endpoints list updates automatically, filtered by readiness.
:::

@@lesson config-secrets

The same container image runs in every environment. What differs — URLs, timeouts, credentials — is injected at runtime through **ConfigMaps** and **Secrets**.

## ConfigMaps

```yaml title="deploy/k8s/config.yaml (excerpt)"
apiVersion: v1
kind: ConfigMap
metadata:
  name: order-service-config
data:
  HTTP_ADDR: ":8082"
  USER_SERVICE_URL: "http://user-service:8081"
  USER_SERVICE_TIMEOUT: "800ms"
  USER_SERVICE_MAX_ATTEMPTS: "3"
  OUTBOX_RELAY_INTERVAL: "500ms"
  LOG_LEVEL: "info"
```

## Secrets

```yaml title="deploy/k8s/config.yaml (excerpt)"
apiVersion: v1
kind: Secret
metadata:
  name: order-service-secrets
type: Opaque
stringData:
  database-url: "postgres://orders:CHANGE_ME@orders-db:5432/orders?sslmode=require"
  rabbitmq-url: "amqp://oms:CHANGE_ME@rabbitmq:5672/"
```

## Consuming them

```yaml title="deploy/k8s/order-service.yaml (excerpt)"
envFrom:
  - configMapRef: { name: order-service-config }       # every key becomes an env var
env:
  - name: DATABASE_URL
    valueFrom: { secretKeyRef: { name: order-service-secrets, key: database-url } }
```

Alternatively mount them as **files** (`volumes` + `volumeMounts`). Mounted files update when the ConfigMap/Secret changes (after a short delay); environment variables only change when the pod restarts.

## What Secrets do — and don't — protect

:::warn base64 is not encryption
Secret values are only base64-encoded in the API. Anyone with `get secrets` permission in the namespace can read them, and by default they are stored unencrypted in etcd.
:::

Production practice:

- Enable **encryption at rest** for Secrets in etcd (KMS provider).
- Restrict access with **RBAC**; most humans and workloads should not read Secrets.
- Prefer an **external secret store** (Vault, AWS Secrets Manager, GCP Secret Manager) synchronised by the External Secrets Operator or the Secrets Store CSI driver — with rotation and audit logs.
- Never commit real Secret manifests to git; use sealed-secrets or SOPS if you must store them encrypted.

## Rolling out config changes

Changing a ConfigMap does not restart pods using it as environment variables. Common approaches: include a hash of the config in a pod annotation (Helm/Kustomize do this), so a config change rolls the Deployment — the same safe, gradual process as an image change.

:::quiz concept="k8s-config"
You update a ConfigMap consumed through `envFrom`. When do running pods see the new values?
- [ ] Immediately
- [ ] Within the kubelet sync period (about a minute)
- [x] Only after the pods are restarted (for example by a rollout)
- [ ] Never; ConfigMaps are immutable
> Environment variables are read at container start. Mounted ConfigMap files update in place, but env vars need a restart — usually triggered by a config-hash annotation.
:::

@@lesson ingress-networking

Kubernetes networking answers three questions: how do pods talk to each other, how do they find each other, and how does traffic get in from outside?

## The model

- Every Pod gets its own IP, and **every Pod can reach every other Pod** without NAT (implemented by the CNI plugin: Calico, Cilium, cloud CNIs).
- **Services** give groups of Pods stable virtual IPs; kube-proxy (iptables/IPVS) or eBPF forwards connections to ready endpoints.
- **CoreDNS** resolves `order-service` → the Service's ClusterIP (and `order-service.oms.svc.cluster.local` across namespaces).

## Ingress: HTTP into the cluster

An **Ingress** describes HTTP routing rules; an **Ingress controller** (NGINX, Traefik, cloud controllers) implements them.

```yaml title="deploy/k8s/ingress.yaml (excerpt)"
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: oms-api
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt
spec:
  ingressClassName: nginx
  tls:
    - hosts: [api.example.com]
      secretName: oms-api-tls
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api-gateway
                port: { number: 8080 }
```

Only the API Gateway is exposed; everything else stays ClusterIP. The newer **Gateway API** (`Gateway`, `HTTPRoute`) is the successor to Ingress with richer, role-oriented routing — worth adopting for new clusters.

## NetworkPolicy: default-deny between services

By default every pod can reach every other pod. That makes the gateway's trust model (`X-User-ID` set only by the gateway) unenforced. NetworkPolicies fix it:

```yaml title="deploy/k8s/ingress.yaml (excerpt)"
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: order-service-ingress
spec:
  podSelector:
    matchLabels: { app: order-service }
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector:
            matchLabels: { app: api-gateway }
      ports:
        - { protocol: TCP, port: 8082 }
```

(Order Service also receives no calls from User Service here; if it did, you'd add that peer explicitly.) Policies are only enforced if the CNI supports them.

## Service mesh (briefly)

A mesh (Istio, Linkerd, Cilium mesh) adds a proxy per pod or per node that provides **mTLS** between services, retries, timeouts, traffic splitting and uniform metrics — without changing application code. It's valuable at scale, but it is significant operational complexity; adopt it when you need its guarantees across many services.

:::quiz concept="ingress"
Why does Order Service's NetworkPolicy allow ingress only from the API gateway's pods?
- [ ] To improve performance
- [x] To enforce that only the gateway — which sets verified identity headers — can call it, so other pods can't forge `X-User-ID`
- [ ] Because Services can only have one client
- [ ] To enable TLS
> Without the policy any compromised or misconfigured pod could call Order Service with arbitrary identity headers. Network policy turns the trust assumption into an enforced rule.
:::

@@lesson probes-resources

Probes tell Kubernetes when a container is ready and alive; resources tell it how much CPU and memory to reserve and allow. Both are frequently misconfigured — and both have Go-specific details.

## Probes

```yaml title="deploy/k8s/order-service.yaml (excerpt)"
startupProbe:        # gives slow starts time before liveness kicks in
  httpGet: { path: /healthz, port: http }
  periodSeconds: 2
  failureThreshold: 30
readinessProbe:      # "send me traffic?" — checks the DB pool
  httpGet: { path: /readyz, port: http }
  periodSeconds: 5
  failureThreshold: 2
livenessProbe:       # "restart me?" — process only, never dependencies
  httpGet: { path: /healthz, port: http }
  periodSeconds: 10
  failureThreshold: 3
```

The design rules are covered in [Health checks, readiness and liveness](#/lesson/m09/health-probes): liveness checks only the process; readiness checks what the service needs to serve; the startup probe protects slow starts from premature restarts.

## Requests and limits

```yaml title="deploy/k8s/order-service.yaml (excerpt)"
resources:
  requests: { cpu: 250m, memory: 128Mi }   # what the scheduler reserves
  limits:   { cpu: "1",  memory: 256Mi }   # memory over limit = OOMKilled
```

| | CPU | Memory |
|---|---|---|
| **Request** | Guaranteed share; used for scheduling and as the HPA's utilisation baseline | Used for scheduling |
| **Limit** | Hard cap enforced by **throttling** (the process is paused for the rest of each 100 ms period) | Hard cap enforced by the **OOM killer** (container restarted) |

**QoS classes**: requests = limits for all resources → *Guaranteed*; some requests → *Burstable*; none → *BestEffort* (first to be evicted under pressure).

:::rec CPU limits are debated
CPU throttling causes latency spikes that are hard to diagnose. Many teams set CPU **requests** but no CPU limits for latency-sensitive services (so they can burst when the node has spare CPU), and always set **memory** limits. Measure throttling (`container_cpu_cfs_throttled_periods_total`) before deciding.
:::

## Go inside a container

- **GOMAXPROCS** — how many OS threads execute Go code in parallel. Before Go 1.25, Go used the node's core count (say 32) even with a 1-CPU limit, causing heavy throttling. Go 1.25+ reads the cgroup CPU limit automatically; for older versions set `GOMAXPROCS` from the limit (or use `go.uber.org/automaxprocs`).
- **GOMEMLIMIT** — a soft memory limit that makes the garbage collector work harder as the heap approaches it, instead of growing until the kernel OOM-kills the container. Set it a bit below the container limit:

```yaml title="deploy/k8s/order-service.yaml (excerpt)"
- name: GOMEMLIMIT
  valueFrom: { resourceFieldRef: { resource: limits.memory, divisor: "1" } }
- name: GOMAXPROCS
  valueFrom: { resourceFieldRef: { resource: limits.cpu, divisor: "1" } }
```

(In practice, many teams set `GOMEMLIMIT` to ~90% of the limit to leave room for non-heap memory.)

## Diagnosing

```bash
kubectl describe pod order-service-7d9f…   # Last State: Terminated, Reason: OOMKilled
kubectl top pods -l app=order-service      # live CPU/memory (metrics-server)
```

:::quiz concept="resource-limits"
A Go service with a 256 Mi memory limit is repeatedly OOMKilled under load, although its live heap is usually ~150 Mi. What setting most directly helps?
- [ ] Increase the CPU limit
- [x] Set `GOMEMLIMIT` somewhat below 256 Mi so the GC runs more aggressively before the kernel limit is reached
- [ ] Remove the liveness probe
- [ ] Set `GOMAXPROCS=1`
> Without GOMEMLIMIT the GC targets heap growth relative to the live heap (GOGC) and can overshoot the container limit. A soft limit keeps total memory under the cap.
:::

@@lesson scaling-rollouts

Kubernetes can add capacity automatically and replace versions without downtime. Both depend on settings you saw in the manifests — and on the service behaving well (readiness, graceful shutdown).

## Horizontal Pod Autoscaler

```yaml title="deploy/k8s/order-service.yaml (excerpt)"
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: order-service
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: order-service }
  minReplicas: 3
  maxReplicas: 12          # cap: 12 × 10 DB connections must fit Postgres limits
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 70 }
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0
      policies: [{ type: Percent, value: 100, periodSeconds: 30 }]
    scaleDown:
      stabilizationWindowSeconds: 300   # avoid flapping
      policies: [{ type: Pods, value: 1, periodSeconds: 60 }]
```

The HPA computes `desired = ceil(current × currentUtilisation / target)` every ~15 seconds. Utilisation is relative to the **request**, so CPU requests must be realistic. Scale on custom metrics (requests per second, queue depth via KEDA) when CPU doesn't track load — e.g. for I/O-bound services or queue consumers.

## Rolling updates

With `maxSurge: 1, maxUnavailable: 0` and 3 replicas:

1. Create 1 new pod (4 total). Wait for it to be **ready**.
2. Terminate 1 old pod (graceful shutdown drains it). 3 total.
3. Repeat until all pods run the new version.

Capacity never drops below 3, and a new version that never becomes ready stalls the rollout instead of replacing healthy pods — `kubectl rollout undo` then restores the previous ReplicaSet.

## PodDisruptionBudgets

```yaml title="deploy/k8s/order-service.yaml (excerpt)"
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: order-service
spec:
  minAvailable: 2
  selector:
    matchLabels: { app: order-service }
```

Voluntary disruptions (node drains for upgrades) must respect the PDB, so maintenance can never take Order Service below 2 pods.

## Progressive delivery

Rolling updates replace everything as soon as pods are ready. **Canary** releases (Argo Rollouts, Flagger) send a small percentage of traffic to the new version, analyse its error rate and latency automatically, and only then continue — rolling back on regression without human involvement.

:::quiz concept="autoscaling"
An HPA targets 70% CPU utilisation. 4 pods average 140% of their CPU **request**. Roughly how many replicas will it want?
- [ ] 4
- [ ] 6
- [x] 8
- [ ] 14
> desired = ceil(4 × 140 / 70) = 8, subject to maxReplicas and scale-up policies.
:::

:::quiz concept="rolling-deploys"
A new version's pods never pass readiness. With `maxUnavailable: 0`, what happens during the rollout?
- [ ] All old pods are replaced anyway, causing an outage
- [x] The rollout stalls: old pods keep serving because none can be removed until a new one is ready
- [ ] Kubernetes automatically rolls back after one minute
- [ ] Traffic is split 50/50
> With zero unavailability, an old pod is only removed after a new one becomes ready. A broken version can't take capacity away; you roll back with `kubectl rollout undo`.
:::

@@lesson production-checklist

Before a service takes real traffic, walk through this list. It condenses the course into the questions reviewers ask in a production-readiness review. Not every item applies to every service — but you should be able to explain why one doesn't.

## Reliability

- [ ] Timeouts on every inbound server and outbound call; budgets fit inside callers' deadlines.
- [ ] Retries only for transient errors and idempotent operations, with jittered backoff and a cap.
- [ ] Circuit breakers (and fallbacks where possible) on synchronous dependencies.
- [ ] Idempotency keys on retryable writes; idempotent consumers for messages.
- [ ] Transactional outbox (or CDC) for events tied to state changes.
- [ ] At least two replicas, spread across zones; PodDisruptionBudget.
- [ ] Graceful shutdown: readiness flip, drain delay, `Shutdown`, workers stopped in order.

## Observability

- [ ] Structured JSON logs with `service`, `request_id`/`trace_id`; no secrets or personal data.
- [ ] RED metrics per route with bounded labels; dependency and pool metrics.
- [ ] Distributed tracing with propagation across HTTP and messaging.
- [ ] Dashboards for golden signals; SLOs with burn-rate alerts; runbooks linked from alerts.

## Operations

- [ ] Liveness checks only the process; readiness checks what's needed to serve.
- [ ] CPU/memory requests from measurements; memory limit + `GOMEMLIMIT`.
- [ ] HPA with a `maxReplicas` that respects downstream limits (DB connections).
- [ ] Immutable image tags; rollback tested.
- [ ] Database migrations backward compatible (expand/contract), run once per deploy.
- [ ] Backups and restore drills for every stateful store.

## Security

- [ ] TLS at the edge; mTLS or network policies between services.
- [ ] Authentication at the gateway; authorisation in services next to the data.
- [ ] Secrets from a secret manager; none in images, repos or logs.
- [ ] Non-root, read-only filesystem, dropped capabilities, minimal base image.
- [ ] Dependency and image vulnerability scanning in CI (`govulncheck`, image scanners).
- [ ] Rate limits on public and expensive endpoints.

## Contracts and ownership

- [ ] API and event contracts documented (OpenAPI, event schemas) and versioned.
- [ ] Consumer-driven contract tests in CI.
- [ ] A clear owning team, on-call rotation and escalation path.

## Check your service against it

Of course the best way to internalise this list is to break things on purpose. Try the [Architecture Lab](#/lab) with every resilience pattern switched **off**, inject failures, and map each bad outcome to the checklist item that prevents it. Then work through the [engineering challenges](#/challenges).

:::quiz concept="production-readiness"
Which item is most likely to turn a short database failover into a full outage of every replica?
- [ ] Structured logging
- [x] A liveness probe that checks database connectivity
- [ ] An HPA with minReplicas = 3
- [ ] Immutable image tags
> A dependency check in liveness restarts every pod simultaneously during the failover, adding a thundering herd of restarts and reconnects on top of the original incident.
:::
